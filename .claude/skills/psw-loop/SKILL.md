# psw-loop

피드백 루프의 공통 절차다. 기획·설계·구현 스킬은 이 절차를 복사하지 않고 이 스킬을 호출한다.

## 무엇을 하는가

| 상황 | 처리 |
|---|---|
| `draft` 문서를 고친다 | 그대로 고친다. 결정이 끼면 결정 기록을 붙인다 |
| 아직 정해지지 않은 것(누락·모호)을 발견했다 | 미결 등록 (A) |
| 승인된(`approved`) 내용을 바꾸거나 없애야 한다 (모순, 실현 불가능, 사용자 번복) | 승인된 내용의 변경 (D) |
| 미결의 답으로 승인된 문서에 내용을 추가한다 | D 없이 반영하고 문서를 `draft`로 되돌린다 |

## 공통 규칙

- MUST: 결정, 변경 수락·거절, 미결 보류는 사용자만 정한다. 에이전트는 선택지와 추천안만 만든다
- MUST: 모르는 것은 추측하지 않고 미결로 등록한다
- MUST: 하위 단계에서 상위 문서를 고치지 않는다. 상위 문서 반영은 그 문서의 소유 스킬 절차를 따른다
  - REQ: `psw-interview`(범위·목록), `psw-req`(상세), 설계: `psw-design`
  - 소유 스킬이 아직 설치되지 않았으면 이 스킬에서 직접 반영하고, 그 사실을 보고한다
- 미결 ID는 `.claude/scripts/psw/next-id.sh OPEN`으로 발급한다. 직접 번호를 매기지 않는다
- 미결 항목 형식은 `references/open.md`를 따른다. 제목 줄과 `- 상태:` 줄은 스크립트가 읽는다
- 결정 기록 형식: `<값> 〔YYYY-MM-DD〕 <이유>` (harness-psw 8.1). 이유가 길면 커밋 본문에 적고 문서에는 한 줄만 둔다

## 절차

### A. 미결 등록

1. `next-id.sh OPEN`으로 ID를 받는다
2. `docs/open-question.md` 끝에 항목을 추가한다 (`상태: 미정`)
3. 원천 문서의 해당 위치에 `[OPEN-NNN]` 자리표시를 넣는다
   - 그 문서가 `approved`였다면 `status: draft`로 되돌린다
4. 보고: ID, 질문, 자리표시 위치

### B. 미결 해결

1. 사용자에게 질문한다. 선택지와 추천안을 함께 제시한다
2. 원천 문서의 자리표시를 값과 결정 기록으로 바꾼다 (예: `동시 로그인: 3대 〔2026-09-25〕 가족 공용 기기 고려`)
   - `approved` 문서였다면 `status: draft`로 되돌린다
3. `docs/open-question.md`에서 항목을 지운다
4. 커밋 트레일러: `Closes: OPEN-NNN`, 관련 요구사항이 있으면 `Refs:`

### C. 미결 보류

1. 사용자가 "지금 정하지 않고 진행한다"고 정했을 때만 한다
2. 항목의 상태를 `보류`로 바꾸고 `보류 사유:`에 `〔YYYY-MM-DD〕 <사유>`를 적는다
3. 자리표시는 그대로 둔다

### D. 승인된 내용의 변경

1. 변경 대상이 정말 승인된 내용인지 확인한다. `draft`면 D 없이 고친다
2. 작업 중이던 단계를 멈춘다
3. 영향 범위를 찾는다 (E 절차)
4. 사용자에게 변경안을 보인다
   - 대상 ID와 파일, 바꿀 내용, 사유(트리거: 모순·실현 불가능·사용자 번복), 영향 범위
5. 사용자가 정한다
   - 수락: 영향 범위의 문서를 소유 스킬 절차로 반영한다. 반영한 `approved` 문서는 `draft`로 되돌리고, 바뀐 값에 결정 기록을 붙인다. 커밋 본문에 변경 사유를 적고 트레일러 `Refs:`를 단다
   - 거절: 반영하지 않는다. 같은 요청이 다시 나올 만하면 해당 값 옆에 거절 이유를 결정 기록으로 남긴다
6. 변경안을 파일로 따로 남기지 않는다
   → 수락되면 결과가 원천 문서와 git에 남고, 거절되면 원천이 바뀌지 않는다

### E. 영향 분석

1. 바뀌는 ID로 `.claude/scripts/psw/find-refs.sh <ID...>`를 실행한다
   - 계열 전체를 보려면 접두사만 준다 (예: `FR-ORD-`)
2. 설계가 바뀌는 경우 아래 경로도 확인한다

| 바뀐 것 | 다시 볼 곳 |
|---|---|
| 상태 전이 (`_policy.md`) | 해당 상태를 바꾸는 FR, 관련 AC 테스트, 해당 목업 |
| 화면 (IA) | 해당 목업, 셸 메뉴 (`ui/kit/shell.js`) |
| 컴포넌트, 테마 | 해당 컴포넌트를 쓰는 목업 (`data-component`로 찾는다) |
| 코드 규칙 (`conventions.md`) | 규칙을 따르는 기존 코드. 고칠지 사용자에게 확인한다 |

3. 결과를 ID와 경로 목록으로 정리한다. 다시 산출하거나 검토할 문서만 고른다

### F. 종료 조건 확인

1. `.claude/scripts/psw/loop-status.sh [경로...]`를 실행한다
   - 경로를 주지 않으면 `docs` 전체와 모든 미결을 본다
   - 설계 루프를 도메인 단위로 끝낼 때는 해당 도메인 문서 경로를 준다
2. "종료 가능"이 나와야 루프를 끝낸다
   - 막는 것: `미정` 항목, 끊긴 자리표시
   - 막지 않는 것: `보류` 항목
3. 결과를 사용자에게 보고한다

## 단계 사이 루프

| 발견한 단계 | 발견한 결함 | 호출할 루프 |
|---|---|---|
| 설계 | 요구사항 결함 (상태 전이 누락 포함) | 기획 (`psw-req`, 범위가 바뀌면 `psw-interview`) |
| 설계 (백엔드 기초) | 키트 문서 조각의 REQ 초안 | 기획 (범위에 넣을지 사용자에게 확인하고 REQ로 만든다. 초안은 참고로만 쓴다) |
| 구현 | 설계 결함 (코드 규칙 포함) | 설계 |
| 구현 | 요구사항 결함 | 기획 |

- 발견한 단계의 작업은 멈추고, 상위 루프가 끝난 뒤 돌아간다
- 같은 불일치가 설계 루프에서 2회, 구현에서 같은 AC가 3회 반복되면 사용자에게 보고한다
