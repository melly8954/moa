# 코드 규칙

## 적용 범위

- 대상: `frontend/`, `backend/`, DB 마이그레이션
- 규칙과 코드가 다르면 규칙이 맞다. 코드를 고친다. "고치지 않는다"고 적은 예외는 뺀다
- 모호하면 추측하지 않고 `docs/open-question.md`에 등록한다

## 강도 표기

- `[MUST]` 지킨다. 어기면 결함이다
- `[SHOULD]` 지킨다. 어기면 이유를 커밋 본문이나 이 문서 예외 표에 적는다
- `NEVER` 하지 않는다

## 1. 백엔드

### 1.1 패키지 구조와 레이어 [MUST]

- <예: api(controller·application·service·repository·entity·dto), common(response·exception·security·config)>
- 의존 방향: `docs/design/architecture.md` 모듈 경계 절. 검사: <예: ArchUnit 레이어 테스트>

### 1.2 이름 [MUST]

- 코드 이름은 `docs/glossary.md`의 코드 이름을 따른다
- <클래스 접미사와 뜻. 예: *Controller, *Application(트랜잭션 경계), *Service(도메인 규칙)>
- <메서드 동사. 예: 조회 get/find, 생성 create, 수정 update, 삭제 delete>

### 1.3 트랜잭션 [MUST]

- <예: 트랜잭션은 Application 계층에서만 연다>

### 1.4 응답과 예외 [MUST]

- 응답·오류 형식은 5절 REST를 따른다
- <예: 업무 예외는 ErrorCode를 담은 공통 예외로 던진다>

### 1.5 검증 [MUST]

- <예: 요청 DTO에 Bean Validation, 업무 규칙 검증은 Service>

### 1.6 설정과 환경변수 [MUST]

- 환경변수는 설정 모듈 한 곳에서만 읽고, 시작할 때 검증한다 (harness-psw 5.3)
- <설정 클래스 위치>

### 1.7 보안 [MUST]

- 역할별 권한의 정본은 `docs/req/actors.md`다. 검사 위치: <예: 컨트롤러 진입점>
- 설계: `docs/design/security.md`

### 1.8 API 문서 [SHOULD]

- API 명세는 코드에서 만든다: <예: springdoc(Swagger UI), local 프로필에서만 켠다>
- <예: 컨트롤러와 DTO에 요약·설명 어노테이션을 단다>

### 1.9 하지 않는 것

- NEVER: <예: 컨트롤러에서 Repository를 직접 부르지 않는다>

## 2. DB

### 2.1 이름 [MUST]

- 테이블: <예: 복수형 snake_case>
- 컬럼: <예: snake_case, FK는 <테이블 단수>_id>

### 2.2 표준 컬럼과 삭제 [MUST]

- 감사 컬럼: <예: created_at, created_by, updated_at, updated_by>
- 삭제는 소프트 삭제가 기본이다: <예: deleted_at, deleted_by> (harness-psw 4.7)
- 행위자 개념이 없는 테이블(로그, 토큰 등)은 시각 컬럼만 둔다

| 하드 삭제 테이블 | 이유 |
|---|---|

### 2.3 타입 [MUST]

- <예: 금액 decimal(15,0), 시각 datetime(6), 상태 varchar(30)>
- 상태 컬럼의 값은 도메인 `_policy.md` 상태 전이 절이 정본이다

### 2.4 인덱스와 제약 [SHOULD]

- <예: FK마다 인덱스, 유니크는 이름에 uk_ 접두사>

### 2.5 마이그레이션 [MUST]

- 위치: `docs/design/architecture.md` 백엔드 절
- 이미 적용된 마이그레이션 파일은 고치지 않는다. 바꿀 것은 새 파일로 추가한다 (harness-psw 9.3)
- <파일 이름 규칙. 예: V<번호>__<설명>.sql>

## 3. 프론트

### 3.1 디렉터리 [MUST]

- <예: app/(라우트), components/ui/(키트 컴포넌트), components/(앱 컴포넌트), lib/>
- 공유 파일(테마, UI 컴포넌트 코드, 셸)은 `docs/design/architecture.md` UI 절

### 3.2 컴포넌트 [MUST]

- 공통 컴포넌트 목록: `docs/design/ui/components.md`. 새 컴포넌트는 목록에 먼저 추가한다
- 컴포넌트 코드의 스타일을 직접 바꾸지 않는다. 테마 변수로 바꾼다

### 3.3 API 호출 [MUST]

- <예: API 호출은 lib/api 한 곳에서만. 응답 타입은 백엔드 DTO에서 만든다>

### 3.4 상태 관리 [SHOULD]

- <예: 서버 상태는 쿼리 라이브러리, 화면 상태는 컴포넌트 안>

### 3.5 스타일 [MUST]

- 화면 규칙은 `docs/design/ui/ui-rules.md`
- <예: 색은 테마 변수의 클래스만 쓴다>

### 3.6 라우팅과 환경변수 [MUST]

- 라우트는 `docs/design/ui/ia/`의 화면 목록 경로와 같다
- <예: 브라우저에 노출할 환경변수만 NEXT_PUBLIC_ 접두사>

## 4. 백엔드 ↔ 프론트 연관 [MUST]

<!-- 한쪽을 바꾸면 다른 쪽도 같은 커밋에서 바꿔야 하는 것 -->

- API 경로를 바꾸면 프론트 호출 경로를 같은 커밋에서 바꾼다
- 에러 코드를 추가하면 프론트의 오류 처리 분기를 확인한다
- <예: 요청·응답 타입 생성 절차>

## 5. REST

### 5.1 기본 [MUST]

- 기본 경로: <예: /api/v1>
- 형식: <예: JSON, UTF-8>
- 경로: <예: kebab-case 복수형 명사. 동사를 넣지 않는다>
- 필드: <예: camelCase>

### 5.2 인증 [MUST]

- <헤더와 방식. 예: Authorization: Bearer <token>>

### 5.3 오류 응답 [MUST]

<!-- 이 절의 형식과 기본 표는 백엔드 키트 골격과 같다 (harness-psw 4.7). 한쪽만 바꾸지 않는다 -->

```json
{
  "code": "V001",
  "message": "<사용자에게 보여줄 문장>",
  "timestamp": "<발생 시각, ISO-8601>",
  "path": "<요청 경로>",
  "traceId": "<요청 추적 ID. 서버 로그와 같은 값>",
  "errors": [{ "field": "<필드>", "message": "<사유>" }]
}
```

- `errors`는 입력 검증 실패(V001)일 때만 넣는다
- 코드는 접두사 + 세 자리 번호다
  - V: 입력 검증, A: 인증·인가, R: 리소스, B: 업무 규칙, S: 시스템
  - 도메인 오류는 해당 접두사의 다음 번호를 쓴다. 번호는 다시 쓰지 않는다
- 에러 코드 목록의 정본은 백엔드 코드의 에러 코드 정의다. 아래는 골격이 처음 가진 기본 코드다

| HTTP | 코드 | 의미 |
|---|---|---|
| 400 | V001 | 입력 검증 실패 |
| 405 | V002 | 지원하지 않는 요청 방식 |
| 415 | V003 | 지원하지 않는 요청 형식 |
| 401 | A001 | 인증 필요 (토큰 없음 또는 무효) |
| 401 | A002 | 액세스 토큰 만료 |
| 401 | A003 | 리프레시 토큰 무효 또는 만료 |
| 401 | A004 | 리프레시 토큰 재사용 감지 (해당 사용자 토큰 전부 폐기) |
| 403 | A005 | 권한 없음 |
| 404 | R001 | 대상 없음 |
| 409 | R002 | 이미 존재함 |
| 409 | B001 | 현재 상태에서 할 수 없는 요청 |
| 500 | S001 | 서버 오류 |

### 5.4 페이징 [MUST]

- <예: page, size 파라미터, 응답에 total>

### 5.5 버전 [SHOULD]

- <예: 경로에 버전. 호환되지 않는 변경은 새 버전>

### 5.6 하지 않는 것

- NEVER: <예: 성공 응답에 HTTP 200과 오류 코드를 함께 담지 않는다>
