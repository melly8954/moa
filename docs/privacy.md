# 개인정보 파기 규칙

moa가 정한 개인정보 보관 기간과 파기 규칙이다. 개인정보를 저장하는 기능의 스펙과 코드는 이 문서를 따른다.
사용자에게 공개하는 개인정보처리방침은 이 문서의 보관 기간과 맞춘다.

## 근거

| 조문 | 내용 |
|---|---|
| 개인정보 보호법 제21조 | 보유기간이 지나거나 목적을 이루면 지체 없이 파기한다. 복구·재생되지 않게 한다. 다른 법령으로 보존하면 분리해서 저장한다 |
| 같은 법 시행령 제16조 제1항 | 전자 파일은 복원이 불가능한 방법으로 영구 삭제한다. 기술적 특성으로 영구 삭제가 현저히 곤란하면 익명정보(법 제58조의2)로 처리한다 |
| 표준 개인정보 보호지침 제10조 | 정당한 사유가 없으면 불필요하게 된 때부터 5일 안에 파기한다. 파기 사항을 기록·관리한다. 개인정보 보호책임자가 파기 결과를 확인한다 |
| 같은 지침 제11조 | 법령으로 보존하는 개인정보는 분리해서 저장하고, 처리방침으로 알린다 |
| 통신비밀보호법 시행령 제41조 제2항 | 로그기록자료·접속지 추적자료(법 제2조 제11호 마목·사목)는 3개월 이상 보관한다 |

## 원칙

- 보관 기간이 끝나거나 목적을 이룬 개인정보는 5일 안에 파기한다
- 소프트 삭제(`deleted_at`)는 파기가 아니다. 개인정보가 든 행을 소프트 삭제하는 기능은 유예 기간이 끝나면 아래 "탈퇴 회원 파기"처럼 지운다
- 다른 법령이나 이 문서의 보관 기간 표 때문에 남기는 개인정보는 그 목적 말고는 쓰지 않는다
- 개인정보를 담는 테이블이나 열을 새로 만드는 스펙은 아래 "보관 기간 표"에 한 줄을 더한다. 보관 기간이 정해지지 않으면 `[NEEDS CLARIFICATION]`으로 묻는다

## 파기 방법

| 대상 | 방법 |
|---|---|
| DB 행 | `DELETE`로 지운다 |
| DB 행의 개인정보 열 | 행을 남겨야 하면 개인정보 열의 값을 지운다. NULL로 두거나, `NOT NULL`·유니크 열이면 개인정보가 아닌 고정값(`withdrawn_<id>` 등)으로 덮는다 |
| 파일 (업로드 이미지 등) | 저장소의 파일과 메타 행을 함께 지운다 |
| 로그 파일 | 순환 설정(`logging.logback.rollingpolicy`)대로 지운다. 로그에 비밀번호, 토큰, 이메일 원문을 남기지 않는다 |
| 백업 | 백업 보관 기간이 끝나면 함께 지운다. 백업을 두면 보관 기간을 아래 표에 적는다. 백업을 복원하면 그 사이에 파기했어야 할 데이터를 다시 파기한다 |

- 해시로 바꾸는 것은 파기가 아니다. 원래 값으로 같은 해시를 다시 만들 수 있으면 아직 개인정보(가명정보)다

## 실행

- 기간 파기는 `@Scheduled` 정리기가 매일 새벽에 한다. 여러 서버에서 같이 돌아도 결과가 같아야 한다
- 보관 기간은 설정값(`app.<기능>.retention-days` 등)으로 두고, 기본값을 아래 표와 맞춘다
- 정리기는 지운 건수를 로그에 남긴다. 지운 내용(개인정보)은 남기지 않는다

## 탈퇴 회원 파기

탈퇴 유예 기간(30일)이 끝나면 한 번의 처리로 아래를 함께 한다.

- 기준: 다른 회원의 데이터가 가리키는 행은 남기고 개인정보 열만 지운다. 그 회원 혼자 쓰는 행은 지운다
- 회원 행(`tb_user`): 남기고 개인정보 열(아이디, 비밀번호, 이름 등)을 지운다. 글·파티·메시지와 감사 열(`created_by`)이 이 행을 가리키기 때문이다(외래 키를 걸지 않아 행을 지우면 주인 없는 ID가 남는다, `docs/db.md`). 상태는 탈퇴로 둔다
- 그 회원 혼자 쓰는 행: 지운다. 프로필, 소셜 계정 연결, 약관 동의 기록, 푸시 구독, 리프레시 토큰, 알림, 공지 확인이 여기에 든다
- 다른 회원과 엮인 행: 남긴다. 글, 댓글, 파티, 메시지가 여기에 든다. 회원 행의 개인정보 열을 지우면 작성자는 저절로 "탈퇴한 회원"이 된다
- 남은 회원 ID가 어떤 개인정보와도 이어지지 않아야 파기가 끝난 것이다
- 보관 기간이 따로 있는 것(접속 이력, 재가입 제한 기록, 1:1 문의)은 이 처리에서 지우지 않고 각자의 기간이 끝날 때 지운다
- 본문 안에 회원이 직접 쓴 개인정보는 이 처리로 지워지지 않는다. 약관·처리방침에 "탈퇴해도 게시물은 남는다"를 알리고, 탈퇴 전에 직접 지우도록 안내한다

## 보관 기간 표

| 정보 | 테이블 | 기간 | 끝나면 | 상태 |
|---|---|---|---|---|
| 접속 이력 (입력한 아이디, IP, 브라우저·기기) | `tb_login_history` | 365일 | 행 삭제 | 구현됨 (`LoginHistoryCleaner`) |
| 알림 | `tb_notification` | 90일 | 행 삭제 | 구현됨 (`NotificationCleaner`) |
| 리프레시 토큰 | `tb_refresh_token` | 만료 뒤 1일 | 행 삭제 | 구현됨 (`RefreshTokenCleaner`) |
| 글에 쓰이지 않은 업로드 이미지 | `tb_rich_text_image` | 24시간 | 파일과 행 삭제 | 구현됨 (`RichTextImageCleaner`) |
| 푸시 구독 | `tb_push_subscription` | 해지할 때, 푸시 서버가 404·410을 줄 때, 탈퇴가 끝날 때 | 행 삭제 | 해지·404·410은 구현됨. 탈퇴는 회원 탈퇴 스펙 |
| 회원 정보 (아이디, 비밀번호 해시, 이름) | `tb_user` | 탈퇴 뒤 30일 | 개인정보 열 삭제 | 회원 탈퇴 스펙 |
| 프로필, 소셜 계정 연결, 약관 동의 기록 | `009`·`010`이 만든다 | 탈퇴 뒤 30일 | 행 삭제 | 회원 탈퇴 스펙 |
| 게임 정보 (게임·랭크·포지션 코드, 게임 아이디) | `tb_user_game_profile` (`009-mypage`) | 회원이 지울 때, 탈퇴 뒤 30일 | 행 삭제 | 지우기는 `009-mypage` FR-010. 탈퇴는 회원 탈퇴 스펙 |
| 플레이 가능 시간대 | `tb_user_profile_play_time` (`009-mypage`) | 회원이 바꿀 때(보낸 목록으로 바꿈), 탈퇴 뒤 30일 | 행 삭제 | 바꾸기는 `009-mypage` FR-012. 탈퇴는 회원 탈퇴 스펙 |
| 공지 확인 | `tb_notice_read` | 탈퇴 뒤 30일 | 행 삭제 | 회원 탈퇴 스펙 |
| 재가입 제한 기록 (소셜 계정 식별자 해시) | `010`이 만든다 | 재가입 가능 일시까지. 영구 정지면 계속 | 행 삭제 | `010` FR-015 |
| 1:1 문의 (제목, 내용, 첨부 이미지, 답변) | `017-customer-center`가 만든다 | 회원이 지울 때(답변 대기만), 탈퇴한 날부터 1년. 탈퇴 뒤에는 다툼 대응 말고는 쓰지 않는다 | 행과 첨부 파일 삭제 | 회원 삭제는 `017` FR-009. 탈퇴 뒤 1년은 `017` FR-017 (회원 탈퇴 스펙 뒤) |
| 글, 댓글, 파티, 메시지 | 각 기능 | 탈퇴해도 남긴다 | 회원 행의 개인정보 열 삭제로 작성자가 "탈퇴한 회원"이 된다 | 각 기능 스펙 |
| 만 14세 미만으로 확인된 계정 | `tb_user` 등 | 확인한 때 | 탈퇴 회원 파기와 같다 (유예 없음) | 가입은 막는다 |

## 파기 이력

- 남기는 것: 일시, 대상 종류, 건수, 방법(행 삭제, 개인정보 열 삭제), 처리자(정리기 또는 사람)
- 남기지 않는 것: 지운 회원의 아이디, 이름, 이메일 등 개인정보. 개별 파기(탈퇴 완료 등)에는 내부 회원 ID를 남겨도 된다. 개인정보 열을 지운 뒤의 회원 ID는 어떤 개인정보와도 이어지지 않는다
- 보관 기간: 1년. 기간이 지나면 기록 없이 지운다. 파기 이력에는 개인정보가 없기 때문이다
- 로그 파일은 30일이 지나면 지워지므로(`logging.logback.rollingpolicy.max-history: 30`) 파기 이력은 로그 파일과 따로 남긴다. `specs/013-purge-log`가 정리기의 파기 이력을 `tb_purge_log`에 남긴다. 새 정리를 붙이는 기능은 그 스펙의 이벤트(`PersonalDataPurgedEvent`)를 낸다
- 개인정보 보호책임자는 관리 메뉴 "파기 이력" 화면에서 파기 결과를 확인한다
