# Feature Specification: 기본 회원가입·로그인 (basic-signup)

**Feature Branch**: `feat/019-basic-signup`

**Created**: 2026-11-28

**Status**: Draft

**Input**: User description: "기본 회원가입·로그인(아이디·비밀번호, 이메일 인증). 지금 관리자가 쓰는 아이디·비밀번호 로그인 폼을 일반 회원도 쓴다. 이메일은 따로 받고 가입 인증과 비밀번호 재설정에만 쓴다. 이메일은 중복 불가(010과 같은 정규화)이고 소셜 계정의 이메일과도 양방향으로 겹치지 않게 한다. 이메일 인증은 6자리 코드, 만료·재발송 제한·시도 제한, 인증 전에는 계정을 만들지 않는다. 메일은 Gmail SMTP, 로컬·테스트는 가짜 발송, 설정은 .env.<프로필>, 메일 로그에 이메일 원문을 남기지 않는다. 비밀번호 재설정은 이메일 코드 방식이고 계정 존재 여부가 새지 않는다. 로그인 실패 5번이면 15분 잠금, 시간이 지나면 자동 해제. 가입 단계는 010의 닉네임·태그와 약관 동의 기록을 다시 쓴다. 018 파기 때 이메일도 지우고 유예 중 같은 아이디·이메일 가입을 막는다. privacy.md에 보관 기간 줄을 더한다."

**출처**: moa. 메일 발송도 moa가 만든다(FR-019). 담당: jeonggi4007

**배경** (기존 문서에서 따름):

- 지금 가입 경로는 소셜 가입(`010-social-login`) 하나다. 010 배경은 "이 기능이 moa의 첫 회원 가입 경로다"라고 적었고, 아이디·비밀번호 로그인 폼은 "그대로 둔다"(010 FR-001)고 했다. "소셜만" 결정은 어느 문서에도 없다 (2026-11-28 확인)
- `002-admin-users` 가정 "회원 가입·로그인 방식과 회원 정보 모델은 사용자 쪽 기능이 정한다"의 사용자 쪽 기능에 이 스펙도 더해진다
- 010 가정은 "회원에 이메일이 생기면 그것도 비교한다"고 이미 적었다. 이 스펙이 회원 이메일을 만든다
- 비밀번호 로그인은 지금도 역할을 가리지 않는다. 비밀번호가 있는 계정이면 회원(`USER`)도 로그인한다. 소셜 회원은 비밀번호가 없어 로그인되지 않는다 (010 FR-010)
- 지금 계정 잠금은 관리자가 거는 잠금뿐이고, 로그인 실패 횟수로 잠그는 규칙은 없다 (2026-11-28 dev 확인)
- 탈퇴·복구·파기는 `018-member-withdrawal`이 정한다. 비밀번호 회원의 탈퇴·복구는 이미 된다(018 US2-AC2·AC3)
- 개인정보 보관 기간과 파기 방법은 `docs/privacy.md`가 정본이다
- 관리자·운영자 계정(시스템 역할 `ADMIN`)은 회원 활동을 하지 않는다 (`specs/README.md` 맞춰야 할 경계, `009-mypage` FR-016)

**용어**:

- **비밀번호 회원**: 아이디와 비밀번호로 로그인하는 회원. 이 스펙으로 가입한 회원과, 시드·관리자가 만든 기존 회원이다
- **회원 이메일**: 이 스펙으로 가입한 회원이 인증한 이메일. 가입 인증과 비밀번호 재설정에만 쓴다. 소셜 계정 연결에 저장된 이메일(010)과는 다른 값이다
- **인증 코드**: 메일로 보내는 6자리 숫자. 쓰임은 가입 인증과 비밀번호 재설정 두 가지다
- **임시 잠금**: 로그인 실패가 이어져 정해진 시간 동안 비밀번호 로그인을 막는 것. 관리자가 거는 잠금(002)과 다르다

## Clarifications

### Session 2026-11-28 (사용자 결정, 요청으로 받음)

- Q: 가입·로그인은 무엇으로 하는가? → A: 아이디 + 비밀번호. 지금 로그인 화면의 아이디·비밀번호 폼을 회원도 쓴다. 이메일은 따로 받고 가입 인증과 비밀번호 재설정에만 쓴다 (FR-001, FR-002)
- Q: 이메일 중복은? → A: 막는다. 010과 같은 정규화(앞뒤 공백 제거, 소문자)로 비교하고, 소셜 계정의 이메일과도 양방향으로 확인한다 (FR-005, 010 FR-014·가정)
- Q: 이메일 인증은 어떻게 하는가? → A: 6자리 코드 입력. 만료 시간, 재발송 제한, 시도 제한을 둔다. 인증을 마치기 전에는 계정을 만들지 않는다 (FR-006~FR-008)
- Q: 메일은 무엇으로 보내는가? → A: Gmail SMTP. 로컬·테스트는 가짜 발송(실제로 보내지 않음). 설정값은 `.env.<프로필>`로 받는다. 메일 로그에 이메일 원문을 남기지 않는다 (FR-018~FR-020)
- Q: 비밀번호를 잊으면? → A: 이메일 코드로 재설정한다. 응답으로 계정이 있는지 알 수 없어야 한다 (FR-012~FR-014)
- Q: 로그인 실패 잠금은? → A: 5번 틀리면 15분 잠금, 시간이 지나면 저절로 풀린다 (FR-015~FR-017)
- Q: 관리자·운영자 계정에도 임시 잠금을 거는가? → A: 건다. 회원과 같은 규칙(5번, 15분)이다. 관리 계정이 비밀번호를 맞히는 공격의 가장 값진 대상이고, 15분 뒤 저절로 풀려 갇히는 위험이 작다 (2026-11-28 사용자 결정, 처음 권장안 A, FR-015)
- Q: psw-dev-kit의 메일 헬퍼를 쓰는가? → A: moa가 직접 만든다(Gmail SMTP + 가짜 발송). 키트에 메일 헬퍼가 있는지는 팀에 물었다 (2026-11-28 사용자 결정, FR-019, 가정)
- Q: 가입 첫 화면에서 이메일이 이미 가입됐는지 알려 주는가? → A: 알려 주지 않는다. 어떤 이메일이든 똑같이 "코드를 보냈다"로 응답하고, 메일함의 주인만 알 수 있게 한다. "이미 가입된 이메일"은 코드를 맞힌 뒤에만 알린다. 010 소셜 가입은 제공자가 이메일 주인을 확인한 뒤라 그 자리에서 알려도 되지만, 이메일 가입은 누구나 남의 이메일을 넣을 수 있어 다르다 (2026-11-28 사용자 결정, FR-005)
- Q: 이미 쓰는 이메일로 가입 코드를 요청받으면 무엇을 보내는가? → A: 가입 코드 대신 "이미 가입돼 있다, 찾기나 소셜 로그인으로" 안내 메일을 보낸다. 다른 안(가입 코드를 보내고 맞힌 뒤 알림)은 주인이 코드를 넣고서야 알게 되어 고르지 않았다 (2026-11-28 사용자 결정, 권장안 A, FR-005, US5-AC6)
- Q: 가입 때 닉네임과 약관은? → A: 010의 닉네임·태그(`009-mypage` FR-003)와 약관 동의 기록(010 FR-013)을 그대로 다시 쓴다 (FR-009)
- Q: 탈퇴와는? → A: 파기 때 이메일도 지우고, 유예 중에는 같은 아이디·이메일로 가입하지 못한다 (FR-022, FR-023)

### 이 스펙에서 정한 값 (잠정, 2026-11-28)

- 가입 순서는 "이메일 인증 → 계정 정보" 두 단계다. 인증 전에 계정을 만들지 않으려면 이메일을 먼저 확인해야 해서다 (FR-006)
- 인증 코드: 10분 만료, 재발송은 60초 간격·같은 이메일에 1시간 5번까지, 한 코드에 5번 틀리면 그 코드는 못 쓴다 (FR-007, FR-008)
- 인증을 마친 뒤 계정 정보를 넣을 수 있는 시간은 30분이다 (FR-006)
- 비밀번호 재설정은 이메일만 넣는다. 코드를 맞히면 그 이메일의 아이디를 보이고 새 비밀번호를 받는다. 아이디를 잊은 사람도 같은 길로 찾는다 (FR-013)
- 실패 횟수는 입력한 아이디마다 센다. 없는 아이디도 같은 규칙으로 세어, 잠금 안내가 계정이 있는지 알려 주지 않는다 (FR-015)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 이메일을 인증하고 아이디·비밀번호로 가입한다 (Priority: P1)

moa에 계정이 없는 사람이 로그인 화면에서 "회원가입"을 누른다. 이메일을 넣고 메일로 받은 6자리 코드를 입력해 인증한다. 이어서 아이디, 비밀번호, 닉네임을 넣고 약관에 동의하면 회원이 만들어지고 로그인된다.

**Why this priority**: 소셜 계정이 없거나 쓰고 싶지 않은 사람도 가입할 수 있게 하는 이 기능의 목적 자체다.

**Independent Test**: 가짜 발송 환경에서 새 이메일로 코드를 받아 인증하고 가입을 마친 뒤, 로그아웃하고 그 아이디·비밀번호로 다시 로그인한다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** 로그인하지 않았다, **When** 로그인 화면을 연다, **Then** 아이디·비밀번호 폼 아래에 "회원가입"과 "아이디·비밀번호 찾기" 링크가 보인다
2. **US1-AC2** **Given** 회원가입 첫 화면이다, **When** 아무도 쓰지 않는 이메일을 넣고 코드 받기를 누른다, **Then** 그 이메일로 6자리 인증 코드 메일이 가고, 화면에 코드 입력 칸과 남은 시간(10분)이 보인다. 아직 회원은 만들어지지 않았다
3. **US1-AC3** **Given** 코드를 받았다, **When** 맞는 코드를 10분 안에 넣는다, **Then** 이메일이 인증되고 계정 정보 화면(아이디, 비밀번호, 비밀번호 확인, 닉네임, 약관 동의)으로 넘어간다. 인증한 이메일이 보이고 바꿀 수 없다
4. **US1-AC4** **Given** 계정 정보 화면이다, **When** 규칙에 맞는 아이디·비밀번호·닉네임을 넣고 필수 약관 둘에 동의해 가입한다, **Then** 시스템 역할 `USER`인 회원이 만들어지고 로그인되며, 닉네임에 태그가 붙고(`닉네임#0421`), 첫 화면(또는 돌아갈 주소)으로 간다 (FR-009, `001-admin-menus` FR-006)
5. **US1-AC5** **Given** US1-AC4로 가입했다, **When** 로그아웃한 뒤 로그인 화면의 아이디·비밀번호 폼으로 로그인한다, **Then** 그 회원으로 로그인된다
6. **US1-AC6** **Given** US1-AC4로 가입했다, **When** 그 회원의 약관 동의 기록과 회원 이메일을 본다, **Then** 이용약관·개인정보 수집·이용 각각의 동의 시각과 버전이 남아 있고, 회원 이메일은 정규화한 값(공백 제거, 소문자)이다 (FR-005, FR-009)
7. **US1-AC7** **Given** 계정 정보 화면이다, **When** 이미 쓰는 아이디(대소문자만 다른 것 포함)를 넣는다, **Then** 가입되지 않고 "이미 쓰는 아이디" 안내가 보인다
8. **US1-AC8** **Given** 계정 정보 화면이다, **When** 아이디·비밀번호 규칙(FR-003·FR-004)에 맞지 않는 값이나 서로 다른 비밀번호 확인을 넣는다, **Then** 가입되지 않고 어느 칸이 왜 틀렸는지 보인다
9. **US1-AC9** **Given** 계정 정보 화면이다, **When** 필수 약관 중 하나라도 동의하지 않는다, **Then** 가입할 수 없고 회원이 만들어지지 않는다 (010 US1-AC7과 같다)
10. **US1-AC10** **Given** 인증을 마치고 30분이 지났다, **When** 계정 정보 화면에서 가입한다, **Then** 가입되지 않고 "인증 시간이 지났다, 이메일 인증부터 다시" 안내와 함께 첫 화면으로 돌아간다
11. **US1-AC11** **Given** 이메일 인증을 하지 않았다, **When** 화면을 거치지 않고 계정 만들기 요청을 바로 보낸다, **Then** 거부되고 회원이 만들어지지 않는다 (FR-006)
12. **US1-AC12** **Given** 로그인한 사람(회원이든 관리자든)이다, **When** 회원가입 화면 주소를 연다, **Then** 가입 화면 대신 로그인한 뒤 첫 화면으로 간다

### User Story 2 - 인증 코드의 만료·재발송·시도 제한 (Priority: P1)

코드를 받은 사람이 시간이 지나 다시 받거나 잘못 넣는다. moa는 코드를 오래 쓰지 못하게 하고, 메일을 너무 자주 보내지 않으며, 코드를 넣어 맞히는 공격을 막는다.

**Why this priority**: 제한이 없으면 코드를 맞히는 공격과 메일 폭탄이 바로 가능하고, Gmail 발송 한도도 금세 찬다. 가입(US1)과 재설정(US3)이 이 규칙 위에 선다.

**Independent Test**: 가짜 발송 환경에서 코드를 받아 시간을 넘기고, 짧은 간격으로 다시 받고, 틀린 코드를 여러 번 넣어 각 제한이 걸리는지 본다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 코드를 받은 지 10분이 지났다, **When** 그 코드를 넣는다, **Then** 인증되지 않고 "코드가 만료되었다" 안내와 다시 받기 단추가 보인다
2. **US2-AC2** **Given** 코드를 받은 지 60초가 지나지 않았다, **When** 다시 받기를 누른다, **Then** 메일이 가지 않고 몇 초 뒤에 다시 받을 수 있는지 보인다. 다시 받기 단추는 그때까지 꺼져 있다
3. **US2-AC3** **Given** 같은 이메일로 1시간 안에 코드를 5번 받았다, **When** 여섯째로 받으려 한다, **Then** 메일이 가지 않고 "잠시 뒤 다시" 안내가 보인다. 가입과 재설정 코드를 합쳐 센다
4. **US2-AC4** **Given** 코드를 다시 받았다, **When** 앞서 받은 코드를 넣는다, **Then** 인증되지 않는다. 마지막에 받은 코드만 쓸 수 있다
5. **US2-AC5** **Given** 코드를 받았다, **When** 틀린 코드를 5번 넣는다, **Then** 다섯째부터 그 코드는 맞는 값을 넣어도 쓸 수 없고 "새 코드를 받아 달라" 안내가 보인다
6. **US2-AC6** **Given** 맞는 코드로 한 번 인증했다, **When** 같은 코드를 다시 넣는다, **Then** 다시 쓰이지 않는다 (한 번 쓴 코드는 버린다)
7. **US2-AC7** **Given** 인증 코드 메일을 받았다, **When** 메일을 연다, **Then** 6자리 코드, 만료 시간(10분), 쓰임(가입 또는 비밀번호 재설정), "요청하지 않았다면 무시하라"는 안내가 보인다

### User Story 3 - 이메일 코드로 비밀번호를 재설정한다 (Priority: P1)

비밀번호를 잊은 회원이 로그인 화면에서 "아이디·비밀번호 찾기"를 누르고 가입 때 인증한 이메일을 넣는다. 메일로 받은 코드를 넣으면 자기 아이디가 보이고 새 비밀번호를 정할 수 있다.

**Why this priority**: 아이디·비밀번호 회원은 비밀번호를 잊으면 로그인할 길이 없다. 관리자 초기화(002)에만 기대면 회원마다 문의가 생긴다.

**Independent Test**: 가입한 회원의 이메일로 재설정을 요청해 코드를 받고 새 비밀번호로 로그인한다. 가입되지 않은 이메일로 요청해 화면 응답이 같은지 본다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 회원 이메일이 있는 비밀번호 회원이다, **When** 찾기 화면에서 그 이메일을 넣고 코드 받기를 누른다, **Then** "입력한 이메일이 가입된 이메일이면 코드를 보냈다"는 안내와 코드 입력 칸이 보이고, 그 이메일로 재설정 코드 메일이 간다
2. **US3-AC2** **Given** 어느 회원의 이메일도 아니거나, 소셜 계정 연결에만 있는 이메일이다, **When** 찾기 화면에서 그 이메일로 코드 받기를 누른다, **Then** US3-AC1과 똑같은 안내·화면·응답이 보이고 메일은 가지 않는다 (FR-014)
3. **US3-AC3** **Given** 재설정 코드를 받았다, **When** 맞는 코드를 넣는다, **Then** 그 회원의 아이디가 보이고 새 비밀번호·비밀번호 확인 칸이 보인다
4. **US3-AC4** **Given** US3-AC3 화면이다, **When** 규칙에 맞는 새 비밀번호를 넣어 바꾼다, **Then** 비밀번호가 바뀌고, 그 회원의 다른 기기 로그인이 모두 끊기며, 로그인 화면에서 "비밀번호를 바꿨다" 안내와 함께 새 비밀번호로 로그인할 수 있다. 옛 비밀번호로는 로그인되지 않는다
5. **US3-AC5** **Given** 회원이 임시 잠금 중이다, **When** 재설정으로 비밀번호를 바꾼다, **Then** 임시 잠금과 실패 횟수가 풀려 바로 새 비밀번호로 로그인할 수 있다 (FR-016)
6. **US3-AC6** **Given** 재설정 코드에도, **When** 만료·재발송·시도 제한(US2)에 걸린다, **Then** 가입 코드와 같은 규칙으로 막힌다
7. **US3-AC7** **Given** 코드를 맞힌 뒤 30분이 지났다, **When** 새 비밀번호를 저장한다, **Then** 바뀌지 않고 처음부터 다시 하라는 안내가 보인다
8. **US3-AC8** **Given** 관리자가 잠근 회원이거나 탈퇴 유예 중인 회원의 이메일이다, **When** 재설정을 요청한다, **Then** 화면 응답은 US3-AC1과 같고 메일은 가지 않는다. 관리자 잠금은 재설정으로 풀리지 않는다 (FR-014)

### User Story 4 - 로그인 실패가 이어지면 잠시 잠긴다 (Priority: P1)

누군가 아이디·비밀번호 폼에서 같은 아이디로 비밀번호를 계속 틀리면 그 아이디의 비밀번호 로그인이 15분 동안 막힌다. 15분이 지나면 저절로 풀린다.

**Why this priority**: 누구나 가입할 수 있게 되면 비밀번호를 맞히는 공격이 바로 생긴다. 공개 가입과 함께 들어가야 한다.

**Independent Test**: 한 아이디로 틀린 비밀번호를 5번 넣고, 맞는 비밀번호도 막히는지, 15분 뒤 풀리는지 본다. 없는 아이디로도 같은 안내가 나오는지 본다.

**Acceptance Scenarios**:

1. **US4-AC1** **Given** 비밀번호 회원이다, **When** 비밀번호를 연속 4번 틀린다, **Then** 매번 지금과 같은 실패 안내("아이디 또는 비밀번호가 올바르지 않습니다")가 보인다
2. **US4-AC2** **Given** 연속 4번 틀렸다, **When** 다섯째도 틀린다, **Then** "로그인을 5번 실패해 15분 동안 로그인할 수 없다. 비밀번호를 잊었다면 찾기를 이용하라" 안내가 보인다
3. **US4-AC3** **Given** 임시 잠금 중이다, **When** 맞는 비밀번호로 로그인한다, **Then** 로그인되지 않고 US4-AC2와 같은 안내와 풀리는 시각이 보인다
4. **US4-AC4** **Given** 임시 잠금이 걸린 지 15분이 지났다, **When** 맞는 비밀번호로 로그인한다, **Then** 로그인되고 실패 횟수는 0부터 다시 센다
5. **US4-AC5** **Given** 비밀번호를 3번 틀렸다, **When** 맞는 비밀번호로 로그인한다, **Then** 로그인되고 실패 횟수가 0이 된다
6. **US4-AC6** **Given** 없는 아이디다, **When** 그 아이디로 5번 로그인을 시도한다, **Then** 있는 아이디와 똑같이 다섯째에 임시 잠금 안내가 보인다. 응답으로 아이디가 있는지 알 수 없다 (FR-015)
7. **US4-AC7** **Given** 비밀번호 회원이 임시 잠금 중이고 소셜 계정이 연결되어 있다, **When** 그 소셜 계정으로 로그인한다, **Then** 로그인된다. 임시 잠금은 비밀번호 로그인만 막는다
8. **US4-AC8** **Given** 임시 잠금이 걸렸다, **When** 관리자가 접속 이력을 연다, **Then** 다섯째 실패와 잠금 중의 시도가 실패로 보이고, 잠금 중 시도는 "임시 잠금" 사유로 구별된다 (FR-017)
9. **US4-AC9** **Given** 관리자가 사용자 관리에서 그 회원을 본다, **When** 임시 잠금 중이다, **Then** 계정 상태는 "잠김"으로 보이지 않는다. 임시 잠금은 관리자 잠금과 따로이고 관리 화면에서 다루지 않는다 (FR-016)

### User Story 5 - 이메일은 회원과 소셜 계정을 통틀어 하나만 쓴다 (Priority: P2)

한 이메일은 아이디·비밀번호 회원의 회원 이메일과 소셜 계정의 이메일을 통틀어 한 회원만 쓴다. 이메일 가입은 소셜 이메일과, 소셜 가입은 회원 이메일과 겹치는지 본다.

**Why this priority**: 겹치게 두면 같은 사람이 계정을 여러 개 만들고, 재설정 메일이 엉뚱한 계정으로 간다. 다만 가입(US1)이 먼저 있어야 겹칠 일이 생긴다.

**Independent Test**: 소셜 회원의 이메일로 이메일 가입을 시도하고, 이메일 회원의 이메일을 쓰는 소셜 계정으로 가입을 시도한다.

**Acceptance Scenarios**:

1. **US5-AC1** **Given** 다른 회원이 회원 이메일로 쓰는 이메일이다(대소문자·앞뒤 공백만 다른 것 포함), **When** 회원가입 첫 화면에서 그 이메일로 코드 받기를 누른다, **Then** 아무도 쓰지 않는 이메일(US1-AC2)과 똑같은 "코드를 보냈다" 안내·화면·응답이 보인다. 화면으로는 이미 가입된 이메일인지 알 수 없다 (FR-005)
2. **US5-AC2** **Given** 어느 회원의 소셜 계정 연결에 저장된 이메일이다, **When** 회원가입 첫 화면에서 그 이메일로 코드 받기를 누른다, **Then** US5-AC1과 똑같은 응답이다 (FR-005)
3. **US5-AC3** **Given** 이메일 회원의 회원 이메일과 같은 이메일의 소셜 계정이다, **When** 그 소셜 계정으로 처음 로그인한다, **Then** 010 US1-AC9대로 가입이 막히고 "다른 방식으로 가입된 이메일" 안내가 보인다 (010 FR-014가 회원 이메일도 비교, 가정 240줄)
4. **US5-AC4** **Given** 다른 회원의 회원 이메일과 같은 이메일의 소셜 계정이다, **When** 로그인한 회원이 계정 설정에서 그 소셜 계정을 연결한다, **Then** 010 US5-AC8대로 연결되지 않는다. 그 이메일을 쓰는 회원이 연결하려는 본인이면 연결된다
5. **US5-AC5** **Given** 이메일 인증을 마친 뒤 계정 정보를 넣는 사이에 같은 이메일로 다른 사람이 먼저 가입(또는 소셜 가입)했다, **When** 가입을 마치려 한다, **Then** 가입되지 않고 "이미 가입된 이메일"(회원 이메일) 또는 "다른 방식으로 가입된 이메일"(소셜 연결) 안내가 보인다. 이 사람은 코드를 맞혀 메일함 주인임을 보였으므로 알려도 된다. 한 이메일로 회원이 둘 생기지 않는다
6. **US5-AC6** **Given** US5-AC1·AC2의 이메일이다, **When** 그 이메일의 메일함을 본다, **Then** 가입 코드가 아니라 "이 이메일은 이미 가입돼 있다. 아이디·비밀번호를 잊었다면 찾기로, 소셜 계정으로 가입했다면 그 계정으로 로그인하라. 요청하지 않았다면 무시하라" 안내 메일이 와 있다. 코드가 없으므로 그 이메일로는 계정 정보 화면으로 넘어갈 수 없다 (FR-005)

### User Story 6 - 탈퇴와 파기에서 회원 이메일을 다룬다 (Priority: P2)

이메일로 가입한 회원이 탈퇴하면 유예 기간 동안 아이디와 이메일은 그 회원 것으로 남아 다른 사람이 가입에 쓰지 못한다. 파기하면 이메일도 지워지고 다시 쓸 수 있다.

**Why this priority**: 018 규칙을 새 개인정보(이메일)에 넓히는 일이다. 탈퇴는 이미 동작하므로 가입보다 뒤다.

**Independent Test**: 이메일 회원을 탈퇴시키고 유예 중에 같은 아이디·이메일로 가입을 시도한 뒤, 파기를 돌려 이메일이 지워졌는지와 다시 가입할 수 있는지 본다.

**Acceptance Scenarios**:

1. **US6-AC1** **Given** 탈퇴 유예 중인 이메일 회원이 있다, **When** 같은 이메일로 회원가입 코드를 받으려 한다, **Then** 응답은 US5-AC1과 같고 그 이메일로는 가입할 수 없다(US5-AC6과 같은 메일). 그 회원은 유예 기간 안에 복구할 수 있다 (018 US2-AC12·AC13과 같은 규칙)
2. **US6-AC2** **Given** 탈퇴 유예 중인 이메일 회원이 있다, **When** 같은 아이디로 가입하려 한다, **Then** "이미 쓰는 아이디"로 막힌다 (018 US2-AC12)
3. **US6-AC3** **Given** 탈퇴 유예 중인 이메일 회원이다, **When** 비밀번호 재설정을 요청한다, **Then** US3-AC8대로 메일이 가지 않는다. 복구는 로그인 화면의 복구 길(018 US2)로 한다
4. **US6-AC4** **Given** 탈퇴한 지 30일이 지난 이메일 회원이 있다, **When** 정리가 돈다, **Then** 아이디·비밀번호·이름과 함께 회원 이메일도 원래 값이 남지 않게 지워진다 (018 US3-AC1, `docs/privacy.md` "파기 방법")
5. **US6-AC5** **Given** 이메일 회원이 파기되었다, **When** 그 회원이 쓰던 아이디나 이메일로 새로 가입한다, **Then** 막히지 않는다 (018 US3-AC13)
6. **US6-AC6** **Given** 이메일 회원이 가입·재설정·탈퇴·파기를 거쳤다, **When** 그동안의 애플리케이션 로그와 메일 발송 기록을 본다, **Then** 이메일 원문, 인증 코드, 비밀번호가 없다 (FR-020, `docs/privacy.md`)

### Edge Cases

- 코드 받기 화면에서 다른 이메일로 바꿔 다시 받을 때: 앞 이메일의 코드는 쓰이지 않고, 재발송 간격·횟수는 이메일마다 센다
- 같은 이메일로 두 브라우저에서 코드를 받을 때: 마지막에 받은 코드만 쓰인다 (US2-AC4). 먼저 인증을 마친 쪽만 계정 정보로 넘어간다
- 가입 도중 화면을 떠날 때: 회원도 약관 동의 기록도 만들어지지 않는다. 인증은 30분 뒤 쓸 수 없게 되고, 다시 오면 이메일 인증부터 한다 (010 Edge Cases와 같다)
- 메일 발송이 실패할 때(SMTP 오류, Gmail 한도): 실패한 발송은 재발송 간격·횟수에 세지 않고, 실패 건수를 로그에 남긴다(FR-020). 가입과 재설정 모두, 메일을 보내려 한 경우와 보내지 않는 경우(재설정의 없는 계정)가 응답으로 갈리지 않도록 발송은 응답 뒤에 따로 하고, 화면은 늘 "코드를 보냈다"다. 발송 실패는 회원이 다시 받기로 다시 시도한다 (FR-005, FR-014)
- 메일이 스팸함으로 갈 때: 코드 입력 화면에 "메일이 안 보이면 스팸함을 확인하라"를 늘 보인다
- 다른 사람이 남의 아이디로 일부러 5번 틀려 잠글 때: 15분 뒤 저절로 풀리고, 그 회원은 재설정으로 바로 풀 수 있다(US3-AC5). 소셜 로그인은 막히지 않는다(US4-AC7). 이 공격을 더 막는 일(IP별 제한 등)은 이번 범위가 아니다
- 임시 잠금과 관리자 잠금이 함께 있을 때: 관리자 잠금 안내(지금의 A007)가 먼저 보인다. 임시 잠금이 풀려도 관리자 잠금은 남는다
- 탈퇴 유예 중 비밀번호 회원이 틀린 비밀번호로 로그인할 때: 실패로 세고, 탈퇴하지 않은 회원과 같은 안내만 보인다 (018 US2-AC3). 5번이면 임시 잠금이 걸린다
- 시드·관리자가 만든 기존 비밀번호 회원(회원 이메일 없음)이 비밀번호를 잊을 때: 재설정 메일을 받을 이메일이 없으므로 지금처럼 관리자 초기화(002)로 한다. 이 회원들의 이메일 등록은 이번 범위가 아니다 (가정)
- 관리자가 만든 회원(002)의 아이디가 이 스펙의 아이디 규칙(FR-003)에 맞지 않을 때: 로그인은 지금대로 된다. 규칙은 새 가입에만 건다
- 소셜 회원(비밀번호 없음)이 아이디·비밀번호 찾기를 쓸 때: 회원 이메일이 없으므로 US3-AC2와 같다. 소셜 로그인을 쓰라는 안내는 화면에 늘 보이는 문구로 둔다 ("소셜 계정으로 가입했다면 그 계정으로 로그인하라")
- 대소문자만 다른 아이디로 로그인할 때: 아이디는 소문자로 저장하고 입력도 소문자로 바꿔 찾는다 (FR-003)
- 가입 중 닉네임의 태그가 다 찼을 때: 010·009와 같은 안내(B201)로 다른 닉네임을 넣게 한다

### Functional Requirements

**가입**

- **FR-001**: 로그인하지 않은 사람은 아이디·비밀번호와 인증한 이메일로 회원 가입을 할 수 있어야 한다(MUST). 만든 회원의 시스템 역할은 `USER`다. 로그인 화면에 "회원가입"과 "아이디·비밀번호 찾기" 링크를 둔다. 로그인은 지금 로그인 화면의 아이디·비밀번호 폼 하나를 관리자·운영자와 함께 쓴다 (`010-social-login` FR-001)
- **FR-002**: 회원 이메일은 가입 인증과 비밀번호 재설정에만 써야 한다(MUST). 로그인 아이디로 쓰지 않고, 다른 회원에게 보이지 않으며, 알림·광고 메일에 쓰지 않는다. 관리자 화면에 보일지는 `002-admin-users`가 정한다 (영향 목록)
- **FR-003**: 아이디 규칙 (잠정)
  - 4~20자, 영문 소문자로 시작하고 영문 소문자·숫자·`_`만 쓴다. 대문자로 넣으면 소문자로 바꿔 저장한다(MUST)
  - 이미 있는 아이디와 대소문자를 무시하고 같으면 막는다(MUST). 탈퇴 유예 중인 회원의 아이디도 막는다 (FR-023)
  - 예약 아이디(`admin`, `administrator`, `root`, `system`, `moa`, `operator`, `support`, `test`로 시작하는 것)는 막는다(MUST, 잠정)
  - 관리자가 만드는 계정(002)의 아이디 규칙은 바꾸지 않는다
- **FR-004**: 비밀번호 규칙 (잠정)
  - 8~100자, 영문과 숫자를 각각 하나 이상 넣는다(MUST). 길이는 지금 비밀번호 변경의 8~100자와 같다
  - 아이디와 같은 비밀번호는 막는다(MUST)
  - 가입·재설정 화면은 비밀번호 확인 칸을 두고 두 값이 같아야 한다(MUST)
  - 이 규칙은 이 스펙의 가입과 재설정에 건다. 지금 비밀번호 변경 화면(`/account/password`)의 규칙을 맞출지는 영향 목록에 둔다
- **FR-005**: 회원 이메일은 앞뒤 공백을 없애고 소문자로 바꿔 저장·비교해야 한다(MUST, 010 FR-014와 같은 정규화). 한 이메일은 회원 이메일과 소셜 계정 연결의 이메일을 통틀어 한 회원만 쓴다(MUST)
  - 이메일 가입은 코드 받기 응답으로 이메일이 이미 쓰이는지 알리지 않아야 한다(MUST). 회원 이메일·소셜 연결 이메일·탈퇴 유예 중인 회원 이메일·아무도 쓰지 않는 이메일 모두 같은 "코드를 보냈다" 안내·응답이고, 발송 간격·횟수(FR-008)도 똑같이 센다. 응답 시간 차이로도 드러나지 않게 한다 (US5-AC1·AC2, SC-004)
  - 이미 쓰는 이메일(회원 이메일, 소셜 연결 이메일, 탈퇴 유예 중인 회원 이메일)에는 가입 코드 대신 안내 메일을 보내야 한다(MUST, 2026-11-28 사용자 결정). 문구는 "이 이메일은 이미 가입돼 있다. 아이디·비밀번호를 잊었다면 찾기로, 소셜 계정으로 가입했다면 그 계정으로 로그인하라. 요청하지 않았다면 무시하라"다. 주인은 코드를 넣는 헛걸음 없이 바로 알고, 남이 넣었으면 주인만 안다. 쓸 수 없는 가입 코드를 내주지 않는다 (US5-AC6)
  - 코드를 보낸 뒤 그 이메일을 다른 사람이 먼저 가입에 쓰면, 코드를 맞힌 사람에게만 "이미 가입된 이메일"(회원 이메일) 또는 "다른 방식으로 가입된 이메일"(소셜 연결)을 알리고 계정 정보 화면으로 넘기지 않는다(MUST). 코드를 맞히면 메일함의 주인이기 때문이다. 계정을 만들 때도 한 번 더 찾아 그사이 생긴 중복을 막는다 (US5-AC5)
  - 소셜 가입·연결: `010-social-login` FR-014가 회원 이메일도 비교한다. 010 구현에 더한다 (영향 목록, US5-AC3·AC4)
  - 010 소셜 가입은 그 자리에서 "다른 방식으로 가입된 이메일"을 알린다. 구글·디스코드가 이메일 주인임을 이미 확인했기 때문이다. 이메일 가입은 누구나 남의 이메일을 넣을 수 있어 코드를 맞히기 전에는 알리지 않는다 (2026-11-28 사용자 결정)
- **FR-006**: 이메일 인증을 마치기 전에는 회원을 만들지 않아야 한다(MUST)
  - 가입은 두 단계다: (1) 이메일 입력 → 코드 받기 → 코드 확인, (2) 아이디·비밀번호·닉네임·약관 동의 → 가입
  - (1)을 마치면 그 브라우저에 30분 동안 쓸 수 있는 "인증된 가입" 상태를 준다. (2)는 이 상태가 있어야만 받는다(MUST). 상태는 한 번 가입에 쓰면 버린다
  - 화면을 거치지 않은 요청도 같은 규칙으로 막는다 (US1-AC11)
- **FR-007**: 인증 코드 (MUST)
  - 6자리 숫자이고 무작위로 만든다. 저장할 때는 원래 값을 알 수 없게 바꿔 둔다(해시)
  - 10분 뒤 만료된다. 한 번 맞히면 버린다. 새 코드를 보내면 같은 이메일·쓰임의 앞 코드는 버린다
  - 한 코드에 5번 틀리면 그 코드는 버린다 (US2-AC5)
  - 쓰임(가입, 비밀번호 재설정)을 함께 저장하고, 다른 쓰임에는 통하지 않는다
- **FR-008**: 코드 발송 제한 (MUST)
  - 같은 이메일로는 60초 안에 다시 보내지 않는다
  - 같은 이메일로는 1시간에 5번까지 보낸다. 가입과 재설정을 합쳐 센다
  - 값(만료 10분, 간격 60초, 1시간 5번, 시도 5번, 인증 뒤 30분)은 설정값으로 둔다. 바꾸면 이 스펙을 고친다
- **FR-009**: 가입 단계의 닉네임과 약관은 `010-social-login`의 가입과 같아야 한다(MUST)
  - 닉네임 규칙과 태그는 `009-mypage` FR-003을 따른다(010 가입과 같은 처리). 닉네임이 회원의 표시 이름이다
  - 이용약관·개인정보 수집·이용 필수 동의와 동의 기록(동의 시각, 버전)은 010 FR-013과 같다. 같은 약관 버전을 쓴다. 약관 칸의 모양(전문 상자, 더보기·처리방침 보기 새 탭)은 `012-terms-privacy` FR-005를 따른다
  - 회원 프로필 행은 010 가입처럼 가입 때 만든다 (`009-mypage` research R14)
- **FR-010**: 가입을 마치면 바로 로그인시켜야 한다(MUST). 로그인 유지·로그아웃과 첫 화면은 아이디·비밀번호 로그인과 같다 (`001-admin-menus` FR-006, 010 FR-012)
- **FR-011**: 가입·찾기 화면은 로그인하지 않은 사람만 쓴다(MUST). 로그인한 사람이 열면 첫 화면으로 보낸다 (US1-AC12). 이 화면들은 메뉴로 열지 않으므로 프로그램으로 등록하지 않는다 (`001-admin-menus` FR-008)

**비밀번호 재설정**

- **FR-012**: 회원 이메일이 있는 비밀번호 회원은 이메일 코드로 비밀번호를 재설정할 수 있어야 한다(MUST). 코드 규칙은 FR-007·FR-008과 같다
- **FR-013**: 재설정은 이메일만 받는다(MUST). 코드를 맞히면 그 회원의 아이디를 보이고 새 비밀번호를 받는다. 코드를 맞힌 뒤 30분 안에 바꿔야 한다. 아이디 찾기를 따로 두지 않고 이 길로 찾는다
  - 바꾸면 그 회원의 모든 로그인(리프레시 토큰)을 끊는다(MUST). 지금 비밀번호 변경과 같다
  - 바꾸면 임시 잠금과 실패 횟수를 0으로 한다(MUST, US3-AC5). 관리자 잠금은 풀지 않는다
  - 비밀번호 변경 요구 상태(관리자 초기화의 임시 비밀번호)가 있으면 푼다
- **FR-014**: 재설정 요청의 응답으로 그 이메일의 계정이 있는지 알 수 없어야 한다(MUST)
  - 코드 받기는 이메일이 회원 이메일이든 아니든(소셜 연결에만 있든, 없든, 관리자 잠금·탈퇴 유예·파기된 회원이든) 같은 안내·같은 응답이다. 메일은 정상 비밀번호 회원일 때만 보낸다
  - 코드 확인도 메일을 받지 않은 이메일에 대해 "코드가 맞지 않다"로만 답한다
  - 발송 간격·횟수 제한도 이메일에 계정이 있는지와 상관없이 센다. 응답 시간 차이로 계정 유무가 드러나지 않게 한다 (SC-004)

**로그인 실패 잠금**

- **FR-015**: 아이디·비밀번호 로그인에서 같은 아이디로 비밀번호를 연속 5번 틀리면 그 아이디의 비밀번호 로그인을 15분 동안 막아야 한다(MUST)
  - 실패는 입력한 아이디(정규화한 값)마다 센다. 없는 아이디도 같은 규칙으로 세어, 안내로 아이디가 있는지 알 수 없게 한다 (US4-AC6)
  - 로그인에 성공하면 0으로 한다. 잠금이 풀리면 0부터 센다
  - 잠금 중에는 맞는 비밀번호도 막고 풀리는 시각을 안내한다
  - 15분이 지나면 저절로 풀린다. 사람이 풀 일은 없다
  - 값(5번, 15분)은 설정값으로 둔다
  - 관리자·운영자 계정(`ADMIN`, 최고 관리자 포함)에도 같은 규칙(5번, 15분)을 건다(MUST, 2026-11-28 사용자 결정). 관리 계정은 회원 이메일이 없어 재설정으로 풀 수 없으므로 15분을 기다린다. 키트 로그인 동작을 바꾸는 것이므로 바꾸는 것만 적는다 (원칙 III)
- **FR-016**: 임시 잠금은 관리자 잠금(`002-admin-users`)과 따로여야 한다(MUST). 사용자 관리의 계정 상태와 잠금·해제에 보이거나 섞이지 않는다. 소셜 로그인은 막지 않는다 (US4-AC7). 관리자 잠금이 함께 있으면 관리자 잠금 안내가 먼저다
- **FR-017**: 임시 잠금은 접속 이력(`005-admin-login-history`)에 남아야 한다(MUST)
  - 잠금을 거는 다섯째 실패는 지금과 같은 "비밀번호 틀림" 실패로 남는다
  - 잠금 중 시도는 실패로 남기고 사유를 "임시 잠금"으로 따로 둔다(새 실패 사유 코드). 입력한 아이디·IP·기기는 지금 접속 이력과 같다
  - 잠금 걸림·풀림을 따로 행으로 남기지는 않는다. 풀림은 시간으로 정해지기 때문이다

**메일 발송**

- **FR-018**: 메일은 Gmail SMTP로 보내야 한다(MUST). 보내는 주소·계정·앱 비밀번호 등 설정값은 실행 폴더의 `.env.<프로필>`이나 환경 변수로 받고, 저장소에 넣지 않는다(원칙 VI). 설정이 없는 환경에서는 메일 기능을 켜지 않고, 가입·재설정 화면에 "지금은 이메일 가입을 쓸 수 없다"를 보인다
- **FR-019**: 메일을 보내는 부분은 moa가 만든다(MUST, 2026-11-28 사용자 결정). 키트 메일 헬퍼로 옮기는 일은 가정을 본다
  - 로컬 실행과 자동 테스트는 가짜 발송을 쓴다(MUST). 실제로 보내지 않고, 테스트는 보낸 메일(받는 주소, 코드)을 읽어 확인할 수 있어야 한다. 로컬 실행은 보낸 코드를 개발자가 볼 수 있게 한다(로그가 아닌 곳, FR-020)
- **FR-020**: 메일과 코드에 관한 로그·기록에 이메일 원문, 인증 코드, 비밀번호를 남기지 않아야 한다(MUST, `docs/privacy.md` "파기 방법"의 로그 줄). 발송 성공·실패 건수와 쓰임만 남긴다. 메일 본문을 따로 저장하지 않는다

**탈퇴·개인정보**

- **FR-021**: 이 스펙이 만드는 개인정보는 `docs/privacy.md` 보관 기간 표를 따라야 한다(MUST). 표에 줄을 더한다
  - 회원 이메일: 탈퇴 뒤 30일, 개인정보 열 삭제 (회원 정보와 같다)
  - 인증 코드(가입·재설정. 이메일, 코드 해시, 쓰임, 시도 횟수, 시각): 쓰거나 만료된 뒤 1일, 행 삭제
  - 로그인 실패 횟수·임시 잠금(입력한 아이디, 횟수, 시각): 마지막 실패 뒤 1일, 행 삭제 (성공하면 바로 지운다)
  - 정리는 매일 새벽 정리기가 한다 (`docs/privacy.md` "실행")
- **FR-022**: 탈퇴 회원 파기(`018-member-withdrawal` FR-008·US3)는 회원 이메일도 원래 값이 남지 않게 지워야 한다(MUST). 방법은 `docs/privacy.md` "파기 방법"의 개인정보 열 삭제다. 그 회원에게 남은 인증 코드도 함께 지운다. 018 구현에 더한다 (영향 목록)
- **FR-023**: 탈퇴 유예 중인 회원의 아이디와 회원 이메일로는 다른 사람이 가입할 수 없어야 한다(MUST, US6-AC1·AC2). 파기된 뒤에는 쓸 수 있다 (US6-AC5). 이메일 회원의 재가입 제한 기록은 두지 않는다 (`018-member-withdrawal` FR-015와 같다)
- **FR-024**: 관리자·운영자 계정은 이 가입으로 만들 수 없다(MUST). 가입으로 만든 회원은 늘 `USER`다. 관리자가 회원을 관리자 계정으로 바꾸는 일은 002 규칙을 따른다

### Key Entities

- **회원**: moa의 계정(키트 `tb_user`). 이 스펙의 회원은 아이디(소문자), 비밀번호 해시, 이름(닉네임)을 가진다. 역할은 `USER`
- **회원 이메일**: 회원 하나에 하나. 정규화한 이메일, 인증한 시각. 한 이메일은 한 회원만 (소셜 계정 연결의 이메일과도 겹치지 않음)
- **인증 코드**: 이메일(정규화), 쓰임(가입·재설정), 코드 해시, 만료 시각, 틀린 횟수, 쓴 시각. 같은 이메일·쓰임에 살아 있는 코드는 하나
- **인증된 가입 상태 / 재설정 상태**: 코드를 맞힌 뒤 30분 동안 다음 단계를 허락하는 표. 한 번 쓰면 버린다
- **로그인 실패 기록**: 입력한 아이디(정규화), 연속 실패 횟수, 마지막 실패 시각, 잠금이 풀리는 시각
- **약관 동의 기록**, **회원 프로필(닉네임·태그)**: 010·009가 만든 것을 그대로 쓴다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 처음 온 사람이 로그인 화면에서 시작해 이메일 인증과 계정 정보 입력을 마치고 로그인된 첫 화면을 보기까지 3분 안에 끝낼 수 있다 (메일이 1분 안에 온다고 할 때)
- **SC-002**: 이메일 인증을 마치지 않은 가입 시도는 하나도 회원을 만들지 않는다. 한 이메일로 회원이 둘 생기는 일이 없다 (회원 이메일과 소셜 이메일을 통틀어)
- **SC-003**: 한 아이디에 15분 동안 시도할 수 있는 비밀번호는 5개를 넘지 않는다. 6자리 코드 하나는 5번까지만 맞혀 볼 수 있다
- **SC-004**: 가입 코드 받기, 비밀번호 재설정, 로그인 잠금의 화면·응답만으로는 어떤 이메일이나 아이디의 계정이 있는지 알 수 없다 (있는 것과 없는 것의 응답이 같다). 이메일이 이미 가입됐는지는 그 메일함의 주인만 안다
- **SC-005**: 한 이메일로 한 시간에 가는 인증 메일은 5통을 넘지 않는다
- **SC-006**: 로그와 메일 발송 기록 어디에도 이메일 원문, 인증 코드, 비밀번호가 남지 않는다
- **SC-007**: 비밀번호를 잊은 회원은 관리자에게 묻지 않고 5분 안에 새 비밀번호로 다시 로그인할 수 있다

## Assumptions

- 메일은 Gmail SMTP(앱 비밀번호)로 보낸다. 무료 Gmail은 하루 보낼 수 있는 수에 한도가 있어 회원이 늘면 다른 발송 서비스로 옮겨야 할 수 있다. 옮겨도 이 스펙의 동작(코드, 제한, 응답)은 같다
- 메일 발송은 moa가 만든다. psw-dev-kit에 메일 헬퍼가 있는지는 팀에 물었고, 키트에 있으면 그쪽으로 바꾼다(그때 출처를 "moa, 키트 <헬퍼>"로 고치고 moa가 바꾸는 것만 남긴다, 원칙 III)
- 아이디는 로그인 화면의 실패 안내로 있는지 드러나지 않지만(FR-015), 가입 화면의 "이미 쓰는 아이디"(US1-AC7)로는 드러난다. 아이디는 공개되는 값이 아니어도 고르는 사람에게 겹침을 알려야 해서 둔다. 계정 정보 화면은 이메일 인증을 마친 사람만 쓰므로 대량 조회는 코드 발송 제한(FR-008)으로 늦춰진다
- 만 14세 미만 가입 처리는 `010-social-login`·`009-mypage`의 같은 질문(팀 확인 중)의 답을 이 가입에도 똑같이 건다. 이 스펙에서 따로 정하지 않는다
- 가입 뒤 회원 이메일 바꾸기, 기존 비밀번호 회원(시드·관리자가 만든 회원)과 소셜 회원의 이메일 등록, 소셜 회원이 비밀번호를 더하는 일은 이번 범위가 아니다. 필요하면 이 스펙을 고쳐 더한다
- 로그인 실패 잠금을 IP나 기기 기준으로 더 막는 일, 캡차, 2단계 인증은 이번 범위가 아니다
- 인증 코드 메일 문안은 한국어 하나다. 보내는 이름은 "moa"다
- 아이디·비밀번호 규칙과 코드 값(만료, 간격, 횟수)은 이 스펙의 잠정 값이다. 바꾸면 이 스펙을 고친다
- 앱 클라이언트는 이번 범위가 아니다 (010과 같다)

## 다른 스펙·문서에 줄 영향 (이 스펙에서는 고치지 않는다)

남의 스펙은 고치지 않는다. 구현 때 담당에게 알리고, 담당이 자기 스펙을 고친다 (원칙 IV).

- `010-social-login` (jeonggi4007)
  - 배경 "이 기능이 moa의 첫 회원 가입 경로다": 가입 경로가 소셜(010)과 아이디·비밀번호(019) 둘이라고 고친다
  - FR-014·가정 240줄: 이메일 중복 확인이 019의 회원 이메일도 비교한다고 적는다. 가입과 연결(FR-006) 모두다 (019 FR-005)
  - FR-001 "지금의 아이디·비밀번호 로그인 폼은 그대로 둔다": 회원도 이 폼을 쓴다고 적는다
- `002-admin-users` (haily)
  - 사용자 관리 목록·드로어에 회원 이메일과 가입 방식(아이디·비밀번호 / 구글 / 디스코드)을 보일지 정한다. FR-004 회원 정보 모델, `specs/README.md` "회원 정보 모델" 경계 줄과 이어진다
  - 가정 "회원 가입·로그인 방식은 사용자 쪽 기능이 정한다": 010과 019를 가리키게 고친다
  - 관리자 잠금과 임시 잠금(019 FR-016)이 따로라는 것, 드로어의 비밀번호 초기화가 임시 잠금을 풀지 않는 것을 적을지 정한다
  - 019 FR-015의 임시 잠금이 관리자·운영자 계정에도 걸린다(최고 관리자 포함, 5번·15분). 관리자 로그인 동작이 바뀐다는 것을 알린다
- `005-admin-login-history` (haily): 실패 사유에 "임시 잠금"이 더해진다 (019 FR-017). 머리 설명("계정 잠금은 사용자 관리에서 해요")에 임시 잠금은 저절로 풀린다는 뜻을 더할지 정한다
- `012-terms-privacy` (haily): 처리방침 문안의 처리 항목·목적에 회원 이메일(가입 인증·비밀번호 재설정), 보유 기간에 회원 이메일(탈퇴 뒤 30일)·인증 코드(1일)·로그인 실패 기록(1일)을 넣는다. 019가 `docs/privacy.md`에 세 줄을 더했으므로 012 FR-009대로 처리방침 새 버전이 필요한지 본다. 개인정보 수집·이용 동의서(010 `PRIVACY`)의 수집 항목에도 이메일이 더해지는지 함께 본다
- `018-member-withdrawal` (jeonggi4007): 파기 대상에 회원 이메일과 인증 코드를 더한다 (019 FR-022). 유예 중 같은 이메일 가입 막기(US2-AC13)가 회원 이메일에도 걸린다
- `008-party` (hyeonchang): 가정 "회원 가입은 아직 없으므로 시드 계정으로 시험한다"는 010·019로 낡았다. 고칠 때 알린다
- `001-admin-menus` (haily): 로그인 화면에 "회원가입"·"아이디·비밀번호 찾기" 링크가 더해진다. 계정 화면·프로그램 표는 고칠 것이 없다 (019 FR-011)
- `docs/privacy.md`: 보관 기간 표에 019 FR-021의 세 줄을 더한다 (이 스펙 브랜치에서 함께 고친다)
- 지금 비밀번호 변경 화면(`/account/password`, 키트)의 규칙(8~100자)을 019 FR-004(영문·숫자 포함, 아이디와 다름)에 맞출지: 키트 동작 변경이라 plan에서 정한다
