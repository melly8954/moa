# Feature Specification: UI 기반 (ui-foundation)

**Feature Branch**: `feat/020-ui-foundation`

**Created**: 2026-11-28

**Status**: Draft

**Input**: User description: "프론트 기준 표준. 팀원이 이 스펙과 (나중의) 견본 파일을 각자 AI 도구에 넣으면 모든 화면이 같은 모양으로 나오게 한다. 메인 화면은 디스코드(서버·채널식 왼쪽 띠, 촘촘한 어두운 화면)와 트위터/X(타임라인 피드, 촘촘한 글, 오른쪽 트렌드·추천)를 잘 섞는다. 개인 프로필은 인스타그램식 피드(아바타·수·소개 머리, 게시물·숏폼 격자, 탭). AI가 만든 듯한 느낌(보라·파랑 그라디언트, 유리 효과, 이모지 많은 화면, 둥글고 흐린 그림자 카드, Inter/Pretendard만 쓴 흔한 모양, 반짝이 아이콘)을 피하고 moa만의 성격을 낸다. 글꼴과 색(브랜드, 강조, 의미 색, 중립 색, 밝게·어둡게, WCAG 2.2 AA)을 정한다. 소셜 로그인 화면(제공자 단추, 계정 연결 표시)은 기존 스펙에 맞춘다. 웹 기본기(시맨틱 HTML, 접근성, 반응형, 성능, 폼, 상태, 문구 파일, 메타, 주소·뒤로 가기)를 지킨다."

**출처**: moa. 토큰을 두는 방식(테마 파일의 CSS 변수 → 테마 변수 클래스, 색 직접 지정 검사, 문구 검사)은 키트 web-next 골격의 것을 그대로 쓰고 값과 토큰 몇 개를 더한다 (원칙 III). 화면 배치는 디스코드(레일·채널 목록·계정 줄), X(가운데 타임라인·오른쪽 곁줄), 인스타그램(프로필 머리·3열 격자)을 본떴고 값은 moa가 정했다 (2026-11-28)

**배경** (기존 스펙과 코드에서 따름):

- 화면은 관리 셸과 사용자 셸로 나뉜다. 지금 두 셸은 같은 사이드바 모양을 쓰고 메뉴만 다르다 (`001-admin-menus` FR-005). 사용자 메뉴는 메뉴 관리에서 대상 "사용자"로 다루고 아이콘 이름을 가진다 (`001-admin-menus` FR-007·FR-008)
- `specs/README.md` "맞춰야 할 경계"의 "사용자 셸의 메뉴와 모양"은 사용자 쪽 담당이 정하도록 남아 있다. 이 스펙이 그 "모양"에 답한다. 메뉴 항목 자체는 각 기능 스펙이 정한다
- 색은 테마 변수 클래스로만 쓴다. 화면 코드에 팔레트 색·hex·rgb를 적으면 색 검사가 실패한다 (프론트 `check:colors`). 화면 글자는 `messages/ko.json`에만 두고 화면 코드에 한글을 적으면 문구 검사가 실패한다 (`check:i18n`)
- 화면 모드는 밝게·어둡게·기기 설정 셋이고 계정 줄 톱니에서 고른다 (`001-admin-menus` FR-005)
- 소셜 로그인 제공자는 구글과 디스코드다. 설정된 제공자만 단추가 보이고, 계정 연결·해제는 계정 설정 화면에 있다 (`010-social-login` FR-001·FR-006·FR-007). 아이디·비밀번호 회원가입은 `019`(예약, 담당 jeonggi4007, 기본 회원가입·로그인)가 정한다
- 프로필 페이지의 틀(머리, 009 공개 항목, 활동 칸 탭)은 `014-friends-follow` "화면"이, 숏폼 격자(3:4 썸네일, 3열)와 세로 뷰어는 `015-game-shortform` "화면"이 정한다. 이 스펙은 그 내용을 다시 정하지 않고 배치·크기·모양만 정한다
- 기존 기능 스펙들은 "배치, 색, 컴포넌트는 plan에서 정한다"고 남겼다 (`008-party` "화면"). 이 스펙이 그 공통 기준이다
- 구체 값(색 코드, 글꼴, 크기, 와이어프레임, 컴포넌트 규칙)은 같은 폴더의 `design-system.md`에 둔다. 이 spec.md는 지켜야 할 동작과 기준만 적고, 값은 `design-system.md`가 정본이다

**용어**:

- **레일**: 사용자 셸 맨 왼쪽의 아이콘 띠 (디스코드의 서버 목록 자리)
- **패널**: 레일 오른쪽의 목록 띠 (디스코드의 채널 목록 자리). 맨 아래에 계정 줄이 있다
- **본문 열**: 가운데의 내용 열 (X의 타임라인 자리)
- **곁줄**: 넓은 화면에서 본문 열 오른쪽에 붙는 띠 (X의 트렌드·추천 자리)
- **토큰**: 색·글꼴·간격·모서리·움직임의 이름 붙은 값. 화면 코드는 값 대신 토큰 이름만 쓴다
- **시그널**: moa의 강조 색 (밝은 라임). 한 화면의 가장 중요한 행동과 "새것·안 읽음·지금 선택됨"에만 쓴다

## Clarifications

### Session 2026-11-28

- Q: 기본 화면 모드는? → A: A. 지금처럼 기기 설정(밝게·어둡게 선호)을 따른다. 회원이 톱니 메뉴에서 직접 고르면 그 값이 먼저다(`001-admin-menus` FR-005). 밝게·어둡게 두 벌 모두 AA를 지킨다 (2026-11-28 사용자 결정)
- Q: 관리 셸에도 새 색·글꼴을 쓰는가? → A: 아니다, 아직 건드리지 않는다. 이 스펙은 사용자 화면(사용자 셸, 로그인 등 공개 화면, 회원의 계정 화면)에만 적용한다. 관리 셸이 그리는 화면(관리 화면, 관리자 계정의 계정 화면)은 지금 모양·배치·테마(색, 글꼴, 모서리)를 그대로 둔다. 그래서 새 토큰 값은 사용자 화면 범위 안에서만 쓰이게 나눠 둔다(FR-022). 관리 셸에 들일지는 나중에 따로 정한다 (2026-11-28 사용자 결정)
- Q: 소셜 단추 순서는? → A: 디스코드, 구글 순이다. 게임 커뮤니티라 디스코드 계정이 가장 흔할 것으로 본다. 설정된 제공자만 보이는 규칙(`010` FR-001)은 그대로다 (2026-11-28, 작성하며 정함)
- Q: 좁은 화면의 길 찾기는? → A: 아래 탭 줄(X처럼) + 왼쪽 서랍(디스코드처럼, 레일과 패널을 함께 연다)이다. 아래 탭 줄에는 레일 위쪽 항목 넷과 "더보기"(서랍 열기)를 둔다 (2026-11-28, 작성하며 정함)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 팀원이 표준만 보고 새 화면을 만든다 (Priority: P1)

팀원이 새 기능의 화면을 만들 때 이 스펙과 `design-system.md`를 자기 AI 도구에 넣고 만든다. 나온 화면은 다른 팀원이 만든 화면과 같은 색·글꼴·간격·단추 모양을 갖고, 프론트 검사를 한 번에 통과한다.

**Why this priority**: 이 스펙을 만드는 이유다. 사람마다·도구마다 화면이 달라지면 서비스가 한 제품으로 보이지 않고, 리뷰에서 모양을 고치는 데 시간이 든다.

**Independent Test**: 토큰과 기준 컴포넌트만 바뀐 상태에서, 표준을 넣은 AI 도구로 새 화면 하나(예: 빈 목록 화면)를 만들어 프론트 전체 검사와 아래 AC를 확인한다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** 새 화면을 만들었다, **When** 프론트 전체 검사를 돌린다, **Then** 색 검사와 문구 검사를 포함해 모두 통과한다. 화면 코드에 색 값, 한글, 글꼴 이름이 직접 없다 (FR-001, FR-016)
2. **US1-AC2** **Given** 새 화면에 그라디언트 배경, 흐림(backdrop blur) 유리 효과, 큰 흐린 그림자, 장식 이모지 중 하나가 있다, **When** 프론트 전체 검사를 돌린다, **Then** 검사가 실패하고 어느 줄인지 알려 준다 (FR-020)
3. **US1-AC3** **Given** 테마 파일의 토큰 값 하나(예: 시그널 색)를 바꾼다, **When** 화면들을 다시 연다, **Then** 그 토큰을 쓰는 모든 사용자 화면이 함께 바뀌고 화면 코드는 고치지 않는다 (FR-001)
4. **US1-AC4** **Given** 이 스펙의 토큰·글꼴·컴포넌트 변경이 들어갔다, **When** 관리자 계정으로 관리 화면, 관리 화면의 창·메뉴·토스트, 관리자의 계정 화면(알림, 설정)을 두 모드에서 연다, **Then** 색, 글꼴, 모서리, 포커스 표시, 배치가 변경 전과 같다 (FR-022)

### User Story 2 - 회원이 메인 셸에서 길을 찾는다 (Priority: P1)

회원이 넓은 화면에서 moa를 열면 왼쪽 레일에서 큰 영역(홈, 탐색, 모집 등)을 고르고, 패널에서 그 영역의 세부 목록을 고르고, 가운데 본문 열에서 내용을 훑고, 오른쪽 곁줄에서 인기·모집 중인 것을 본다. 화면이 좁아지면 띠들이 차례로 접히고, 휴대폰에서는 아래 탭 줄과 서랍으로 같은 곳에 간다.

**Why this priority**: 모든 사용자 화면이 이 셸 안에 들어간다. 셸이 먼저 정해져야 각 기능 화면이 자리를 잡는다.

**Independent Test**: 사용자 메뉴 몇 개를 둔 채 화면 폭을 1440·1100·900·375px로 바꾸며 각 띠가 보이는지와, 각 폭에서 모든 메뉴에 닿는지 본다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 화면 폭이 1280px 이상이다, **When** 사용자 셸 화면을 연다, **Then** 레일, 패널, 본문 열, 곁줄이 왼쪽부터 차례로 보이고, 본문 열은 정해진 최대 폭을 넘지 않는다 (FR-005)
2. **US2-AC2** **Given** 사용자 메뉴에 1단계 메뉴와 그 아래 2단계 메뉴가 있다, **When** 레일에서 1단계 메뉴 하나를 고른다, **Then** 패널에 그 메뉴의 2단계 메뉴가 보이고, 고른 레일 항목에 선택 표시(왼쪽 막대)가 보이며 `aria-current`가 붙는다 (FR-006)
3. **US2-AC3** **Given** 화면 폭이 1024~1279px이다, **When** 화면을 연다, **Then** 곁줄이 보이지 않고 레일·패널·본문 열이 보인다. 곁줄에만 있던 내용은 다른 화면(탐색, 모집)에서 볼 수 있다 (FR-005, FR-007)
4. **US2-AC4** **Given** 화면 폭이 768~1023px이다, **When** 패널 열기 단추를 누른다, **Then** 패널이 본문 위로 겹쳐 열리고, Esc나 바깥을 누르면 닫히며 포커스가 그 단추로 돌아온다 (FR-005, FR-014)
5. **US2-AC5** **Given** 화면 폭이 767px 이하다, **When** 화면을 연다, **Then** 레일·패널 대신 위쪽 머리 줄과 아래 탭 줄이 보이고, 아래 탭 줄의 "더보기"를 누르면 레일과 패널이 든 서랍이 열린다. 가로 스크롤이 생기지 않는다 (FR-005)
6. **US2-AC6** **Given** 로그인한 회원이다, **When** 패널을 본다, **Then** 패널 맨 아래에 계정 줄(`001-admin-menus` FR-005)이 그대로 있다. 좁은 화면에서는 서랍 맨 아래에 있다 (FR-006)

### User Story 3 - 회원이 밝게·어둡게 어느 쪽에서도 편히 읽는다 (Priority: P1)

회원이 밝게나 어둡게를 고르면 모든 화면의 글자, 아이콘, 입력칸 테두리, 포커스 표시가 그 모드에서 충분히 또렷하다. 강조 색과 의미 색(성공·주의·위험·안내)은 두 모드에서 같은 뜻으로 보인다.

**Why this priority**: 게임 커뮤니티는 밤에 어둡게 쓰는 사람이 많다. 한 모드만 맞춰 두면 다른 모드에서 글자가 안 보이는 화면이 생긴다.

**Independent Test**: 두 모드에서 주요 화면(홈, 프로필, 로그인)을 자동 접근성 검사로 돌리고, `design-system.md`의 대비 표를 계산 도구로 다시 잰다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 밝게 또는 어둡게다, **When** 주요 화면을 자동 접근성 검사로 돌린다, **Then** 색 대비 위반이 0건이다 (FR-002, SC-002)
2. **US3-AC2** **Given** 어느 모드든, **When** 키보드로 단추·링크·입력칸에 포커스를 옮긴다, **Then** 포커스 표시가 늘 보이고 그 주변 색과 3:1 이상 차이 난다 (FR-002, FR-014)
3. **US3-AC3** **Given** 상태(성공·주의·위험·안내)를 보이는 표시다, **When** 색을 구별하지 못하는 사람이 본다, **Then** 색 말고도 글자나 아이콘으로 상태를 알 수 있다 (FR-011)

### User Story 4 - 처음 온 사람이 소셜 계정으로 시작한다 (Priority: P2)

처음 온 사람이 로그인 화면에서 디스코드나 구글 단추를 알아보고 누른다. 단추는 각 제공자의 공식 모양을 지키고, 둘은 같은 크기·같은 줄 맞춤이다. 이미 회원이면 계정 설정에서 어느 제공자가 연결됐는지 한눈에 보고 연결·해제한다.

**Why this priority**: 소셜 로그인이 지금 회원의 첫 가입 경로다(`010-social-login` 배경). 제공자 단추가 어색하면 가입하지 않고 떠난다. 다만 셸(US2)보다 화면 수가 적어 P2다.

**Independent Test**: 두 제공자를 설정한 환경에서 로그인 화면과 계정 설정 화면을 두 모드·두 폭(1440, 375)으로 열어 본다.

**Acceptance Scenarios**:

1. **US4-AC1** **Given** 두 제공자가 설정되어 있다, **When** 로그인 화면을 연다, **Then** "Discord로 계속하기", "Google로 계속하기" 단추가 이 순서로 아이디·비밀번호 폼 위에 있고, 둘은 높이·폭·로고 위치가 같으며, 로고는 각 제공자의 공식 그림을 바꾸지 않고 쓴다 (FR-009)
2. **US4-AC2** **Given** 한 제공자만 설정되어 있다, **When** 로그인 화면을 연다, **Then** 그 단추 하나만 보이고 빈자리가 남지 않는다 (FR-009, `010-social-login` FR-001)
3. **US4-AC3** **Given** 단추를 눌러 제공자 화면으로 넘어가는 중이다, **When** 다시 누른다, **Then** 두 번 넘어가지 않고 단추가 "진행 중" 상태로 보인다 (FR-009)
4. **US4-AC4** **Given** 소셜 로그인이 실패해 돌아왔다(`010-social-login` US3), **When** 로그인 화면이 보인다, **Then** 실패 안내가 단추들 위에 오류 알림으로 보이고 화면 읽기 도구가 읽어 준다 (FR-009, FR-012)
5. **US4-AC5** **Given** 회원이 계정 설정 화면을 연다, **When** 소셜 계정 칸을 본다, **Then** 제공자마다 한 줄에 로고, 제공자 이름, 상태(연결됨/연결 안 됨)와 연결·해제 단추가 보인다. 상태는 글자로도 보인다 (FR-010)
6. **US4-AC6** **Given** 비밀번호가 없고 연결된 소셜 계정이 하나뿐인 회원이다, **When** 계정 설정 화면을 본다, **Then** 그 줄에 "유일한 로그인 수단이라 해제할 수 없다"는 안내가 미리 보이고, 해제를 눌러도 `010-social-login` US5-AC6대로 막힌다 (FR-010)

### User Story 5 - 회원이 프로필을 인스타그램처럼 본다 (Priority: P2)

회원이 다른 회원의 이름을 눌러 프로필을 연다. 위쪽 머리에 큰 아바타, 닉네임·태그, 친구·팔로워·팔로잉 수, 관계 단추, 자기소개가 있고, 그 아래 탭과 3열 격자가 있다. 휴대폰에서도 같은 순서로 보인다.

**Why this priority**: 프로필은 피드형 SNS의 중심 화면이고 `014`·`015`가 내용을 이미 정했다. 모양만 정하면 바로 만들 수 있다.

**Independent Test**: 숏폼이 있는 회원의 프로필을 1440·375px에서 열어 머리와 격자의 배치, 탭 전환, 격자 칸의 비율을 본다.

**Acceptance Scenarios**:

1. **US5-AC1** **Given** 넓은 화면이다, **When** 프로필을 연다, **Then** 프로필은 본문 열과 곁줄 자리를 합친 폭(정해진 최대 폭)을 쓰고, 머리는 왼쪽 아바타, 오른쪽 이름 줄·수 줄·소개 순서다 (FR-008)
2. **US5-AC2** **Given** 휴대폰 폭이다, **When** 프로필을 연다, **Then** 아바타와 수 줄이 한 줄에 있고, 그 아래 이름·소개, 그 아래 관계 단추(폭을 나눠 가득)가 있다 (FR-008)
3. **US5-AC3** **Given** 활동 칸에 탭이 있다, **When** 탭을 바꾼다, **Then** 주소의 탭 값이 바뀌고, 뒤로 가기를 누르면 앞 탭으로 돌아오며, 고른 탭에 시그널 밑줄과 `aria-selected`가 붙는다 (FR-008, FR-017)
4. **US5-AC4** **Given** 숏폼 탭이다, **When** 격자를 본다, **Then** 3열, 칸 사이 2px, 칸 비율 3:4이고, 칸마다 조회수가 왼쪽 아래에 보인다. 불러오는 동안 같은 비율의 자리 표시가 보여 내용이 들어와도 화면이 밀리지 않는다 (FR-008, FR-012, `015-game-shortform` "프로필의 숏폼 칸")
5. **US5-AC5** **Given** 회원 한 명과 파티 하나가 함께 보이는 화면이다, **When** 둘의 아바타를 본다, **Then** 사람은 원, 모임(파티·크루)은 모서리 둥근 사각형이다 (FR-011)

### User Story 6 - 키보드·화면 읽기 도구·움직임 줄이기를 쓰는 회원도 다 쓴다 (Priority: P2)

마우스를 쓰지 않는 회원은 키보드만으로, 화면을 보지 못하는 회원은 화면 읽기 도구로, 움직임에 어지러움을 느끼는 회원은 기기의 "동작 줄이기"를 켠 채로 모든 화면을 쓴다.

**Why this priority**: 접근성은 나중에 붙이면 거의 모든 화면을 다시 고쳐야 한다. 기준에 처음부터 넣어야 한다.

**Independent Test**: 주요 화면을 키보드만으로 끝까지 써 보고, 자동 접근성 검사와 동작 줄이기 설정으로 다시 본다.

**Acceptance Scenarios**:

1. **US6-AC1** **Given** 아무 사용자 셸 화면이다, **When** 처음 Tab을 누른다, **Then** "본문으로 건너뛰기" 링크가 보이고, 누르면 포커스가 본문 열로 간다 (FR-014)
2. **US6-AC2** **Given** 아무 화면이다, **When** 화면 읽기 도구로 영역 목록을 본다, **Then** 레일·패널(navigation), 본문(main), 곁줄(complementary)이 이름과 함께 보이고, 화면마다 제목(h1)이 하나다 (FR-014)
3. **US6-AC3** **Given** 아이콘만 있는 단추다, **When** 포커스하거나 화면 읽기 도구가 읽는다, **Then** 이름이 읽히고 마우스를 올리면 같은 이름의 툴팁이 보인다 (FR-014)
4. **US6-AC4** **Given** 기기의 동작 줄이기가 켜져 있다, **When** 서랍·창·툴팁을 열고 닫는다, **Then** 미끄러지거나 커지는 움직임 없이 바로(또는 짧은 투명도 변화로만) 나타난다 (FR-015)
5. **US6-AC5** **Given** 창(dialog)을 열었다, **When** Tab을 계속 누른다, **Then** 포커스가 창 안에서만 돌고, 닫으면 창을 연 단추로 돌아온다 (FR-014)

### User Story 7 - 회원이 어느 화면에서든 같은 방식으로 기다리고, 비었음을 알고, 실패에서 돌아온다 (Priority: P3)

목록이 불러오는 중이면 그 모양의 자리 표시가, 비었으면 한 줄 설명과 할 일 하나가, 실패하면 이유와 "다시 시도"가 늘 같은 자리·같은 모양으로 보인다.

**Why this priority**: 화면마다 상태 표시가 다르면 사용자가 지금 무슨 일인지 배워야 한다. 기능마다 다시 정하지 않게 공통으로 정한다.

**Independent Test**: 피드 목록 하나를 느린 응답·빈 응답·오류 응답으로 바꿔 가며 본다.

**Acceptance Scenarios**:

1. **US7-AC1** **Given** 피드 목록을 처음 불러온다, **When** 응답을 기다린다, **Then** 목록 항목과 같은 높이·모양의 자리 표시가 보이고, 회전 표시만 덩그러니 있지 않다 (FR-012)
2. **US7-AC2** **Given** 결과가 없다, **When** 화면을 본다, **Then** 그림·이모지 없이 한 줄 설명과 할 일 단추 하나(있으면)가 보인다 (FR-012)
3. **US7-AC3** **Given** 불러오기가 실패했다, **When** 화면을 본다, **Then** 오류 코드에 맞는 문구, "다시 시도" 단추, 문의 번호가 보이고, 다시 시도하면 그 자리만 다시 불러온다 (FR-012)
4. **US7-AC4** **Given** 저장 단추를 눌렀다, **When** 저장이 끝나기 전이다, **Then** 단추가 진행 중으로 바뀌고 다시 눌리지 않으며, 입력한 값은 그대로다 (FR-013)

### User Story 8 - 회원이 링크를 나누고 뒤로 가기로 돌아온다 (Priority: P3)

회원이 탐색 탭·거르기를 바꾸거나 숏폼을 열면 주소가 따라 바뀌어, 그 주소를 친구에게 보내면 같은 화면이 열린다. 피드에서 글을 열었다가 뒤로 가면 보던 자리로 돌아온다. 공유한 주소는 메신저 미리보기에 제목과 그림이 나온다.

**Why this priority**: SNS는 링크로 퍼진다. 다만 각 기능 화면이 생겨야 확인할 수 있어 P3다.

**Independent Test**: 탐색 화면에서 탭·거르기를 바꾸고 숏폼을 연 뒤 주소를 새 창에 붙이고, 뒤로 가기를 눌러 본다.

**Acceptance Scenarios**:

1. **US8-AC1** **Given** 탭·거르기·쪽이 있는 화면이다, **When** 값을 바꾼다, **Then** 주소의 검색 값이 바뀌고, 그 주소를 새 창에서 열면 같은 탭·거르기·쪽이 보인다 (FR-017)
2. **US8-AC2** **Given** 피드를 여러 묶음 내려 항목 하나를 열었다, **When** 뒤로 가기를 누른다, **Then** 다시 불러오지 않고 보던 스크롤 자리로 돌아온다 (FR-017)
3. **US8-AC3** **Given** 누구나 볼 수 있는 화면(공지 상세, 모집 중 파티, 공개 숏폼)이다, **When** 그 주소를 미리보기를 만드는 곳에 붙인다, **Then** 화면 제목, 설명, 대표 그림이 나온다. 로그인해야 보는 화면과 계정 화면은 검색 엔진에 올라가지 않게 표시한다 (FR-018)

### Edge Cases

- 닉네임·자기소개가 아주 길거나 띄어쓰기 없는 영문·숫자가 이어진다: 정해진 줄 수에서 말줄임하고, 한글은 낱말 중간에서 줄을 바꾸지 않으며, 긴 영문·주소는 칸 안에서 끊는다. 가로 스크롤이 생기지 않는다 (FR-004)
- 수(팔로워, 조회수)가 아주 크다: 한국어 줄임(1.2만, 3.4억)으로 보이고 정확한 수는 툴팁·화면 읽기 도구로 준다. 숫자 폭이 같아 바뀌어도 옆 글자가 흔들리지 않는다 (FR-004)
- 화면 확대 200%, 폭 320px: 내용이 잘리거나 가로로 넘치지 않고 아래 탭 줄 배치로 바뀐다 (FR-005, FR-014)
- 글꼴 파일을 못 받았거나 느리다: 기기 글꼴로 먼저 보이고, 받은 뒤 바뀔 때 줄 높이가 거의 같아 화면이 크게 밀리지 않는다 (FR-003, FR-019)
- 사용자 메뉴의 1단계가 레일에 다 들어가지 않을 만큼 많다: 레일이 그 안에서 세로로 스크롤되고, 아래 탭 줄에는 앞 넷만, 나머지는 서랍에 있다 (FR-006)
- 1단계 메뉴에 2단계 메뉴가 없다: 레일 항목이 바로 그 화면으로 간다. 그 화면이 패널에 보일 보조 목록을 주지 않으면 빈 패널을 두지 않고 패널을 접어 본문 열이 그 자리를 쓴다 (FR-006)
- 제공자 로고 그림을 못 받았다: 단추의 글자("Discord로 계속하기")만으로 무엇인지 알 수 있고 단추 크기가 바뀌지 않는다 (FR-009)
- 기기 설정 화면 모드가 바뀐다(낮→밤 자동): 다시 열지 않아도 바로 따라 바뀐다. 화면 모드를 직접 골랐으면 그 값이 먼저다 (FR-002)
- 사용자가 브라우저에서 글자 크기를 키웠다: 글자 크기는 화면 기준 단위를 따라 함께 커지고 단추·줄 높이도 따라 늘어 글자가 잘리지 않는다 (FR-004)

## Requirements *(mandatory)*

### Functional Requirements

**토큰**

- **FR-001**: 사용자 화면의 색·글꼴·모서리·그림자·움직임 값은 토큰으로만 써야 한다(MUST). 토큰 값은 테마 파일 한 곳에 두고, 화면 코드는 토큰 이름(테마 변수 클래스)만 쓴다. 화면 코드에 색 값, 글꼴 이름, 임의 그림자 값을 직접 적지 않는다. 간격·폭·높이의 화면 상수는 배치 상수 파일에 둔다
- **FR-002**: 밝게·어둡게 두 벌의 색 토큰을 둬야 한다(MUST). 값은 `design-system.md` "색"이 정본이다
  - 글자와 그 바탕은 4.5:1 이상, 큰 글자(24px 이상, 또는 굵은 18.66px 이상)와 아이콘·입력칸 테두리·포커스 표시·선택 표시는 3:1 이상이다 (WCAG 2.2 AA, 1.4.3·1.4.11)
  - 기존 토큰 이름(배경, 글자, 주 색, 보조, 흐림, 강조 배경, 위험 등)은 그대로 두고, 사용자 화면 범위(FR-022)에서만 값을 바꾼다. 모자란 토큰(시그널, 레일, 주의·안내, 의미 색의 진한 글자, 제공자 단추)을 더한다. 더한 토큰도 테마 변수 클래스로 쓸 수 있게 한다
  - 강조 색(시그널)은 한 화면 영역의 가장 중요한 행동 하나와 "새것·안 읽음·선택됨" 표시에만 쓴다. 위험 색은 오류와 되돌릴 수 없는 행동에만 쓴다
- **FR-003**: 글꼴은 `design-system.md` "글꼴"의 세 벌(본문·제목, 숫자·영문 표시, 고정폭)만 써야 한다(MUST). 셋 다 무료로 쓸 수 있는 오픈 라이선스이고 서비스가 직접 내려 준다(외부 글꼴 서버에 화면마다 요청하지 않는다). 글꼴을 받기 전에는 기기 글꼴로 먼저 보인다
- **FR-004**: 글자 크기는 `design-system.md` "글자 크기" 단계만 써야 한다(MUST). 본문 글은 15px·줄 높이 1.5 안팎, 가장 작은 글자는 12px이다. 한글은 낱말 단위로 줄을 바꾸고, 수는 폭이 같은 숫자로 보이며, 큰 수는 한국어 줄임으로 보인다

**배치**

- **FR-005**: 사용자 셸은 레일·패널·본문 열·곁줄의 네 띠로 나뉘어야 한다(MUST). 화면 폭에 따라 다음처럼 바뀐다. 폭 기준값과 띠 폭은 `design-system.md` "배치"가 정한다
  - 1280px 이상: 네 띠 모두
  - 1024~1279px: 곁줄 없음
  - 768~1023px: 레일과 본문 열. 패널은 단추로 본문 위에 겹쳐 연다
  - 767px 이하: 위쪽 머리 줄(로고, 화면 제목, 알림 벨), 아래 탭 줄(레일 앞 넷 + 더보기), 서랍(레일+패널+계정 줄)
  - 어느 폭에서도 가로 스크롤이 생기지 않는다(표 같은 넓은 내용은 그 칸 안에서만 가로로 넘긴다)
- **FR-006**: 레일과 패널은 메뉴 관리의 사용자 메뉴를 그대로 보여야 한다(MUST). 레일은 1단계 메뉴(아이콘과 툴팁), 패널은 고른 1단계의 2단계 메뉴다. 레일 위쪽에는 moa 표지(홈), 그 아래 1단계 메뉴, 구분선 아래에 내가 속한 모임(파티·크루)의 아이콘 자리를 둔다. 모임 자리에 무엇을 보일지는 각 모임 기능 스펙이 정한다. 패널 맨 아래는 계정 줄이다(`001-admin-menus` FR-005)
- **FR-007**: 곁줄은 기능들이 꽂는 묶음(모듈) 자리여야 한다(MUST). 각 묶음은 제목, 짧은 목록(최대 5줄), "더 보기" 링크로 된다. 곁줄에만 있는 정보나 행동은 두지 않는다(좁은 화면에서는 곁줄이 없기 때문). 어떤 묶음을 둘지는 각 기능 스펙이 정한다. 곁줄 맨 아래에 이용약관·개인정보처리방침 줄을 둔다(`001-admin-menus` FR-005의 푸터 줄은 곁줄이 있을 때 곁줄로 옮기고, 없을 때는 본문 맨 아래에 둔다)
- **FR-008**: 프로필 페이지는 `design-system.md` "프로필 배치"를 따라야 한다(MUST). 내용과 공개 규칙은 `014-friends-follow`·`015-game-shortform`이 정한다
  - 프로필은 본문 열과 곁줄 자리를 합친 폭을 쓴다(곁줄 없음)
  - 머리: 아바타(넓은 화면 128px, 좁은 화면 80px), 이름 줄(닉네임·태그, 비공개 자물쇠, 관계 단추), 수 줄(친구·팔로워·팔로잉), 자기소개, 009 공개 항목
  - 활동 칸: 아이콘+글자 탭, 고른 탭은 시그널 밑줄. 탭 값은 주소에 둔다. 숏폼 격자는 3열·2px 간격·3:4 칸
- **FR-009**: 로그인 화면의 소셜 단추는 다음을 지켜야 한다(MUST). 동작(어떤 제공자가 보이는가, 실패 안내)은 `010-social-login`이 정하고 이 스펙은 모양만 정한다
  - 순서는 Discord, Google. 단추는 아이디·비밀번호 폼 위에 있고 "또는" 구분선으로 나뉜다
  - 두 단추는 높이 40px, 폭 가득, 로고를 왼쪽 같은 자리에, 글자는 가운데다. 로고 크기·여백은 제공자 지침이 먼저다
  - 색·로고는 각 제공자의 브랜드 지침을 따른다. 로고는 제공자가 낸 공식 그림을 바꾸지 않고(색, 비율, 모양) 정해진 여백을 둔다. 제공자 이름은 영문(Discord, Google)으로 적는다
  - 누르면 단추가 진행 중으로 바뀌고 두 번 넘어가지 않는다
  - 아이디·비밀번호 가입·찾기 링크 자리는 폼 아래에 둔다. 그 동작은 `019`(기본 회원가입·로그인)가 정한다
- **FR-010**: 계정 설정의 소셜 계정 칸은 제공자마다 한 줄(로고, 제공자 이름, 상태 글자, 단추)이어야 한다(MUST). 연결됨은 성공 색 점과 "연결됨" 글자, 연결 안 됨은 흐린 글자다. 해제할 수 없는 줄은 그 이유를 줄 아래에 미리 보인다. 연결·해제 규칙과 안내 문구는 `010-social-login` FR-006·US5가 정한다. 관리자·운영자 계정에는 이 칸이 없다(`010` FR-007)

**컴포넌트**

- **FR-011**: 화면은 기존 기준 컴포넌트(단추, 입력, 창, 서랍, 메뉴, 탭, 알림, 토스트, 배지, 아바타, 자리 표시 등)를 `design-system.md` "컴포넌트 규칙"대로 써야 한다(MUST). 같은 일을 하는 컴포넌트를 새로 만들지 않는다
  - 단추 종류: 주(ink), 시그널(영역마다 하나), 테두리, 보조, 투명, 위험, 링크
  - 사람 아바타는 원, 모임(파티·크루) 아바타는 모서리 둥근 사각형이다
  - 상태는 색만으로 나타내지 않는다(글자나 아이콘을 함께)
  - 피드 항목은 카드(그림자·둥근 상자)가 아니라 아래 선으로 나뉜 줄이다
- **FR-012**: 불러오는 중·빈 결과·오류는 `design-system.md` "상태"대로 보여야 한다(MUST). 처음 불러올 때는 내용과 같은 모양의 자리 표시, 다시 불러올 때는 있던 내용을 그대로 두고 작은 진행 표시, 빈 결과는 한 줄 설명과 할 일 하나, 오류는 오류 코드 문구·다시 시도·문의 번호다. 오류·완료 안내는 화면 읽기 도구가 읽는다
- **FR-013**: 폼은 지금 로그인 화면의 모양(스키마 검사 → 칸 → 칸 아래 오류)을 따라야 한다(MUST). 칸 이름은 늘 보이고(자리 표시 글자를 이름 대신 쓰지 않음), 선택 칸에 "(선택)"을 붙이며, 오류는 그 칸 아래에 칸과 이어 두고, 오류가 나도 입력한 값을 지우지 않는다. 보내는 동안 단추는 진행 중이고 두 번 보내지 않는다. 저장하지 않은 변경이 있으면 떠날 때 묻는다

**접근성·움직임**

- **FR-014**: 모든 화면은 키보드만으로 모든 행동을 할 수 있어야 한다(MUST)
  - 영역은 의미 있는 요소(navigation, main, complementary, header)로 나누고 이름을 붙인다. 화면마다 h1이 하나다
  - 첫 포커스 자리에 "본문으로 건너뛰기"를 둔다
  - 누를 수 있는 것은 단추나 링크 요소다. 이동은 링크, 동작은 단추다
  - 포커스 표시는 지우지 않는다. 대체 표시 없이 외곽선을 없애지 않는다
  - 아이콘만 있는 단추에는 이름과 툴팁을 단다. ARIA는 기본 요소로 나타낼 수 없을 때만 쓴다
  - 창·서랍은 포커스를 안에 가두고, 닫으면 연 자리로 돌려준다. Esc로 닫힌다
  - 누르는 자리는 24×24px 이상, 좁은 화면의 주 행동은 높이 40px 이상이다 (WCAG 2.2 2.5.8)
  - 확대 200%와 폭 320px에서 내용이 잘리지 않는다
- **FR-015**: 움직임은 `design-system.md` "움직임"의 시간·곡선만 써야 한다(MUST). 기기의 동작 줄이기가 켜져 있으면 미끄러짐·커짐·튕김을 끄고 짧은 투명도 변화만 남긴다. 저절로 반복되는 장식 움직임은 두지 않는다(숏폼 재생처럼 기능이 정한 것은 그 스펙을 따른다)

**문구·주소·메타·성능**

- **FR-016**: 화면 글자는 모두 문구 파일에 둬야 한다(MUST). 화면 읽기 도구용 이름과 툴팁도 같다. 문구는 `design-system.md` "문구"를 따른다(해요체, 짧게, 느낌표·이모지 없음, 단추는 하는 일, 확인 창 단추는 "확인" 대신 그 행동)
- **FR-017**: 화면의 상태 중 다시 열었을 때 같아야 하는 것(탭, 거르기, 검색어, 쪽, 열린 숏폼처럼 주소가 있는 겹침 화면)은 주소에 둬야 한다(MUST). 확인 창 같은 잠깐 뜨는 창은 주소를 바꾸지 않는다. 피드는 뒤로 가기로 돌아오면 다시 불러오지 않고 보던 자리로 돌아온다. 로그인이 필요한 곳은 로그인한 뒤 원래 주소로 돌아온다(지금 규칙 그대로)
- **FR-018**: 모든 화면은 고유한 제목("화면 이름 | moa")을 가져야 한다(MUST). 누구나 볼 수 있고 나눌 만한 화면은 설명과 대표 그림을 미리보기 정보로 준다. 로그인해야 보는 화면, 계정·설정·로그인 화면은 검색 엔진에 올리지 않는다고 표시한다
- **FR-019**: 첫 화면이 빨리 보여야 한다(MUST). 글꼴은 쓰는 굵기만 받고, 한글 글꼴은 받는 동안 기기 글꼴로 먼저 보인다. 그림은 보이는 크기에 맞는 크기로 받고, 자리(가로·세로 비율)를 미리 잡아 들어올 때 화면이 밀리지 않으며, 화면 밖 그림은 나중에 받는다

**적용 범위**

- **FR-022**: 이 스펙은 사용자 화면에만 적용되고, 관리 셸이 그리는 화면은 지금 모양을 그대로 유지해야 한다(MUST, 2026-11-28)
  - 사용자 화면: 사용자 셸 화면, 로그인·가입 같은 공개 화면, 회원이 사용자 셸 안에서 보는 계정 화면(마이페이지, 알림, 설정)
  - 관리 셸 화면: 관리 화면(`/admin/...`), 관리자 계정이 관리 셸 안에서 보는 계정 화면(`001-admin-menus` FR-005). 색, 글꼴, 모서리, 포커스 표시, 배치가 바뀌지 않는다
  - 테마 파일은 지금처럼 한 개다. 새 값은 그 안에서 "사용자 화면 범위" 아래에만 두고, 범위 밖(관리 셸)은 지금 값이 그대로 쓰인다. 창·메뉴·토스트처럼 화면 밖으로 떠서 그려지는 층도 그 화면의 범위를 따라야 한다
  - 함께 쓰는 기준 컴포넌트를 고칠 때는 기존 종류의 모양을 바꾸지 않는다. 새 종류를 더하거나 범위 안에서만 달라지게 한다
  - 관리 셸에 이 스펙을 들이는 것은 범위 밖이고, 나중에 따로 정한다

**검사**

- **FR-020**: "AI 느낌 금지 목록"(`design-system.md`)의 항목 중 기계로 찾을 수 있는 것은 프론트 검사가 막아야 한다(MUST): 그라디언트 배경, 흐림 유리 효과, 큰 그림자(떠 있는 층 밖), 문구 파일과 화면 코드의 이모지, 정해진 세 벌 밖의 글꼴 이름. 지금 색 검사·문구 검사에 더하는 방식은 plan에서 정한다. 관리 화면 코드는 지금 모양을 그대로 두므로 이 검사에서 뺄 수 있다(이모지 검사는 문구 파일 전체에 건다). 사람이 판단할 항목은 리뷰에서 본다
- **FR-021**: 견본 파일(셸, 프로필, 로그인, 피드 항목, 상태 견본)은 이 스펙의 다음 단계에서 만든다(SHOULD). 견본과 `design-system.md`가 다르면 `design-system.md`를 고치고 견본을 맞춘다. 팀원의 AI 도구에는 `design-system.md`의 "AI 도구에게 주는 규칙"을 그대로 넣는다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 표준을 넣은 AI 도구로 만든 새 화면의 90% 이상이 첫 리뷰에서 색·글꼴·간격·컴포넌트 모양 지적 없이 넘어간다 (첫 다섯 화면으로 잰다)
- **SC-002**: 주요 화면(홈, 탐색, 모집, 프로필, 로그인, 계정 설정)을 두 모드에서 자동 접근성 검사로 돌리면 심각·치명 위반이 0건이다
- **SC-003**: `design-system.md`의 글자·바탕 짝 100%가 4.5:1 이상, 테두리·포커스·선택 표시 짝 100%가 3:1 이상이다
- **SC-004**: 폭 320·375·768·1024·1280·1440px 모두에서 가로 스크롤이 0이고, 모든 사용자 메뉴에 세 번 이하의 누름으로 닿는다
- **SC-005**: 주요 화면을 키보드만으로 끝까지 쓸 수 있다(행동 100%)
- **SC-006**: 첫 화면을 여는 동안 글꼴 때문에 글자가 안 보이는 시간이 없고, 화면 밀림 점수가 0.1 미만이다
- **SC-007**: 금지 목록 중 기계로 찾을 수 있는 항목을 넣은 시험 화면은 프론트 검사에서 100% 걸린다
- **SC-008**: 변경 전후 관리 화면(사용자 관리, 메뉴 관리, 관리자 설정)의 화면 비교에서 두 모드 모두 차이가 0이다

## Assumptions

- 토큰 방식(테마 파일 한 개의 CSS 변수와 테마 변수 클래스, `dark` 클래스로 바뀌는 화면 모드)은 지금 것을 그대로 쓴다. 바꾸는 것은 값, 더하는 토큰, 글꼴, 배치 상수 값이다. 다만 관리 셸을 그대로 두려고 새 값을 "사용자 화면 범위" 아래에 두는 것(FR-022)은 지금 방식에 없는 것이라 더한다. 범위를 어떻게 정하는지(문서 뿌리에 붙이는 표시 등)는 plan에서 정한다
- 기존 기준 컴포넌트(키트 web-next 골격의 `ui`·`kit`)의 구조는 그대로 두고, 모양(모서리, 단추 종류 하나 더함, 크기)만 토큰과 몇 줄로 바꾼다. 키트로 옮길 것은 키트 담당에게 알린다
- 사용자 셸의 모양과 테마는 이 스펙에서 바뀌고, 관리 셸은 배치(사이드바 한 겹)와 테마(지금 중립 회색, Geist 글꼴, 지금 모서리) 모두 그대로다(FR-022). 관리 셸에 들이는 것은 이번 범위가 아니다
- 관리 셸과 사용자 셸의 모양이 한동안 다르다. 관리자 계정은 사용자 셸 화면을 열 수 없으므로(`001-admin-menus` FR-005) 한 사람이 두 모양을 오가는 일은 거의 없다
- 게시물(글) 피드, 메신저, 크루는 아직 스펙이 없다. 이 스펙은 그것들이 쓸 자리(본문 열의 피드 항목 모양, 레일의 모임 자리, 곁줄 묶음)만 정하고 그 내용과 동작은 만들지 않는다
- 홈 화면의 내용(무엇을 피드에 보일지)은 피드 기능 스펙이 정한다. 그 전에는 지금 홈 화면 내용을 새 셸 안에 둔다
- 글꼴 세 벌은 Google Fonts에 있는 오픈 라이선스(SIL OFL) 글꼴이고, 앱이 빌드 때 받아 직접 내려 준다. 한글 글꼴의 나눠 받기 설정은 plan에서 Next 문서로 확인한다
- 제공자 로고와 색은 2026-11-28 기준 각 제공자 브랜드 지침을 따른다. 지침이 바뀌면 `design-system.md`의 그 줄만 고친다
- 다국어는 지금 한국어 하나다(`src/i18n/config.ts`). 글자 길이가 다른 언어를 더할 때 단추 폭이 늘어날 수 있게 글자 폭을 고정하지 않는다
