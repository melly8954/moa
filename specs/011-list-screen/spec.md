# Feature Specification: 업무 목록의 쪽 이동·빈 결과 (list-screen)

**Feature Branch**: `feat/011-list-screen`

**Created**: 2026-11-17

**Status**: Draft

**Input**: User description: "업무 목록(관리 셸·사용자 셸 공통)의 쪽 이동과 빈 결과 동작을 바꾼다. 기본 쪽 크기 10, 아래 줄은 건수·쪽 이동·쪽 크기 세 칸, 처음·마지막 버튼, 표 높이를 쪽 크기만큼 확보, 넘친 쪽은 마지막 쪽으로, 조건이 걸린 빈 결과에는 조건 초기화."

**출처**: psw-dev-kit web-next 골격 `web-next/v0.5.0`의 목록 부품(표, 검색 조건·쪽 상태).
키트 목록 동작(조건과 쪽을 주소에 두기, 조회를 눌러야 조건 반영, 정렬·쪽 크기를 바꾸면 1쪽)은 키트 문서가 기준이다 (원칙 III).
이 스펙은 moa가 바꾸는 것만 적는다. 바꾼 것은 나중에 키트로 옮긴다.

**범위**: 원칙의 "업무 목록"(서버 페이징과 쪽 번호) 가운데 키트 목록 표를 쓰는 모든 화면. 관리 셸과 사용자 셸 어느 쪽이든 해당한다 (자세한 대상은 Assumptions).

## 배경과 결정

접속 이력 화면을 검토하다 나온 결정이다 (2026-11-17).

- **아래 줄 배치**: 지금은 왼쪽에 건수·쪽 크기, 오른쪽에 쪽 이동이 있다. 쪽 이동을 가운데로 옮겨 세 칸(건수 | 쪽 이동 | 쪽 크기)으로 나눈다.
  - 택하지 않은 안: 건수와 쪽 크기를 검색 영역의 조회·초기화 줄로 옮기기. 검색 조건은 조회를 눌러야 반영되는데 쪽 크기는 고르는 즉시 반영되고, 건수는 입력이 아니라 결과라서 한 줄에 섞이면 헷갈린다.
  - 택하지 않은 안: 표 바로 위에 결과 줄 두기. 건수가 잘 보이지만 변경이 크다.
- **표 높이**: 빈 결과·오류·로딩일 때 표가 한 칸 높이로 줄어 쪽 이동 줄이 조회마다 위아래로 움직였다. 쪽 크기만큼 줄 높이를 확보한다.
  - 택하지 않은 안: 화면 높이 비율. 화면 크기마다 결과가 달라지고, 큰 화면에서는 빈 결과가 데이터가 찬 표보다 커진다.
  - 택하지 않은 안: 남은 높이 채우기. 셸·화면 틀까지 높이 구조를 바꿔야 하고, 표 안 스크롤로 바뀌어 업무 목록에 맞지 않는다.
- **기본 쪽 크기 10**: 선택지(10·20·50)는 그대로 두고 처음 열 때의 값만 바꾼다. 쪽 수가 늘어나므로 처음·마지막 버튼을 함께 둔다.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 쪽 이동 줄에서 원하는 쪽으로 간다 (Priority: P1)

목록을 보는 사람이 아래 줄에서 건수를 확인하고, 가운데의 쪽 이동으로 처음·이전·번호·다음·마지막 쪽으로 간다.

**Why this priority**: 기본 쪽 크기를 10으로 줄이면 쪽 수가 두 배가 된다. 처음·마지막으로 한 번에 가지 못하면 긴 목록을 다루기 어렵다.

**Independent Test**: 결과가 여러 쪽인 목록(예: 접속 이력)을 열고 아래 줄의 배치와 각 버튼을 눌러 본다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** 결과가 여러 쪽인 목록, **When** 넓은 화면에서 연다, **Then** 아래 줄 왼쪽에 총 건수(숫자 강조), 가운데에 쪽 이동, 오른쪽에 쪽 크기 선택이 있고 쪽 이동은 줄의 가운데에 놓인다
2. **US1-AC2** **Given** 결과가 12쪽이고 6쪽을 보고 있다, **When** 처음 버튼을 누른다, **Then** 1쪽으로 가고 처음·이전 버튼이 비활성이 된다
3. **US1-AC3** **Given** 결과가 12쪽이고 1쪽을 보고 있다, **When** 마지막 버튼을 누른다, **Then** 12쪽으로 가고 다음·마지막 버튼이 비활성이 된다
4. **US1-AC4** **Given** 결과가 한 쪽뿐이다, **When** 목록을 연다, **Then** 처음·이전·다음·마지막 버튼이 모두 비활성이다
5. **US1-AC5** **Given** 좁은 화면, **When** 목록을 연다, **Then** 아래 줄이 두 줄로 나뉘어 건수·쪽 크기와 쪽 이동이 겹치지 않는다

---

### User Story 2 - 결과가 없어도 표 모양과 쪽 이동 자리가 그대로다 (Priority: P1)

조건을 바꿔 가며 조회할 때 결과가 없거나, 불러오는 중이거나, 오류가 나도 표 영역 높이가 같아서 쪽 이동 줄이 같은 자리에 있다. 조건 때문에 결과가 없으면 그 자리에서 조건을 초기화한다.

**Why this priority**: 조회할 때마다 레이아웃이 튀고, 빈 결과 안내가 작아서 오류인지 빈 것인지 헷갈린다는 문제가 검토의 출발점이다.

**Independent Test**: 같은 목록에서 결과가 있는 조건과 없는 조건으로 번갈아 조회하며 쪽 이동 줄의 위치와 빈 결과 안내를 본다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 쪽 크기 10인 목록에 결과가 10건 보인다, **When** 결과가 없는 조건으로 조회한다, **Then** 표 머리는 남고, 본문은 10줄 높이를 유지한 채 그 안에 빈 결과 안내가 보이며, 쪽 이동 줄의 위치가 바뀌지 않는다
2. **US2-AC2** **Given** 마지막 쪽에 3건만 있다, **When** 그 쪽을 연다, **Then** 본문은 쪽 크기만큼의 높이를 유지한다
3. **US2-AC3** **Given** 목록을 불러오는 중이거나 조회가 실패했다, **When** 표를 본다, **Then** 본문이 쪽 크기만큼의 높이를 유지하고 그 안에 로딩 표시나 오류 안내(다시 시도)가 보인다
4. **US2-AC4** **Given** 쪽 크기 20이나 50, **When** 결과가 없다, **Then** 본문 높이는 10줄 높이까지만 확보한다
5. **US2-AC5** **Given** 검색 조건이 걸려 있고 결과가 없다, **When** 빈 결과 안내를 본다, **Then** 안내 아래에 조건 초기화 버튼이 있고, 누르면 검색 영역의 초기화와 같이 기본 조건으로 바로 다시 조회한다
6. **US2-AC6** **Given** 조건이 걸려 있지 않고 결과가 없다, **When** 빈 결과 안내를 본다, **Then** 조건 초기화 버튼이 없다

---

### User Story 3 - 처음 열면 10건씩, 없는 쪽 주소는 마지막 쪽으로 (Priority: P2)

목록을 처음 열면 10건씩 보인다. 저장해 둔 주소의 쪽이 지금 결과의 쪽 수보다 크면 빈 표 대신 마지막 쪽이 열린다.

**Why this priority**: 기본값과 예외 주소 처리다. 화면 모양(US1·US2)보다 덜 자주 부딪히지만, 넘친 쪽은 빈 표가 보이고 어느 쪽 번호도 현재 쪽으로 표시되지 않는 문제가 있다.

**Independent Test**: 주소에 쪽 크기 없이 목록을 열고, 쪽 수보다 큰 쪽 번호를 주소에 넣어 연다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 주소에 쪽 크기가 없다, **When** 목록을 연다, **Then** 10건씩 보이고 쪽 크기 선택은 "10개씩"이다
2. **US3-AC2** **Given** 쪽 크기 선택, **When** 펼친다, **Then** 10·20·50 세 가지가 있다
3. **US3-AC3** **Given** 결과가 3쪽인데 주소의 쪽이 9다, **When** 목록을 연다, **Then** 3쪽이 열리고 주소의 쪽도 3으로 바뀐다. 뒤로 가기로 9쪽 주소에 돌아가지 않는다
4. **US3-AC4** **Given** 결과가 없는데 주소의 쪽이 2 이상이다, **When** 목록을 연다, **Then** 1쪽(빈 결과)으로 간다
5. **US3-AC5** **Given** 3쪽을 보고 있다, **When** 새로고침한다, **Then** 같은 조건의 3쪽이 그대로 열린다 (지금 동작 유지)

---

### Edge Cases

- 주소의 쪽 크기가 선택지에 없는 값(예: 30)이면 기본값 10으로 연다 (지금 동작, 기본값만 바뀜).
- 쪽 크기를 20으로 정해 연 주소는 그대로 20건씩 열린다. 기본값(10)과 같으면 주소에 쪽 크기를 적지 않는다.
- 넘친 쪽으로 보내는 것은 조회 결과로 전체 쪽 수를 안 뒤다. 조회가 실패하면 보내지 않고 오류 안내를 보인다.
- 행 선택(일괄 처리)이 있는 목록에서도 표 높이와 아래 줄은 같은 규칙을 따른다.
- 정렬·쪽 크기를 바꾸면 1쪽으로 돌아간다 (지금 동작 유지).
- 쪽 번호는 지금처럼 현재 쪽을 가운데 두고 최대 5개만 보인다. 말줄임(…)과 쪽 번호 직접 입력은 두지 않는다.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 업무 목록의 기본 쪽 크기는 10이다. 쪽 크기 선택지는 10·20·50이다.
- **FR-002**: 표 아래 줄은 세 칸이다: 왼쪽 총 건수, 가운데 쪽 이동, 오른쪽 쪽 크기 선택. 쪽 이동은 양쪽 칸 내용의 길이와 관계없이 줄의 가운데에 놓인다.
- **FR-003**: 총 건수는 숫자를 강조해 보인다 (예: "총 **15**건"). 건수를 모르는 동안(로딩·오류)은 건수를 보이지 않는다.
- **FR-004**: 좁은 화면에서는 아래 줄이 두 줄로 나뉘고 요소가 겹치지 않는다.
- **FR-005**: 쪽 이동은 처음·이전·쪽 번호(최대 5개)·다음·마지막 순서다. 처음·이전은 1쪽에서, 다음·마지막은 마지막 쪽에서 비활성이다. 각 버튼은 화면 낭독기가 읽는 이름을 가진다.
- **FR-006**: 표 본문은 데이터·빈 결과·로딩·오류 모든 상태에서 쪽 크기만큼의 줄 높이(최대 10줄)를 최소 높이로 확보한다. 표 머리는 모든 상태에서 보인다.
- **FR-007**: 빈 결과이면서 검색 조건이 기본값과 다르면 빈 결과 안내 아래에 조건 초기화 버튼을 둔다. 누르면 검색 영역의 초기화와 같이 동작한다.
- **FR-008**: 주소의 쪽이 조회 결과의 전체 쪽 수보다 크면 마지막 쪽으로 보낸다. 결과가 없으면 1쪽으로 보낸다. 이때 방문 기록을 쌓지 않는다.
- **FR-009**: 이 규칙은 키트 목록 표를 쓰는 모든 업무 목록에 함께 적용된다. 화면마다 따로 고치지 않는다.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 같은 화면 크기와 쪽 크기에서 데이터 10건·마지막 쪽 일부·빈 결과·로딩·오류 상태를 오가도 쪽 이동 줄의 세로 위치가 바뀌지 않는다.
- **SC-002**: 어느 쪽에 있든 첫 쪽과 마지막 쪽까지 한 번 눌러 간다.
- **SC-003**: 전체 쪽 수보다 큰 쪽 번호의 주소를 열면 빈 표가 아니라 마지막 쪽이 열린다.
- **SC-004**: 조건 때문에 결과가 없을 때 한 번 눌러 기본 조건의 목록으로 돌아간다.
- **SC-005**: 키트 목록 표를 쓰는 모든 업무 목록이 쪽 크기를 고르지 않고 열면 10건씩 보인다.

## Assumptions

- 대상은 원칙의 업무 목록 가운데 키트 목록 표를 쓰는 화면이다 (지금: 사용자 관리, 공지 관리, 접속 이력). 구성 목록(예: 메뉴 관리 트리 표, 공통코드 트리 표), 피드 목록은 바꾸지 않는다.
- 표 대신 "이전 · 1 / 3 · 다음"만 두는 간단한 쪽 이동(사용자 공지 목록, 알림함, 역할 구성원 창)은 이번 범위가 아니다. 쪽 크기를 화면이 직접 정하고 있어 기본값 변경의 영향도 받지 않는다.
- 쪽 크기 선택지와 기본값은 모든 업무 목록이 같다. 화면별로 다르게 정할 필요는 아직 없다.
- 서버의 페이징 응답과 API는 바꾸지 않는다. 화면 동작만 바뀐다.
- 바꾼 목록 부품은 키트로 옮길 목록에 올린다 (원칙 III).
