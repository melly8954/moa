# Feature Specification: 공지사항 (notices)

**Feature Branch**: `feat/006-notices`

**Created**: 2026-11-11

**Status**: Draft

**Input**: User description: "관리자가 백오피스에서 공지를 작성·수정·삭제하고, 사용자는 공지 목록과 상세를 본다. 공지가 새로 올라오면 로그인한 사용자에게 실시간으로 알리고, 읽지 않은 새 공지가 있으면 표시(배지)한다. 공지는 사용자별 알림함에 넣지 않는다. 실시간 전달은 알림 기능(007)의 전체 알림 경로를 쓴다. 사용자용 공지 목록·상세 화면도 이번에 만들고 위치·디자인은 팀원과 맞춘다."

**출처**: moa가 만드는 기능. 본문은 키트 rich-text·file 헬퍼, 실시간 전달은 `007-notifications`(키트 websocket 헬퍼)의 전체 알림을 쓴다.

**배경** (2026-11-11 결정):

- 공지와 알림은 스펙을 나눈다. 알림은 댓글·초대·메시지·제재도 쓰는 공통 기능이고, 공지는 그 첫 사용처다
- 공지는 사용자마다 알림함에 넣지 않고 "새 공지 표시"와 전체 실시간 알림만 한다. 사용자 수만큼 알림이 쌓이지 않게 하기 위해서다
- 로그인하지 않은 사람도 공지를 본다. 공지는 가입 전에도 보는 서비스 안내다
- 본문은 서식 있는 글이고 이미지를 넣을 수 있다
- 첫 출시의 목록 관리는 상단 고정과 임시 저장이다. 게시 예약은 두지 않는다

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 공지를 쓰고 게시하고 관리한다 (Priority: P1)

관리자(또는 공지 관리 권한을 받은 운영자)가 백오피스의 공지 관리에서 공지를 쓴다. 바로 게시하거나 임시 저장해 두었다가 게시하고, 중요한 공지는 상단에 고정한다. 필요하면 고치거나 지운다.

**Why this priority**: 공지가 있어야 나머지 스토리가 의미가 있다.

**Independent Test**: 관리자로 공지를 게시·임시 저장·고정·수정·삭제하고, 그때마다 사용자 쪽 목록과 상세에 반영되는지 본다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** 관리자가 로그인했다, **When** 공지 관리에서 제목과 본문을 넣어 공지를 게시한다, **Then** 사용자 공지 목록에서 고정 공지 다음 맨 위에 그 공지가 보인다
2. **US1-AC2** **Given** 관리자가 공지를 쓰는 중이다, **When** 임시 저장한다, **Then** 공지 관리 목록에는 임시 저장으로 보이고, 사용자 목록·상세에는 보이지 않는다
3. **US1-AC3** **Given** 임시 저장한 공지가 있다, **When** 관리자가 그 공지를 게시한다, **Then** 그 순간 사용자 공지 목록에 새 공지로 보인다
4. **US1-AC4** **Given** 게시한 공지가 있다, **When** 관리자가 상단에 고정한다, **Then** 사용자 공지 목록에서 고정하지 않은 공지보다 위에 보인다. 고정을 풀면 게시 순서대로 돌아간다
5. **US1-AC5** **Given** 게시한 공지가 있다, **When** 관리자가 제목이나 본문을 고친다, **Then** 사용자에게 고친 내용이 보인다
6. **US1-AC6** **Given** 게시한 공지가 있다, **When** 관리자가 지운다, **Then** 사용자 목록에서 빠지고, 상세 주소로 들어가면 없는 공지라는 안내가 보인다
7. **US1-AC7** **Given** 공지 관리 권한이 없는 운영자다, **When** 공지를 쓰거나 고치려 한다, **Then** 권한이 없다는 안내와 함께 막힌다
8. **US1-AC8** **Given** 관리자가 공지를 쓴다, **When** 본문에 스크립트 같은 허용하지 않은 내용을 넣어 저장한다, **Then** 그 내용은 걸러져 저장되고 사용자 화면에서 실행되지 않는다

---

### User Story 2 - 사용자가 공지를 본다 (Priority: P1)

사용자(로그인하지 않은 사람 포함)가 공지 목록에서 공지를 찾아 상세를 읽는다.

**Why this priority**: 공지는 사용자가 읽어야 목적을 이룬다.

**Independent Test**: 고정 공지와 일반 공지를 게시한 뒤, 로그인한 사용자와 로그인하지 않은 사람으로 목록과 상세를 연다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 고정 공지와 일반 공지가 있다, **When** 사용자가 공지 목록을 연다, **Then** 고정 공지가 먼저, 그다음 일반 공지가 게시한 최신순으로 제목, 게시 날짜, 고정 여부와 함께 보인다
2. **US2-AC2** **Given** 공지 목록이다, **When** 사용자가 공지 하나를 연다, **Then** 제목, 게시 날짜, 서식과 이미지를 포함한 본문이 보인다
3. **US2-AC3** **Given** 로그인하지 않았다, **When** 공지 목록이나 상세에 들어간다, **Then** 로그인한 사용자와 같은 목록과 상세가 보인다

---

### User Story 3 - 읽지 않은 새 공지를 알아챈다 (Priority: P2)

로그인한 사용자는 공지 목록을 마지막으로 본 뒤 새 공지가 게시됐으면 화면에서 표시(배지)로 알아챈다.

**Why this priority**: 공지를 찾아 들어가지 않는 사용자도 새 공지를 놓치지 않게 한다. 목록·상세만으로도 공지는 쓸 수 있어 P2다.

**Independent Test**: 사용자가 목록을 본 뒤 공지를 하나 게시하고, 표시가 생기는지와 목록을 다시 열면 사라지는지 본다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 로그인한 사용자가 공지 목록을 본 뒤 새 공지가 게시됐다, **When** 사용자가 화면을 연다, **Then** 새 공지가 있다는 표시가 보인다
2. **US3-AC2** **Given** 새 공지 표시가 있다, **When** 사용자가 공지 목록을 연다, **Then** 표시가 사라진다
3. **US3-AC3** **Given** 로그인한 사용자가 공지 목록을 본 뒤 공지가 임시 저장만 됐다, **When** 화면을 연다, **Then** 표시가 없다

---

### User Story 4 - 공지가 게시되면 바로 알린다 (Priority: P3)

화면을 보고 있는 로그인 사용자는 공지가 게시되는 순간 새로고침 없이 알림을 받는다.

**Why this priority**: 새 공지 표시(US3)만으로도 다음에 화면을 열 때 알 수 있다. 실시간 전달은 알림 기능(007)의 전체 알림이 있어야 해서 그 뒤에 붙는다.

**Independent Test**: 사용자 화면을 열어 둔 채 관리자가 공지를 게시한다.

**Acceptance Scenarios**:

1. **US4-AC1** **Given** 로그인한 사용자가 화면을 보고 있다, **When** 관리자가 공지를 게시한다, **Then** 새로고침하지 않아도 공지 제목이 담긴 알림이 뜨고 새 공지 표시가 생긴다

---

### Edge Cases

- 공지 목록을 한 번도 보지 않은 로그인 사용자: 게시된 공지가 하나라도 있으면 새 공지 표시가 보인다
- 공지를 고치거나 지울 때, 고정하거나 풀 때: 실시간 알림을 보내지 않고 새 공지 표시도 다시 생기지 않는다 (게시할 때만 "새 공지")
- 게시한 공지는 임시 저장으로 되돌리지 않는다. 내리려면 지운다
- 지운 공지만 있어 새 공지가 없어진 경우: 표시가 사라진다
- 게시된 공지가 하나도 없을 때: 목록에 빈 결과 안내가 보이고 표시는 없다
- 고정 공지가 여러 개일 때: 고정 공지끼리는 게시한 최신순이다
- 본문에서 뺀 이미지: 공지에서 더 쓰이지 않는 이미지는 정리된다 (키트 rich-text 동작)
- 관리자·운영자 계정도 사용자 화면에서 공지를 볼 수 있다. 조회는 회원 활동이 아니다 (`specs/README.md` 맞춰야 할 경계)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 공지 관리 권한을 가진 사용자는 공지를 쓰고, 임시 저장하고, 게시하고, 고치고, 상단에 고정하거나 풀고, 지울 수 있어야 한다(MUST). 관리자는 이 권한을 가진다
- **FR-002**: 백오피스 사이드바 최상위에 "공지 관리" 메뉴를 공지 관리 권한으로 더한다(MUST). 위치는 역할 관리 다음(6번째)이다. `001-admin-menus` FR-001 표와 수용 시나리오(메뉴 5개 → 6개)를 함께 고친다 (`001-admin-menus` FR-004)
- **FR-003**: 공지는 제목과 본문을 가진다(MUST). 본문은 서식 있는 글(굵게, 목록, 링크 등)이고 이미지를 넣을 수 있다. 허용한 서식만 남기고 나머지는 걸러 저장한다
- **FR-004**: 공지는 임시 저장과 게시 두 상태를 가진다(MUST). 임시 저장 공지는 공지 관리에만 보이고, 게시하면 그 시각이 게시 시각이 된다. 게시 예약은 두지 않는다
- **FR-005**: 사용자 공지 목록은 게시한 공지만, 고정 공지 먼저, 그다음 게시 최신순으로 보인다(MUST). 고정 공지끼리도 게시 최신순이다
- **FR-006**: 로그인하지 않은 사람도 사용자 공지 목록과 상세를 볼 수 있어야 한다(MUST)
- **FR-007**: 지운 공지는 사용자 목록과 상세에서 보이지 않아야 한다(MUST). 지운 공지를 되살리는 기능은 두지 않는다
- **FR-008**: 로그인한 사용자마다 공지 목록을 마지막으로 연 시각을 기억하고, 그 뒤에 게시된 공지가 있으면 새 공지 표시를 보여야 한다(MUST)
- **FR-009**: 공지를 게시하면 로그인해 화면을 보고 있는 모든 사용자에게 알림 기능(007)의 전체 알림으로 공지 제목을 실시간으로 보내야 한다(MUST). 사용자별 알림함에는 넣지 않는다
- **FR-010**: 사용자 공지 화면(목록·상세)의 위치와 디자인은 사용자 쪽 담당과 맞춘다 (`specs/README.md` 맞춰야 할 경계)

### Key Entities *(include if feature involves data)*

- **공지**: 관리자가 쓴 글. 제목, 본문(서식·이미지), 상태(임시 저장·게시), 상단 고정 여부, 게시 시각, 쓴 사람, 고친 사람과 시각을 가진다. 지우면 사용자에게 보이지 않는다
- **공지 이미지**: 공지 본문에 넣은 이미지. 본문에서 빠지면 정리된다
- **공지 확인 기록**: 로그인한 사용자가 공지 목록을 마지막으로 연 시각. 사용자마다 하나다
- **공지 관리 권한**: 공지를 다룰 수 있는 자격. 역할에 묶어 운영자에게 줄 수 있다 (`003-admin-roles`)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자는 이미지 하나가 든 공지를 2분 안에 써서 게시할 수 있다
- **SC-002**: 공지를 게시한 뒤 사용자가 목록을 새로 열면 그 공지가 바로 보인다
- **SC-003**: 화면을 보고 있는 로그인 사용자는 공지가 게시된 뒤 5초 안에 알림을 받는다
- **SC-004**: 새 공지가 있는 로그인 사용자는 화면을 열자마자 표시로 알아챌 수 있다
- **SC-005**: 공지 본문을 통한 스크립트 실행은 0건이다
- **SC-006**: 수용 시나리오(US1~US4) 전부가 자동 테스트로 확인된다 (원칙 II)

## Assumptions

- 실시간 전달(US4, FR-009)은 `007-notifications`가 전체 알림 경로를 만든 뒤에 붙인다. 007 전에도 US1~US3은 단독으로 쓸 수 있다
- 키트 websocket 헬퍼는 007에서 적용하고, 적용 전에 메신저 담당 팀원에게 연결 경로와 구독 경로 규칙을 알린다
- 본문 서식과 이미지는 키트 rich-text·file 헬퍼로 한다. 허용 서식, 이미지 크기·형식 제한, 쓰이지 않는 이미지 정리는 키트 기본을 따른다. 두 헬퍼는 사용자 쪽도 쓸 수 있어 적용 전에 팀원에게 알린다
- 관리자 공지 관리 화면은 키트 목록 화면 모양(머리, 검색, 표)을 따른다
- 공지 수정·삭제 이력은 따로 두지 않는다. 키트 감사 필드(쓴 사람·고친 사람·시각)로 충분하다
- 공지를 메일·문자로 보내지 않는다
- 공지 관리 권한을 쓰는 운영자의 회원 활동 제한은 `specs/README.md` 맞춰야 할 경계를 따른다
