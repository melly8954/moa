# Feature Specification: 관리 메뉴와 접근 (admin-menus)

**Feature Branch**: `feat/001-admin-menus`

**Created**: 2026-11-07

**Status**: Draft

**Input**: User description: "백오피스의 관리 메뉴 구성과 순서를 정하고, 권한이 없는 사용자는 관리 메뉴를 보지 못하고 관리 화면에 들어오지 못하게 한다."

**출처**: psw-dev-kit springboot menu 헬퍼와 admin 프리셋의 메뉴 시드. 태그 `springboot/v0.3.1`, 화면은 `web-next/v0.3.0`.
키트 동작(메뉴 트리 관리, 내 메뉴, 권한 판정)은 키트 문서와 키트 수용 테스트가 기준이다 (원칙 III).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 관리 메뉴를 본다 (Priority: P1)

관리자가 백오피스에 들어가면 관리 메뉴 6개를 사이드바의 "운영"·"설정" 묶음 아래에서 정해진 순서로 보고, 각 화면을 열 수 있다.

**Why this priority**: 백오피스의 첫 화면이다. 다른 관리 기능을 얹을 자리다.

**Independent Test**: 관리자로 로그인해 백오피스에 들어가 메뉴와 각 화면을 확인한다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** 관리자가 로그인했다, **When** 백오피스에 들어간다, **Then** 첫 관리 메뉴(사용자 관리) 화면이 열리고, 사이드바에 "운영" 묶음(사용자 관리, 공지 관리, 접속 이력)과 "설정" 묶음(역할 관리, 메뉴 관리, 공통코드)만 이 순서로 보인다(홈과 사용자 화면 메뉴는 없다)
2. **US1-AC2** **Given** 관리자가 로그인했다, **When** 관리 메뉴 6개를 하나씩 연다, **Then** 모든 화면의 목록이 보인다
3. **US1-AC3** **Given** 관리자가 넓은 폭에서 관리 화면을 본다, **When** 사이드바 맨 위 로고 옆 접기 단추를 누르고 다시 로고 자리의 펼치기 단추를 누른다, **Then** 본문 위에 머리 줄이 없고, 사이드바가 아이콘만 남게 접혔다가 다시 펼쳐진다

---

### User Story 2 - 권한이 없는 사용자는 백오피스에 들어오지 못한다 (Priority: P1)

일반 회원과 로그인하지 않은 사용자는 관리 메뉴를 보지 못하고, 관리 화면 주소로 직접 들어와도 막힌다.

**Why this priority**: 백오피스를 여는 순간부터 지켜져야 하는 보안 경계다.

**Independent Test**: 일반 회원과 비로그인 상태로 메뉴와 관리 화면 주소를 확인한다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 일반 회원이 로그인했다, **When** 메뉴를 본다, **Then** 사용자 셸에 있고 관리 메뉴가 보이지 않는다
2. **US2-AC2** **Given** 일반 회원이 로그인했다, **When** 관리 화면 주소로 직접 들어가거나 관리 기능을 쓰려 한다, **Then** 권한이 없다는 안내와 함께 막힌다
3. **US2-AC3** **Given** 로그인하지 않았다, **When** 관리 화면 주소로 들어간다, **Then** 로그인하라는 안내와 함께 막힌다
4. **US2-AC4** **Given** 일반 회원이다, **When** 로그인한다, **Then** 사용자 셸의 첫 화면이 열리고 사이드바에 홈, 공지가 보인다

---

### User Story 3 - 관리자가 사용자 화면 메뉴도 메뉴 관리에서 다룬다 (Priority: P2)

관리자는 메뉴 관리에서 메뉴마다 대상(관리자, 사용자)을 정하고, 사용자 셸에 보일 메뉴를 코드 수정 없이 더하고 끄고 순서를 바꾼다.
사용자 메뉴는 공개 범위(비회원 포함, 회원만)로 누구에게 보일지 정한다.

**Why this priority**: 사용자 화면 메뉴가 늘어날 때 배포 없이 다룰 수 있게 한다. 지금 사용자 메뉴는 홈·공지 둘이라 P1 셸 나누기보다 뒤다.

**Independent Test**: 메뉴 관리에서 사용자 메뉴를 하나 더하고 끈 뒤, 일반 회원과 로그인하지 않은 사람의 사용자 셸 사이드바를 본다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 관리자가 메뉴 관리를 연다, **When** 메뉴 목록을 본다, **Then** 관리 메뉴와 사용자 메뉴(홈, 공지)가 대상으로 나뉘어 보인다
2. **US3-AC2** **Given** 관리자가 대상이 사용자인 메뉴를 공개 범위 "비회원 포함"으로 더했다, **When** 일반 회원이나 로그인하지 않은 사람이 사용자 셸을 연다, **Then** 사이드바에 그 메뉴가 보이고 관리 셸에는 보이지 않는다
3. **US3-AC3** **Given** 사용자 메뉴가 있다, **When** 관리자가 그 메뉴를 끈다, **Then** 사용자 셸 사이드바에서 빠진다
4. **US3-AC4** **Given** 관리자가 대상이 관리자인 메뉴를 더했다, **When** 일반 회원이 메뉴를 본다, **Then** 그 메뉴가 보이지 않는다
5. **US3-AC5** **Given** 관리자가 대상이 사용자인 메뉴를 공개 범위 "회원만"으로 더했다, **When** 로그인하지 않은 사람과 일반 회원이 사용자 셸을 연다, **Then** 로그인하지 않은 사람의 사이드바에는 없고 일반 회원의 사이드바에는 보인다

---

### User Story 4 - 관리자는 등록된 프로그램을 골라 메뉴를 만든다 (Priority: P2)

관리자는 메뉴를 만들거나 고칠 때 코드에 등록된 프로그램(화면)을 선택 상자에서 고른다. 프로그램 목록을 따로 보여 주는 화면은 없다.
경로와 권한 키를 직접 입력하지 않는다. 관리 메뉴의 권한은 고른 프로그램을 따른다.

**Why this priority**: 경로와 권한 키를 직접 입력하는 방식은 키 이름을 아는 사람만 쓸 수 있고, 잘못 넣기 쉽다. 메뉴를 다룰 일이 생기기 전에 바로잡는다.

**Independent Test**: 메뉴 관리에서 프로그램을 골라 관리 메뉴와 사용자 메뉴를 하나씩 만든다.

**Acceptance Scenarios**:

1. **US4-AC1** **Given** 관리자가 메뉴 드로어에서 프로그램 선택 상자를 연다, **When** 프로그램을 본다, **Then** 등록된 프로그램이 이름과 경로로 보이고, 고르면 필요한 권한(관리 프로그램) 또는 로그인 필요 여부(사용자 프로그램)가 함께 보인다. 프로그램을 더하거나 고치는 곳은 없다
2. **US4-AC2** **Given** 관리자가 관리 메뉴를 만든다, **When** 프로그램을 고른다, **Then** 대상이 관리자인 프로그램만 고를 수 있고, 경로와 필요한 권한은 고른 프로그램의 값으로 보이며 입력 칸이 없다
3. **US4-AC3** **Given** 관리자가 사용자 메뉴를 만든다, **When** 로그인이 필요한 프로그램을 고른다, **Then** 공개 범위는 "회원만"만 고를 수 있다
4. **US4-AC4** **Given** 관리자가 프로그램 "코드 관리"를 고른 관리 메뉴를 묶음 메뉴 아래에 더했다, **When** 코드 관리 권한만 받은 운영자가 관리 셸을 연다, **Then** 묶음 메뉴와 그 아래 메뉴가 보이고 누르면 코드 관리 화면이 열린다
5. **US4-AC5** **Given** 관리자가 프로그램 없이 묶음 메뉴를 만든다, **When** 저장한다, **Then** 저장되고, 보이는 하위 메뉴가 없으면 사이드바에 보이지 않는다

---

### User Story 5 - 관리자는 메뉴 트리를 한 화면에서 고르고 끌어 정리한다 (Priority: P2)

관리자는 메뉴 관리에서 대상별 메뉴 트리 전체를 한 표로 보고, 끌어서 순서와 묶음을 바꾸고, 체크박스로 여러 메뉴를 한꺼번에 켜고 끄고 옮기고 지운다.
메뉴 하나를 고치려면 이름을 눌러 오른쪽에서 열리는 드로어에서 고친다. 행마다 붙은 단추는 없다.

**Why this priority**: 메뉴가 묶음으로 나뉘면 행마다 위·아래·수정·삭제 단추를 두는 방식으로는 묶음 사이를 옮기기 어렵고 표가 단추로 가득 찬다.

**Independent Test**: 메뉴 관리에서 메뉴를 끌어 다른 묶음으로 옮기고, 여러 메뉴를 골라 끈 뒤, 사이드바를 확인한다.

**Acceptance Scenarios**:

1. **US5-AC1** **Given** 관리자가 메뉴 관리를 연다, **When** 관리자 메뉴 탭을 본다, **Then** 묶음 메뉴 아래 하위 메뉴가 들여쓰기된 트리 표가 쪽 나눔 없이 전체로 보이고, 행마다 체크박스·끌기 손잡이·이름·보이는 사람·사용 여부만 있고 단추는 없다
2. **US5-AC2** **Given** 같은 화면이다, **When** 메뉴 이름을 누른다, **Then** 오른쪽 드로어에 이름·아이콘·종류·프로그램·공개 범위·사용 여부가 열리고, 고쳐 저장하면 표와 사이드바에 반영된다
3. **US5-AC3** **Given** 같은 화면이다, **When** "접속 이력"을 끌어 "설정" 묶음 안으로 옮긴다(또는 키보드로 같은 일을 한다), **Then** 저장되고 다음 조회부터 사이드바의 "설정" 아래에 보인다
4. **US5-AC4** **Given** 같은 화면이다, **When** 메뉴 둘을 체크하고 "사용 안 함"을 누른다, **Then** 두 메뉴가 모두 꺼지고 사이드바에서 빠진다. "묶음으로 옮기기"는 고른 메뉴를 고른 묶음 아래로, "삭제"는 확인을 받은 뒤 지운다
5. **US5-AC5** **Given** 하위 메뉴가 있는 묶음과 다른 메뉴를 함께 체크했다, **When** "삭제"를 누른다, **Then** 아무것도 지워지지 않고 하위 메뉴가 있는 묶음 때문이라는 안내가 보인다

---

### Edge Cases

- 관리 메뉴 중 일부 권한만 가진 사용자: 권한이 있는 메뉴만 최상위에 보인다. 하나도 없으면 관리 메뉴가 하나도 보이지 않는다 (키트 메뉴 동작)
- 관리자가 메뉴 관리에서 메뉴를 끄거나 순서를 바꾸면: 다음 조회부터 바뀐 대로 보인다 (키트 메뉴 동작). 이 스펙의 순서는 처음 배포할 때의 구성이다
- 관리자·운영자가 사용자 화면 주소(공지 등)로 들어가면: 사용자 셸로 보인다. 관리 셸에서 사용자 화면으로 가는 메뉴는 두지 않는다
- 운영자의 관리 권한을 모두 빼면: 다음 로그인부터 관리 메뉴가 없는 사용자로 사용자 셸 첫 화면에 간다
- 메뉴 관리에서 메뉴의 대상을 바꾸면: 다음 조회부터 다른 셸에 보인다. 하위 메뉴가 있는 메뉴는 대상을 바꿀 수 없다(하위 메뉴의 프로그램이 원래 대상이다). 하위 메뉴를 먼저 옮기거나 지운다
- 사용자 메뉴를 모두 끄면: 사용자 셸 사이드바에 메뉴가 없다. 화면 주소로 직접 들어가는 것은 막지 않는다
- 메뉴의 공개 범위와 권한은 사이드바에 보일지만 정한다: 화면과 API에 들어올 수 있는지는 코드가 정한다(API의 권한·공개 표시, 로그인이 필요한 화면 묶음). 메뉴를 숨겨도 주소로 들어가는 것은 그대로다
- 같은 프로그램을 여러 메뉴에 걸면: 모두 같은 화면으로 가고, 보이는 조건(권한, 공개 범위)도 같은 규칙을 따른다
- 코드에서 프로그램이 빠지면: 그 프로그램을 가리키던 메뉴는 사이드바에 보이지 않고, 메뉴 관리에는 "없는 프로그램"으로 표시되어 관리자가 다른 프로그램으로 바꾸거나 지운다
- 메뉴의 대상을 바꾸면: 대상이 다른 프로그램을 가리키는 메뉴는 바꿀 수 없다. 프로그램을 먼저 바꾼다. 하위 메뉴를 대상이 다른 묶음 메뉴 아래로 옮기는 것도 같은 이유로 막는다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 처음 배포할 때 관리 메뉴는 아래 표의 묶음·순서·프로그램으로 구성되어야 한다(MUST). 관리 셸 사이드바에는 관리 메뉴만 둔다(홈과 사용자 화면 메뉴를 두지 않는다)
  - "운영"은 매일 쓰는 화면, "설정"은 가끔 정하는 화면이다

  | 묶음 | 순서 | 메뉴 | 프로그램 (FR-008) | 스펙 |
  |---|---|---|---|---|
  | 운영 | 1 | 사용자 관리 | 사용자 관리 | `002-admin-users` |
  | 운영 | 2 | 공지 관리 | 공지 관리 | `006-notices` |
  | 운영 | 3 | 접속 이력 | 접속 이력 | `005-admin-login-history` |
  | 설정 | 1 | 역할 관리 | 역할 관리 | `003-admin-roles` |
  | 설정 | 2 | 메뉴 관리 | 메뉴 관리 | 이 스펙 |
  | 설정 | 3 | 공통코드 | 공통코드 | `004-admin-codes` |

- **FR-002**: 관리 메뉴는 그 메뉴가 가리키는 프로그램의 권한을 가진 사용자에게만 보여야 한다(MUST). 관리자는 모든 권한을 갖는다. 프로그램이 없는 묶음 메뉴는 보이는 하위 메뉴가 하나라도 있을 때만 보인다
- **FR-003**: 권한이 없는 사용자가 관리 화면이나 관리 기능에 접근하면 막아야 한다(MUST). 로그인하지 않았으면 로그인 안내, 로그인했으면 권한 없음 안내를 보인다
- **FR-004**: moa 관리 기능(신고, 제재, 게임, 복구)은 기능이 정해질 때까지 메뉴에 넣지 않는다. 넣을 때는 그 기능의 스펙에 프로그램(FR-008)과 메뉴 위치를 적고 FR-001·FR-008 표에 더한다
- **FR-005**: 화면은 관리 셸과 사용자 셸로 나뉘어야 한다(MUST). 두 셸은 같은 사이드바 모양(사이드바, 계정 줄, 좁은 폭의 서랍)을 쓰고 메뉴만 다르다
  - 관리 셸: 관리 화면(`/admin/...`). 사이드바에는 대상이 "관리자"인 메뉴(관리 메뉴, FR-001)만 있다. 관리 메뉴가 하나라도 있는 사용자(관리자, 권한을 받은 운영자)만 쓴다
  - 사용자 셸: 사용자 화면(첫 화면, 공지 목록·상세). 사이드바에는 대상이 "사용자"인 메뉴(사용자 메뉴, FR-007)만 있다. 로그인하지 않아도 열 수 있는 화면(공지)은 로그인하지 않은 채로도 이 셸에서 보이고, 계정 줄에는 로그인 단추가 보인다
  - 계정 화면(알림, 설정, 비밀번호 변경)은 관리 메뉴가 있는 사용자에게는 관리 셸, 없는 사용자에게는 사용자 셸 안에서 보인다
  - 두 셸의 계정 메뉴는 설정, 비밀번호 변경, 로그아웃 순서다
  - 넓은 폭에서는 본문 위에 머리 줄을 두지 않는다. 사이드바 접기 단추는 사이드바 맨 위 로고 옆에 둔다. 아이콘만 남게 접었을 때는 로고 자리가 펼치기 단추가 된다
  - 사이드바가 서랍이 되는 좁은 폭에서는 머리 줄에 서랍 단추, 사이트 이름, 벨(로그인했을 때) 또는 로그인 단추(로그인하지 않았을 때)를 둔다. 화면 이름은 머리 줄에 두지 않는다(화면 제목이 본문에 있다)
- **FR-006**: 로그인한 뒤 첫 화면은 관리 메뉴가 있는 사용자는 볼 수 있는 첫 관리 메뉴의 화면, 없는 사용자는 사용자 셸의 첫 화면(`/`)이어야 한다(MUST). 로그인 화면이 돌아갈 주소를 받았으면 그 주소가 먼저다
- **FR-007**: 메뉴는 대상(관리자, 사용자)을 가져야 한다(MUST). 관리자는 메뉴 관리에서 관리 메뉴와 사용자 메뉴를 함께 만들고, 고치고, 끄고, 순서를 바꾼다. 하위 메뉴는 부모 메뉴의 대상을 따른다
  - 사용자 메뉴는 권한을 쓰지 않고 공개 범위를 가진다(MUST). "비회원 포함"은 로그인하지 않은 사람을 포함한 모두에게, "회원만"은 로그인한 사용자에게만 보인다. 로그인이 필요한 프로그램(FR-008)을 가리키는 메뉴는 "회원만"이어야 한다
  - 처음 배포할 때 사용자 메뉴는 묶음 없이 아래 표의 순서다

  | 순서 | 메뉴 | 프로그램 (FR-008) | 공개 범위 | 스펙 |
  |---|---|---|---|---|
  | 1 | 홈 | 홈 | 비회원 포함 | 이 스펙 |
  | 2 | 공지 | 공지 | 비회원 포함 | `006-notices` |

  - 사용자 메뉴를 더하는 것은 사용자 쪽 기능의 스펙이 정한다 (`specs/README.md` 맞춰야 할 경계)
- **FR-008**: 메뉴에 걸 수 있는 화면은 프로그램으로 코드에 등록되어야 한다(MUST). 관리자는 메뉴 드로어의 선택 상자에서 프로그램을 고르기만 하고 더하거나 고치지 않는다. 프로그램 목록만 보여 주는 화면은 두지 않는다
  - 프로그램은 이름, 경로, 대상(관리자·사용자)을 가진다. 관리 프로그램은 필요한 권한을 하나 가진다(MUST). 사용자 프로그램은 로그인 필요 여부를 가진다
  - 프로그램의 권한과 로그인 필요 여부는 그 화면이 쓰는 API가 실제로 막는 조건과 같아야 한다. 새 화면을 만드는 기능은 그 스펙에 프로그램(이름, 경로, 권한 또는 로그인 필요 여부)을 적는다
  - 메뉴로 열지 않는 화면(공지 상세, 계정 화면 등)은 프로그램으로 등록하지 않는다
  - 처음 등록하는 프로그램은 아래 표다

  | 프로그램 | 경로 | 대상 | 필요한 권한 / 로그인 | 스펙 |
  |---|---|---|---|---|
  | 사용자 관리 | `/admin/users` | 관리자 | 사용자 관리 | `002-admin-users` |
  | 메뉴 관리 | `/admin/menus` | 관리자 | 메뉴 관리 | 이 스펙 |
  | 공통코드 | `/admin/codes` | 관리자 | 공통코드 관리 | `004-admin-codes` |
  | 접속 이력 | `/admin/login-histories` | 관리자 | 접속 이력 조회 | `005-admin-login-history` |
  | 역할 관리 | `/admin/roles` | 관리자 | 역할 관리 | `003-admin-roles` |
  | 공지 관리 | `/admin/notices` | 관리자 | 공지 관리 | `006-notices` |
  | 홈 | `/` | 사용자 | 로그인 필요 없음 | 이 스펙 |
  | 공지 | `/notices` | 사용자 | 로그인 필요 없음 | `006-notices` |

- **FR-009**: 메뉴는 프로그램 하나를 가리키는 화면 메뉴이거나, 프로그램 없이 하위 메뉴를 묶는 묶음 메뉴여야 한다(MUST). 메뉴 관리에서 경로와 권한 키를 직접 입력하지 않는다
  - 화면 메뉴는 메뉴의 대상과 같은 대상의 프로그램만 가리킨다
  - 메뉴 관리 화면은 권한 키를 몰라도 쓸 수 있어야 한다. 메뉴 관리 권한만 받은 운영자도 선택 상자에서 프로그램 이름·경로와 그 권한 이름을 본다
- **FR-010**: 메뉴 관리의 메뉴 표는 구성 목록이다(원칙 "목록"). 대상 탭마다 트리 전체를 쪽 나눔 없이 보이고 화면 안에서 스크롤한다. 대상마다 메뉴는 200개를 넘지 않는다(MUST)
  - 순서와 부모는 끌기 손잡이로 바꾼다. 같은 일을 키보드로도 할 수 있어야 한다(MUST). 행마다 위·아래·수정·삭제 단추를 두지 않는다
  - 메뉴 하나는 이름을 눌러 오른쪽 드로어에서 고친다. 새 메뉴도 같은 드로어에서 만든다
  - 체크박스로 여러 메뉴를 골라 사용·사용 안 함, 묶음으로 옮기기, 삭제를 한꺼번에 한다. 한꺼번에 하는 일은 하나라도 틀리면 아무것도 바꾸지 않고(MUST) 이유를 보인다. 삭제는 확인을 받는다
  - 끌기와 일괄 처리도 FR-009의 규칙(묶음은 1단계만, 대상이 다른 부모 아래로 옮기지 않음 등)을 그대로 따른다
- **FR-011**: 관리 화면은 머리 설명에 그 화면이 정하는 것과 앞뒤 화면(예: 메뉴 관리 → 역할 관리)을 한두 줄로 알려야 한다(MUST). 앞뒤 화면은 링크로 둔다. 문구는 각 화면의 스펙이 정한다
  - 메뉴 관리: "사이드바에 보일 메뉴와 묶음, 순서를 정해요. 누가 어떤 관리 메뉴를 쓰는지는 역할 관리에서 정해요."

### Key Entities *(include if feature involves data)*

- **셸**: 화면을 감싸는 틀(사이드바, 계정 줄, 머리). 관리 셸과 사용자 셸이 있다
- **프로그램**: 메뉴에 걸 수 있는 화면. 코드에 등록한다. 이름, 경로, 대상, 필요한 권한(관리 프로그램) 또는 로그인 필요 여부(사용자 프로그램)를 가진다
- **메뉴**: 셸 사이드바의 항목. 이름, 아이콘, 순서, 대상(관리자·사용자), 켜짐, 프로그램(화면 메뉴) 또는 하위 메뉴(묶음 메뉴)를 가진다
  - **관리 메뉴**: 대상이 관리자인 메뉴. 관리 셸에 보인다. 처음 배포할 때는 "운영"·"설정" 묶음 아래에 둔다(FR-001). 보이는 조건은 프로그램의 권한이다
  - **사용자 메뉴**: 대상이 사용자인 메뉴. 사용자 셸에 보인다. 공개 범위(비회원 포함, 회원만)를 가진다
- **권한**: 관리 기능 하나를 쓸 수 있는 자격. 관리 프로그램마다 하나씩 있고 코드에 등록한다. 계정에는 시스템 역할(`USER`, `ADMIN`)로, 운영자에게는 역할 관리의 업무 역할(`003-admin-roles`)로 준다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 관리자는 로그인 직후 추가 설정 없이 관리 메뉴 6개를 쓸 수 있다
- **SC-002**: 일반 회원과 로그인하지 않은 사용자의 관리 화면·관리 기능 접근은 100% 막힌다
- **SC-003**: 수용 시나리오(US1~US5) 전부가 자동 테스트로 확인된다 (원칙 II)
- **SC-004**: 관리자 사이드바에는 관리 메뉴 말고 다른 항목이 없다
- **SC-005**: 관리자는 코드를 바꾸지 않고 메뉴 관리에서 사용자 셸 메뉴를 더하거나 끌 수 있다
- **SC-006**: 관리자는 권한 키와 화면 경로를 몰라도, 안내 문서 없이 메뉴 관리 화면만으로 메뉴를 만들 수 있다
- **SC-007**: 관리자는 메뉴 하나를 다른 묶음으로 옮기는 일을 한 번의 끌기로 마친다

## Assumptions

- 관리자 화면(프론트)은 프론트 키트(web-next admin 프리셋)가 만드는 admin 화면을 쓴다
- 키트 admin 프리셋의 기본 시드는 관리 메뉴를 "관리" 그룹 아래에 둔다. moa는 그 그룹을 없애고 메뉴를 최상위로 옮긴다. 순서와 권한은 키트 시드와 같다
  - 배경 (2026-11-14): 백오피스 메뉴가 모두 관리 기능이라 "관리" 한 단계로 묶는 의미가 없다
  - 2026-11-15에 "운영"·"설정" 두 묶음으로 바꿨다 (아래 "관리 화면 정리")
- 관리 셸과 사용자 셸을 나눈다 (2026-11-15 결정, FR-005·FR-006)
  - 배경: 한 사이드바에 홈·공지(사용자 화면)와 관리 메뉴가 섞여, 관리자 사이드바가 일반적인 관리 화면과 달랐다. 공지 화면은 셸 없이 머리만 있어 다른 화면과 구성이 달랐다
  - 두 셸은 같은 사이드바 모양을 쓰고 메뉴만 다르다. 사용자 셸의 메뉴와 모양은 사용자 쪽 담당이 더하거나 바꾼다 (`specs/README.md` 맞춰야 할 경계)
- 넓은 폭에서 머리 줄을 없앤다 (2026-11-15 결정, FR-005)
  - 배경: 머리 줄에는 접기 단추와 메뉴 이름만 있었고, 메뉴 이름은 바로 아래 화면 제목과 같았다. 상위 메뉴도 보이지 않아 위치 표시 구실도 하지 않았다
  - 알림은 메뉴로 따로 두지 않는다. 계정 줄 벨과 그 목록의 "전체 보기"가 알림 화면으로 가는 길이다 (`007-notifications` FR-005)
  - 키트 `SidebarShell`을 고치므로 moa에서 먼저 하고 키트로 옮긴다 (원칙 III)
- 메뉴에 대상(관리자·사용자)을 둔다 (2026-11-15 결정, FR-007)
  - 배경: 사용자 셸 메뉴(홈·공지)가 코드에 고정돼 메뉴 관리에서 보이지 않았다. 권한은 계정의 시스템 역할(USER·ADMIN)로 나누는 느낌을 원했고, 대상이 그 구분을 맡는다. 세부 권한(운영자용)은 선택으로 남긴다
  - 버린 안: 세부 권한을 없애고 시스템 역할만 남기기. 003 역할 관리와 키트 rbac 헬퍼를 걷어내야 해 범위가 크다
  - 키트 menu 헬퍼를 고치므로 moa에서 먼저 하고 키트로 옮긴다 (원칙 III, 사용자 결정)
- 메뉴는 등록된 프로그램을 골라 만들고, 사용자 메뉴는 권한 대신 공개 범위를 쓴다 (2026-11-15 결정, FR-002·FR-007~FR-009)
  - 배경: 메뉴 관리에서 경로와 권한 키를 직접 입력해야 해, 키 이름을 모르면 메뉴를 만들 수 없었다. 권한 칸을 비웠을 때의 뜻도 대상마다 달라(관리 메뉴는 `ADMIN`만, 사용자 메뉴는 모두) 알기 어려웠다. 사용자 쪽에서 필요한 구분은 비회원과 회원뿐이다
  - 흐름은 그룹웨어에서 흔한 "프로그램 등록 → 메뉴 등록 → 권한 그룹에 메뉴 체크 → 사용자에게 권한 그룹 주기"를 따른다. 권한 그룹에 메뉴를 체크하는 것은 `003-admin-roles`가 정한다
  - 프로그램은 화면에서 등록하지 않고 코드에 등록한다. 화면은 코드로 만들어 배포해야 생기므로 화면에서 경로만 등록해도 쓸 데가 없다
  - API를 막는 것은 지금처럼 코드의 권한 표시다. 메뉴나 프로그램 등록으로 API를 막지 않는다(등록을 빠뜨리면 API가 열리는 일을 막는다)
  - 버린 안: 권한 칸을 등록된 권한의 선택 상자로만 바꾸기(잘못 고를 여지가 남는다), 기능 메뉴의 경로·권한을 고정하기(관리자가 메뉴를 다시 짤 수 없다), 사용자 메뉴에 "모두 / 권한 선택"을 두기(사용자 쪽은 권한을 쓰지 않는다)
  - 키트 menu 헬퍼와 admin 프리셋 시드를 고치므로 moa에서 먼저 하고 키트로 옮긴다 (원칙 III, 사용자 결정)
- 관리 화면 정리: 묶음, 메뉴 표 조작, 화면 안내 (2026-11-15 결정, FR-001·FR-008·FR-010·FR-011, US5)
  - 배경: 사용자 관리·메뉴 관리·코드 관리·접속 이력·역할 관리·공지 관리가 같은 무게로 섞여, 권한과 관계없는 코드 관리가 권한 화면 사이에 있었고 셋(코드·메뉴·역할)의 경계가 헷갈렸다. 메뉴 관리는 행마다 위·아래·수정·삭제 단추가 있어 묶음 사이를 옮기기 어려웠다. 프로그램 탭은 관리자가 할 일이 없는 개발자 개념을 보였다
  - 관리 화면은 같은 틀(목록 + 오른쪽 드로어 + 체크박스 일괄 처리)로 맞춘다. 역할 관리(`003-admin-roles`)·공통코드(`004-admin-codes`)도 같은 틀이다
  - 버린 안: 코드 관리 메뉴 숨기기(공통코드를 지금 함께 다시 만들기로 함), 메뉴 표 쪽 나눔(구성 목록이라 전체를 보며 끌어야 한다)
  - 키트 menu 헬퍼 화면과 admin 프리셋 시드를 고치므로 moa에서 먼저 하고 키트로 옮긴다 (원칙 III)
