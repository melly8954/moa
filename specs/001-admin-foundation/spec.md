# Feature Specification: 관리자 백오피스 기반 (admin-foundation)

**Feature Branch**: `feat/001-admin-foundation`

**Created**: 2026-11-07

**Status**: Draft

**Input**: User description: "moa 관리자 백오피스의 기반을 psw-dev-kit springboot admin 프리셋으로 세운다. 키트 기능의 동작은 다시 적지 않고 moa가 키트를 어떻게 쓰는지만 적는다. 최초 관리자는 배포 환경변수로 1명 만들고, 이후 운영자는 사용자 관리에서 만들어 역할을 준다."

**출처**: psw-dev-kit springboot admin 프리셋 (code, login-history, menu, rbac, user-admin). 태그는 키트를 적용할 때 적는다.
키트 기능의 동작은 키트 문서와 함께 들어오는 키트 수용 테스트가 기준이다 (원칙 III).

**배경** (2026-11-07 결정):

- admin 프리셋 전체를 쓴다. rbac를 넣어 운영자가 늘면 역할로 권한을 나눈다. 예전 기획의 "관리자 등급을 나누지 않는다"를 바꾼 것이다
- 프리셋 밖의 헬퍼(redis, excel, mail 등)는 넣지 않는다. 필요한 기능의 스펙에서 정한다
- 운영 환경의 첫 관리자를 만드는 방법이 키트에 없어 moa가 만든다. 다른 프로젝트에도 필요하면 키트로 올릴 후보다

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 관리자가 관리 메뉴를 본다 (Priority: P1)

관리자(ADMIN)가 로그인하면 백오피스의 관리 메뉴 5개를 정해진 순서로 보고, 각 관리 기능을 쓸 수 있다.

**Why this priority**: 백오피스의 첫 화면이다. 이것이 없으면 다른 관리 기능을 얹을 자리가 없다.

**Independent Test**: 관리자 계정으로 로그인해 내 메뉴를 조회하면 "관리" 그룹 아래 메뉴 5개가 정해진 순서로 나오고, 각 메뉴의 관리 기능을 부를 수 있는지로 확인한다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** 관리자가 로그인했다, **When** 내 메뉴를 조회한다, **Then** "관리" 그룹 아래 사용자 관리, 메뉴 관리, 코드 관리, 접속 이력, 역할 관리가 이 순서로 보인다
2. **US1-AC2** **Given** 관리자가 로그인했다, **When** 5개 관리 기능 각각의 목록 조회를 부른다, **Then** 모두 거부되지 않는다

---

### User Story 2 - 일반 회원은 백오피스에 들어오지 못한다 (Priority: P1)

일반 회원(USER)은 관리 메뉴를 보지 못하고, 관리 기능을 직접 불러도 거부된다.

**Why this priority**: 백오피스를 여는 순간부터 지켜져야 하는 보안 경계다.

**Independent Test**: 일반 회원 계정으로 내 메뉴를 조회하고 관리 기능을 직접 불러 확인한다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 일반 회원이 로그인했다, **When** 내 메뉴를 조회한다, **Then** "관리" 그룹과 그 아래 메뉴가 보이지 않는다
2. **US2-AC2** **Given** 일반 회원이 로그인했다, **When** 5개 관리 기능 중 어느 것을 불러도, **Then** 권한 없음으로 거부된다
3. **US2-AC3** **Given** 로그인하지 않았다, **When** 관리 기능을 부른다, **Then** 로그인 필요로 거부된다

---

### User Story 3 - 관리자가 운영자를 만들고 역할로 권한을 나눈다 (Priority: P2)

관리자가 사용자 관리에서 운영자 계정을 만들고, 역할 관리에서 만든 역할(예: 권한 일부를 묶은 "운영 매니저")을 준다. 운영자는 그 역할에 묶인 권한의 메뉴와 기능만 쓴다.

**Why this priority**: 운영자가 늘어날 때를 위한 기능이다. 첫 출시에는 관리자 한 명으로도 운영할 수 있다.

**Independent Test**: 접속 이력 조회 권한만 묶은 역할을 만들어 운영자에게 주고, 그 운영자로 로그인해 메뉴와 기능 접근을 확인한다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 접속 이력 조회 권한만 가진 역할을 받은 운영자가 로그인했다, **When** 내 메뉴를 조회한다, **Then** "관리" 그룹 아래 접속 이력만 보인다
2. **US3-AC2** **Given** 같은 운영자다, **When** 접속 이력 목록을 부른다, **Then** 거부되지 않는다
3. **US3-AC3** **Given** 같은 운영자다, **When** 사용자 관리 목록을 부른다, **Then** 권한 없음으로 거부된다

---

### User Story 4 - 배포할 때 최초 관리자가 한 번만 만들어진다 (Priority: P2)

운영 환경에 처음 배포하면 배포 설정에 넣은 아이디와 비밀번호 해시로 관리자 1명이 만들어진다. 비밀번호는 저장소에 두지 않는다. 다시 배포해도 관리자가 또 만들어지지 않는다.

**Why this priority**: 운영 환경에 관리자가 없으면 백오피스를 쓸 수 없다. 다만 개발과 시험은 키트의 로컬 시험 계정으로 먼저 할 수 있다.

**Independent Test**: 빈 DB에 최초 관리자 설정을 넣고 서버를 두 번 띄운 뒤 관리자 수와 로그인을 확인한다.

**Acceptance Scenarios**:

1. **US4-AC1** **Given** 빈 DB와 최초 관리자 설정(아이디, 비밀번호 해시)이 있다, **When** 서버가 뜬다, **Then** 그 아이디로 ADMIN 계정 1개가 만들어지고 해당 비밀번호로 로그인된다
2. **US4-AC2** **Given** 최초 관리자가 이미 만들어졌다, **When** 서버를 다시 띄운다, **Then** 관리자 계정이 더 만들어지지 않고 기존 계정의 비밀번호도 바뀌지 않는다
3. **US4-AC3** **Given** 운영 환경에 최초 관리자 설정이 없다, **When** 서버가 뜬다, **Then** 서버가 시작을 실패하고, 빠진 설정을 알려 주는 로그를 남긴다

---

### Edge Cases

- 최초 관리자 설정의 아이디가 이미 일반 회원(USER)으로 쓰이고 있으면: 그 계정을 관리자로 바꾸지 않고, 시작 로그에 충돌을 남기고 관리자를 만들지 않는다
- 관리자가 자기 자신의 역할을 USER로 바꾸거나 자신을 지우는 경우: 키트 사용자 관리의 동작을 따른다
- 관리 메뉴 그룹에 보이는 하위 메뉴가 하나도 없는 사용자: 그룹 자체가 보이지 않는다 (키트 메뉴 동작)
- local 프로필: 최초 관리자 설정을 쓰지 않고 키트의 로컬 시험 계정(관리자, 일반 회원 각 1개)을 쓴다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 시스템은 admin 프리셋의 관리 기능 5개(사용자 관리, 메뉴 관리, 코드 관리, 접속 이력, 역할 관리)를 제공해야 한다(MUST). 각 기능의 동작은 키트를 따른다
- **FR-002**: 관리 메뉴 트리는 "관리" 그룹 아래 FR-001의 5개를 사용자 관리, 메뉴 관리, 코드 관리, 접속 이력, 역할 관리 순서로 둬야 한다(MUST). moa 관리 기능(신고, 제재, 게임, 복구)은 정해질 때까지 메뉴에 넣지 않는다
- **FR-003**: 관리 기능은 메뉴마다 정해진 권한을 가진 사용자만 볼 수 있고 부를 수 있어야 한다(MUST). 관리자(ADMIN)는 모든 권한을 갖는다
- **FR-004**: 관리자는 운영자 계정을 만들고, 권한을 묶은 역할을 만들어 운영자에게 줄 수 있어야 한다(MUST)
- **FR-005**: 운영 환경(local이 아닌 프로필)에서 시스템은 시작할 때 배포 설정의 아이디와 비밀번호 해시로 최초 관리자 1명을 만들어야 한다(MUST). 같은 아이디의 계정이 이미 있으면 아무것도 바꾸지 않는다. 설정이 없으면 시작을 실패해야 한다(MUST)
- **FR-006**: 최초 관리자의 비밀번호와 그 해시는 저장소에 두지 않아야 한다(MUST NOT). 배포 설정으로만 넣는다
- **FR-007**: 최초 관리자에게 첫 로그인 때 비밀번호 변경을 강제하지 않는다 (예전 결정 유지: 비밀번호를 운영자만 알기 때문)

### Key Entities *(include if feature involves data)*

- **관리 메뉴**: 백오피스 사이드바의 항목. 이름, 화면 경로, 순서, 보는 데 필요한 권한을 가진다. 그룹 아래 하위 메뉴로 묶인다
- **권한**: 관리 기능 하나를 쓸 수 있는 자격. 관리 기능마다 하나씩 있다 (사용자 관리, 메뉴 관리, 코드 관리, 접속 이력 조회, 역할 관리)
- **역할**: 권한 여러 개를 묶은 것. 관리자가 만들어 운영자에게 준다
- **관리자 / 운영자**: 관리자는 모든 권한을 가진 계정이고, 운영자는 역할로 일부 권한만 받은 계정이다. 둘 다 회원 활동은 하지 않는다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 새 운영 환경에 배포한 직후, 별도 수작업(DB 직접 입력 등) 없이 관리자가 로그인해 관리 메뉴 5개를 쓸 수 있다
- **SC-002**: 일반 회원과 로그인하지 않은 사용자의 관리 기능 호출은 100% 거부된다
- **SC-003**: 관리자가 새 운영자에게 일부 권한만 주는 작업(계정 만들기, 역할 만들기, 역할 주기)을 5분 안에 마칠 수 있다
- **SC-004**: 수용 시나리오(US1~US4) 전부가 자동 테스트로 확인된다 (원칙 II)

## Assumptions

- 관리자 화면(프론트)은 프론트 키트(web-next)가 만드는 admin 화면을 쓴다. 이 스펙의 AC는 서버 동작으로 확인하고, 화면 확인은 프론트 키트를 적용할 때 더한다
- 회원 가입·로그인 방식과 회원 정보 모델은 사용자 쪽 기능이 정한다. 이 스펙은 키트 기본 계정(아이디·비밀번호)으로 관리자와 운영자를 다룬다
- 관리자·운영자 계정이 회원 활동(게시물, 파티, 메시지)을 못 하게 막는 방법은 회원 기능과 맞출 경계다 (`specs/README.md` 맞춰야 할 경계). 이 스펙 범위 밖이다
- 프리셋 밖의 키트 헬퍼(redis, excel, mail 등)는 쓰지 않는다. 그래서 공통코드는 캐시 없이 매번 저장소에서 읽는다
- 운영 환경의 배포 설정(환경변수)을 넣을 수 있는 배포 환경이 있다
