# Feature Specification: 알림 (notifications)

**Feature Branch**: `feat/007-notifications`

**Created**: 2026-11-15

**Status**: Draft

**Input**: User description: "공통 알림 기능을 만든다. 첫 사용처는 006 공지의 실시간 알림이다. 알림은 이후 댓글·초대·메시지·제재 같은 사용자별 알림도 받는 공통 기능이고, 사용자별 알림은 알림함에 쌓인다. 키트 websocket 헬퍼를 이 기능에서 적용한다. 구독 경로 규칙은 정해져 있다. 프론트 WebSocket 연결 부품은 키트에 없어 moa에 먼저 만든다."

**출처**: moa가 만드는 기능. 실시간 전달은 키트 websocket 헬퍼(`springboot`)를 쓴다. 프론트 실시간 연결과 웹 푸시는 키트에 없어 moa에서 먼저 만들고 나중에 키트로 옮긴다.

**배경** (2026-11-15 결정):

- 알림은 공통 기능이다. 공지는 첫 사용처이고, 댓글·초대·메시지·제재처럼 한 사용자에게 가는 알림은 각 기능이 생길 때 이 기능을 써서 보낸다. 이번에는 그 기능들이 아직 없어 알림함은 틀(받기·목록·읽음·안 읽은 수)까지 만든다
- 알림은 두 갈래다
  - **전체 알림**: 로그인해 화면을 보고 있는 모두에게 가는 알림. 알림함에 쌓지 않는다 (공지 게시, `006-notices` FR-009)
  - **개인 알림**: 한 사용자에게 가는 알림. 알림함에 쌓이고 읽음을 기억한다
- 개인 알림함은 사이드바 아래 계정 줄의 벨이다. 공지는 모두에게 같은 소식이라 메뉴(`006-notices` FR-010), 개인 알림은 "나에게 온 것"이라 계정 옆에 둔다
- 화면을 보고 있으면 새로고침 없이 토스트와 표시로 알린다. 화면을 보고 있지 않을 때를 위해 브라우저 알림(웹 푸시)도 이번에 만든다
- 실시간 전달은 메신저와 같은 연결을 쓴다. 구독 경로 규칙은 `specs/README.md` 맞춰야 할 경계(2026-11-14)를 이 스펙으로 옮긴다

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 공지가 게시되면 화면을 보고 있는 사람에게 바로 알린다 (Priority: P1)

로그인해 화면을 보고 있는 사용자는 관리자가 공지를 게시하는 순간 새로고침 없이 알림을 받는다. `006-notices` US4를 이 기능의 전체 알림으로 이룬다.

**Why this priority**: 006에서 미뤄 둔 첫 사용처이고, 전체 알림 경로가 있어야 다른 실시간 기능도 붙는다.

**Independent Test**: 사용자 화면을 열어 둔 채 관리자가 공지를 게시하고, 토스트와 "공지" 메뉴 점이 새로고침 없이 생기는지 본다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** 로그인한 사용자가 화면을 보고 있다, **When** 관리자가 공지를 게시한다, **Then** 새로고침하지 않아도 공지 제목이 담긴 토스트가 뜨고 "공지" 메뉴에 새 공지 점이 생긴다 (`006-notices` US4-AC1)
2. **US1-AC2** **Given** 로그인한 사용자가 화면을 보고 있다, **When** 관리자가 공지를 임시 저장하거나 이미 게시한 공지를 고친다, **Then** 알림이 오지 않는다
3. **US1-AC3** **Given** 로그인하지 않은 사람이 공지 화면을 보고 있다, **When** 관리자가 공지를 게시한다, **Then** 알림을 받지 않는다
4. **US1-AC4** **Given** 공지 알림 토스트가 떴다, **When** 사용자가 토스트의 "보기"를 누른다, **Then** 그 공지의 상세 화면으로 간다

---

### User Story 2 - 나에게 온 알림을 알림함에서 보고 읽는다 (Priority: P1)

로그인한 사용자는 사이드바 계정 줄의 벨에서 안 읽은 알림 수를 보고, 눌러서 최근 알림을 보고, 알림을 누르면 관련 화면으로 가며 읽음이 된다.

**Why this priority**: 개인 알림을 받을 모든 기능(댓글·초대·메시지·제재)이 이 알림함을 쓴다. 이번에 틀을 세워야 그 기능들이 알림만 보내면 된다.

**Independent Test**: 한 사용자에게 개인 알림 몇 개를 만든 뒤, 벨의 수와 펼친 목록, 알림 화면, 읽음 처리를 확인한다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 사용자에게 안 읽은 개인 알림이 3개 있다, **When** 화면을 연다, **Then** 계정 줄의 벨에 3이 보인다
2. **US2-AC2** **Given** 개인 알림이 여러 개 있다, **When** 사용자가 벨을 누른다, **Then** 최근 알림 10개가 최신순으로 제목, 시각, 읽음 여부와 함께 펼쳐지고 "모두 보기"로 알림 화면에 갈 수 있다
3. **US2-AC3** **Given** 안 읽은 알림이 있다, **When** 사용자가 그 알림을 누른다, **Then** 알림에 걸린 화면으로 가고 그 알림은 읽음이 되며 벨의 수가 하나 준다
4. **US2-AC4** **Given** 안 읽은 알림이 여러 개 있다, **When** 사용자가 "모두 읽음"을 누른다, **Then** 모든 알림이 읽음이 되고 벨의 수가 사라진다
5. **US2-AC5** **Given** 알림 화면이다, **When** 사용자가 목록을 연다, **Then** 자기 개인 알림만 최신순으로 보이고, 다른 사용자의 알림은 보이지 않는다
6. **US2-AC6** **Given** 로그인하지 않았다, **When** 알림함이나 알림 화면에 들어가려 한다, **Then** 로그인 안내를 받는다

---

### User Story 3 - 새 개인 알림을 바로 알아챈다 (Priority: P2)

화면을 보고 있는 사용자는 새 개인 알림이 생기는 순간 새로고침 없이 토스트를 보고 벨의 수가 바뀐다.

**Why this priority**: 알림함만으로도 다음에 화면을 열 때 알 수 있다. 실시간은 그 위에 얹는다.

**Independent Test**: 사용자 화면을 열어 둔 채 그 사용자에게 개인 알림을 하나 만든다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 로그인한 사용자가 화면을 보고 있다, **When** 그 사용자에게 개인 알림이 생긴다, **Then** 새로고침하지 않아도 알림 제목이 담긴 토스트가 뜨고 벨의 수가 하나 는다
2. **US3-AC2** **Given** 두 사용자가 화면을 보고 있다, **When** 한 사용자에게만 개인 알림이 생긴다, **Then** 다른 사용자에게는 아무것도 오지 않는다
3. **US3-AC3** **Given** 같은 사용자가 화면을 둘(탭이나 기기) 열어 두었다, **When** 그 사용자에게 개인 알림이 생긴다, **Then** 두 화면 모두에 토스트가 뜨고 벨의 수가 는다

---

### User Story 4 - 화면을 보고 있지 않아도 브라우저 알림으로 받는다 (Priority: P3)

사용자가 브라우저 알림을 켜 두면, moa 화면을 보고 있지 않을 때도 새 개인 알림을 운영체제 알림으로 받는다.

**Why this priority**: 실시간 토스트와 알림함만으로도 알림은 쓸 수 있다. 브라우저 알림은 다시 들어오게 만드는 보탬이다.

**Independent Test**: 알림 화면에서 브라우저 알림을 켜고 탭을 닫은 뒤 그 사용자에게 개인 알림을 만들고, 브라우저 알림이 오고 누르면 관련 화면이 열리는지 본다.

**Acceptance Scenarios**:

1. **US4-AC1** **Given** 사용자가 알림 화면에서 브라우저 알림을 켜고 권한을 허락했다, **When** moa 화면을 닫은 뒤 그 사용자에게 개인 알림이 생긴다, **Then** 알림 제목이 담긴 브라우저 알림이 온다
2. **US4-AC2** **Given** 브라우저 알림이 왔다, **When** 사용자가 그 알림을 누른다, **Then** moa의 관련 화면이 열린다
3. **US4-AC3** **Given** 브라우저 알림을 켜 두었다, **When** 사용자가 알림 화면에서 끈다, **Then** 그 브라우저로는 더 이상 브라우저 알림이 오지 않는다
4. **US4-AC4** **Given** 사용자가 브라우저 알림 권한을 거부했다, **When** 알림 화면을 연다, **Then** 브라우저 알림이 꺼져 있고 브라우저 설정에서 바꿀 수 있다는 안내가 보인다
5. **US4-AC5** **Given** 브라우저 알림을 켜 둔 사용자가 로그아웃한다, **When** 그 사용자에게 개인 알림이 생긴다, **Then** 그 브라우저로 브라우저 알림이 오지 않는다

---

### Edge Cases

- moa 화면이 보이는 상태(앞에 띄운 탭)면 개인 알림은 토스트로만 알리고 브라우저 알림을 띄우지 않는다 (같은 알림이 두 번 보이지 않게). moa 탭이 열려 있어도 다른 탭이나 창을 보고 있으면 브라우저 알림이 온다
- 같은 사용자가 화면을 여러 개 열어 두고 한 화면에서 알림을 읽으면, 다른 화면의 벨 숫자는 그 화면을 다시 보거나 새 알림이 올 때 맞춰진다
- 연결이 끊겼다 다시 이어진 사이에 생긴 개인 알림: 실시간 토스트는 없어도 벨의 수와 알림함에는 보인다. 끊긴 사이의 전체 알림(공지)은 다시 보내지 않는다 (새 공지 점은 006 FR-008로 남는다)
- 로그인 상태가 끝나면(로그아웃, 재발급 실패) 실시간 연결도 끝나고, 다시 로그인하면 다시 이어진다
- 알림에 걸린 화면이 없어진 경우(지운 공지 등): 알림을 누르면 그 화면의 없는 대상 안내가 보인다. 알림은 읽음이 된다
- 안 읽은 수가 많을 때: 벨에는 99까지 보이고 그보다 많으면 "99+"
- 알림이 하나도 없을 때: 펼친 목록과 알림 화면에 빈 결과 안내가 보인다
- 브라우저 알림을 지원하지 않는 브라우저: 켜기 단추 대신 지원하지 않는다는 안내가 보인다
- 한 사용자가 여러 브라우저에서 브라우저 알림을 켜면 켠 브라우저마다 온다
- 관리자·운영자 계정도 알림을 받는다. 받는 것은 회원 활동이 아니다

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 로그인한 사용자의 화면은 서버와 실시간 연결을 유지해야 한다(MUST). 로그인하지 않은 화면은 연결하지 않는다
- **FR-002**: 전체 알림은 그 순간 실시간 연결된 모든 로그인 사용자에게 가야 한다(MUST). 알림함에 쌓지 않고, 연결되지 않은 사용자에게 나중에 보내지 않는다
- **FR-003**: 공지를 게시하면 전체 알림으로 공지 제목과 공지 상세로 가는 연결을 보내야 한다(MUST). 임시 저장, 고치기, 고정, 지우기에는 보내지 않는다 (`006-notices` FR-009)
- **FR-004**: 다른 기능은 한 사용자에게 개인 알림을 보낼 수 있어야 한다(MUST). 개인 알림은 종류, 제목, 관련 화면으로 가는 연결을 가진다. 개인 알림은 알림함에 쌓이고, 그 사용자의 연결된 모든 화면에 실시간으로 간다
- **FR-005**: 로그인한 사용자는 벨에서 안 읽은 개인 알림 수를 보고, 눌러서 최근 알림 10개를 보고, 알림 화면에서 모든 개인 알림을 최신순으로 볼 수 있어야 한다(MUST). 자기 알림만 본다. 벨은 사이드바 계정 줄에 두고, 사이드바가 서랍이 되는 좁은 폭에서는 화면 머리(서랍 단추 옆)에도 둔다
- **FR-006**: 알림을 누르면 관련 화면으로 가고 그 알림은 읽음이 되어야 한다(MUST). "모두 읽음"으로 한 번에 읽음으로 바꿀 수 있다
- **FR-007**: 화면을 보고 있는 사용자에게 새 전체 알림이나 개인 알림이 오면 토스트로 알리고, 관련 표시(공지 점, 벨의 수)를 새로고침 없이 바꿔야 한다(MUST). 토스트의 "보기"를 누르면 관련 화면으로 간다
- **FR-008**: 사용자는 알림 화면에서 그 브라우저의 브라우저 알림을 켜고 끌 수 있어야 한다(MUST). 켜면 그 브라우저에서 moa 화면이 보이는 상태가 아닐 때 새 개인 알림이 브라우저 알림으로 온다. 로그아웃하면 그 브라우저의 브라우저 알림은 꺼진다
- **FR-009**: 개인 알림은 90일 동안 보관하고, 지나면 지운다(MUST)
- **FR-010**: 실시간 구독 경로는 기능별로 나눈다(MUST). 연결은 하나를 메신저 등과 함께 쓰고, 전체는 기능마다 하나(공지는 공지 전체 경로), 한 사용자는 기능마다 하나(알림은 알림 개인 경로)다. 다른 기능도 이 규칙으로 이름을 정한다

### Key Entities *(include if feature involves data)*

- **개인 알림**: 한 사용자에게 간 알림. 받는 사람, 종류(예: 댓글, 초대, 메시지, 제재), 제목, 관련 화면으로 가는 연결, 만든 시각, 읽은 시각을 가진다
- **전체 알림**: 그 순간 연결된 모두에게 가는 알림. 저장하지 않는다. 종류(예: 공지), 제목, 관련 화면으로 가는 연결을 가진다
- **브라우저 알림 구독**: 한 사용자가 한 브라우저에서 브라우저 알림을 켠 기록. 사용자마다 여럿일 수 있다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 화면을 보고 있는 로그인 사용자는 공지가 게시된 뒤 5초 안에 알림을 받는다 (`006-notices` SC-003)
- **SC-002**: 화면을 보고 있는 사용자는 새 개인 알림이 생긴 뒤 5초 안에 토스트와 벨의 수 변화를 본다
- **SC-003**: 사용자는 어느 화면에서든 한 번의 누름으로 최근 알림을 볼 수 있다
- **SC-004**: 다른 사용자의 개인 알림이 보이거나 전달되는 일은 0건이다
- **SC-005**: 브라우저 알림을 켠 사용자는 화면을 닫은 상태에서 새 개인 알림을 1분 안에 받는다
- **SC-006**: 수용 시나리오(US1~US4) 전부가 자동 테스트로 확인된다 (원칙 II). 브라우저 알림의 운영체제 표시처럼 자동으로 확인할 수 없는 부분은 화면 직접 확인으로 남긴다

## Assumptions

- 지금 개인 알림을 보내는 기능은 없다. 댓글·초대·메시지·제재 기능이 생기면 FR-004로 개인 알림을 보내고, 그 기능의 스펙에 알림 종류와 제목·연결을 적는다. 이번 수용 테스트는 테스트에서 개인 알림을 만들어 확인한다
- 공지 게시 알림은 브라우저 알림으로 보내지 않는다. 화면을 보고 있는 사람에게만 가는 전체 알림이다 (`006-notices` FR-009). 화면을 닫은 사람은 다음에 들어와 새 공지 점으로 안다
- 브라우저 알림은 브라우저가 지원하고 사용자가 권한을 허락할 때만 된다. 운영 주소는 https다. iOS는 홈 화면에 추가한 경우에만 되는 브라우저 제약을 따른다
- 실시간 전달은 키트 websocket 헬퍼를 쓴다. 서버를 여러 대로 늘리는 일은 이번 범위가 아니다 (키트 헬퍼 주의: 서버가 한 대일 때만 모두에게 닿는다)
- 개인 알림 보관 90일은 접속 이력(`005-admin-login-history` FR-002)과 같은 기간으로 둔다
- 메신저는 같은 실시간 연결을 쓰고, 구독 경로 이름은 FR-010 규칙을 따른다. 적용 전에 메신저 담당에게 알린다
- 구독 경로 이름 (2026-11-14 결정, `specs/README.md` 맞춰야 할 경계에서 옮김): 연결 `/ws`(키트 그대로), 보내기 `/app/...`, 전체 `/topic/<기능>`(공지 `/topic/notices`), 한 사용자 `/user/queue/<기능>`(알림 `/user/queue/notifications`)
- 알림 설정(종류별로 끄기 등)은 이번에 두지 않는다. 브라우저 알림 켜기·끄기만 있다
