# Feature Specification: 소셜 로그인 (social-login)

**Feature Branch**: `feat/010-social-login`

**Created**: 2026-11-16

**Status**: Draft

**Input**: User description: "구글 소셜 로그인" (2026-11-17 구글 + 디스코드로 넓힘)

**출처**: moa. 잠정으로 키트 oauth 헬퍼를 기본 방향으로 한다 [NEEDS CLARIFICATION: 키트에 oauth 헬퍼가 있는가, 구글·디스코드와 연결·해제(FR-006)까지 지원하는가? 팀 확인 필요 (담당: 키트 담당/팀 리더). 팀이 다른 방식을 제안하면 그때 바꾼다]. 이 스펙은 구현 방식과 상관없이 동작(FR·AC)만 적고, 헬퍼에 맞춘 세부는 plan에서 정한다

**배경** (기존 스펙에서 따름):

- 이 기능이 moa의 첫 회원 가입 경로다. 지금까지 회원은 시드 계정뿐이었다(`008-party` 가정). `002-admin-users` 가정의 "회원 가입·로그인 방식과 회원 정보 모델은 사용자 쪽 기능이 정한다"의 그 기능이 이 스펙이다
- 소셜 계정으로 가입한 회원은 비밀번호 없는 계정이다. 비밀번호 없는 계정의 기존 규칙(`002-admin-users` FR-007, 사용자 관리에서 비밀번호 초기화를 막음)을 그대로 따른다
- 소셜 로그인의 성공과 실패도 접속 이력에 남긴다(`005-admin-login-history` FR-001)
- 로그인한 뒤 첫 화면은 아이디·비밀번호 로그인과 같은 규칙이다(`001-admin-menus` FR-006)
- (2026-11-17 팀 결정) 서버 경유 방식: 소셜 로그인과 계정 설정의 소셜 계정 연결은 서버를 거쳐 제공자 인증을 받는다(인가 코드 + PKCE). 제공자 토큰과 비밀 값은 서버에만 두고, 로그인 뒤 상태는 아이디·비밀번호 로그인과 같다 (자세한 흐름은 plan의 research.md)
- (2026-11-17 결정) 로그인 제공자는 구글과 디스코드다. 디스코드에는 계정 식별과 이메일(`identify`, `email`)만 요청한다. 카카오는 나중이다
- 정해지지 않은 것(회원 정보 모델, 키트 헬퍼 등)은 추측하지 않고 [NEEDS CLARIFICATION]으로 둔다 (원칙 I)

## Clarifications

### Session 2026-11-16

- Q: 구글 계정과 moa 회원을 어떤 구조로 이어 두는가? → A: 잠정 B(회원 계정은 키트 `users` 그대로, 외부 계정 연결을 따로 두어 한 회원이 여러 소셜 계정을 가질 수 있음). 팀 확인 필요 (담당: 팀 회의 — 002 사용자 관리 목록에 영향). 키트 oauth 헬퍼가 기본 방향이므로 plan에서 그 구조와 맞는지 다시 본다
- Q: 아이디·비밀번호 계정이 이미 있는 사람이 구글 로그인을 하면 그 계정과 잇는가? → A: C. 이메일로 자동 연결하지 않는다. 로그인한 회원이 계정 설정 화면에서 자기 계정에 구글 계정을 직접 연결·해제한다. 로그인 수단이 구글 하나뿐인 회원(비밀번호 없음)은 해제할 수 없고, 다른 회원에 이미 연결된 구글 계정은 연결을 막고 안내한다. 관리자·운영자 계정의 연결은 FR-007로 정한다 (처음 답 A를 C로 정정)
- Q: 연결 조건에 "구글이 인증한 이메일일 때만"을 넣는가? → A: 넣는다. 제공자가 이메일을 주지 않거나 인증하지 않은 이메일이면 연결을 막는다 (처음 답 "넣지 않는다"를 2026-11-17에 정정, 아래 Session 2026-11-17)
- Q: 이번 범위에 앱 클라이언트가 들어가는가? → A: 아니다. 이번 범위는 웹 로그인만, 앱 클라이언트는 나중이다
- Q: 회원의 표시 이름은 어디서 가져오는가? → A: B. 처음 구글 로그인 때 닉네임 입력 화면을 거치고, 그 닉네임이 표시 이름이다
- Q: 구글 로그인을 키트 oauth 헬퍼로 만드는가, moa가 직접 만드는가? → A: 잠정 A(키트 oauth 헬퍼가 기본 방향). 헬퍼 유무와 연결·해제(FR-006) 지원은 팀 확인 필요 (담당: 키트 담당/팀 리더). 팀이 다른 방식을 제안하면 바꾼다. 스펙은 동작(FR·AC)만 적고 헬퍼에 맞춘 세부는 plan에서 정한다
- Q: 처음 구글 로그인을 한 사람이 닉네임을 넣지 않고 떠나면 어떻게 하는가? → A: A. 닉네임을 넣기 전에는 회원을 만들지 않는다. 떠나면 가입이 안 된 것이고 다음 구글 로그인 때 닉네임 입력부터 다시 한다

### Session 2026-11-17

- Q: 관리자·운영자 계정이 구글 로그인을 쓸 수 있는가? → A: 아니다. 관리자·운영자 계정에는 구글을 연결할 수 없고, 구글 회원에게 `ADMIN`·업무 역할을 주는 것도 막는다 (`002-admin-users` "관리자와 운영자는 회원 활동을 하지 않는다" 취지를 따름)
- Q: 비밀번호 없는 계정에서 계정 메뉴의 "비밀번호 변경"은 어떻게 하는가? → A: 숨긴다
- Q: 구글 로그인 설정이 없는 환경에서 구글 로그인 단추는 어떻게 하는가? → A: 숨긴다
- Q: 구글 계정의 이름·이메일이 바뀌면 moa에 저장한 값도 바꾸는가? → A: 아니다. 가입(연결) 때 값을 그대로 둔다
- Q: 구글 말고 어떤 소셜 로그인을 넣는가? → A: 구글과 디스코드. 둘 다 서버 경유 인가 코드 + PKCE이고, 디스코드는 `identify`, `email`만 요청한다. 두 제공자는 같은 외부 계정 연결(제공자 GOOGLE·DISCORD)을 쓴다. 카카오는 범위 밖이고 나중이다. 위 구글에 대한 답(자동 연결 없음, 관리자·운영자 막기, 단추 숨김, 값 고정 등)은 디스코드에도 똑같이 적용한다
- Q: 닉네임 말고 가입 때 함께 받는 것(약관·개인정보 동의 등)이 있는가? → A: 있다. 닉네임 입력 화면에서 이용약관과 개인정보 수집·이용에 필수로 동의받는다. 요약만 보이고 펼치면 전문을 본다. 둘 다 체크해야 가입이 진행된다. 동의 시각과 약관 버전을 저장한다 (FR-013)
- Q: 가입하려는 소셜 계정의 이메일을 다른 회원이 이미 쓰고 있으면? → A: 가입을 막고 "다른 방식으로 가입된 이메일" 안내를 보인다. 자동 연결은 하지 않는다 (FR-014)
- Q: 탈퇴(삭제)한 소셜 회원이 같은 소셜 계정으로 다시 가입할 수 있는가? → A: "탈퇴 후 30일"과 "남은 정지 기간 끝" 중 늦은 때까지 재가입할 수 없다. 영구 정지면 재가입할 수 없다. 이를 위해 완전 삭제 뒤에도 제공자·계정 식별자의 해시와 재가입 가능 일시를 남긴다. 탈퇴·30일 복구·완전 삭제 흐름은 별도 스펙(회원 탈퇴)이 정하고, 010은 재가입 제한 확인만 한다 (FR-015)
- Q: 이메일을 주지 않거나 제공자가 인증하지 않은 이메일(디스코드 `verified=false` 등)의 소셜 계정으로 가입하면? → A: 가입을 막고 "제공자에서 이메일 인증 후 다시 시도" 안내를 보인다. 회원을 만들지 않는다 (FR-014)
- Q: 계정 설정의 연결(FR-006)에도 이메일 중복 확인과 재가입 제한을 적용하는가? → A: 적용한다. 가입과 똑같이 확인한다(FR-014, FR-015). 단 이메일 중복에서 그 이메일을 쓰는 회원이 연결하려는 본인이면 막지 않는다
- Q: 연결에도 이메일이 없거나 인증되지 않은 소셜 계정을 막는가? → A: 막는다. 가입과 똑같이 "제공자에서 이메일 인증 후 다시 시도" 안내를 보인다. 미인증 이메일이 연결에 저장되면 그 이메일의 진짜 주인이 가입할 때 FR-014에 막힐 수 있기 때문이다. Session 2026-11-16의 "연결 조건에 인증 이메일을 넣지 않는다" 답과 FR-006의 같은 줄을 이 답으로 정정한다 (FR-006, FR-014)

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 처음 온 사람이 소셜 계정으로 가입한다 (Priority: P1)

moa에 계정이 없는 사람이 로그인 화면에서 "구글로 계속하기" 또는 "디스코드로 계속하기"를 눌러 소셜 계정을 고르고 허락한다. 닉네임을 넣고 약관에 동의하면 moa는 그 소셜 계정으로 회원을 만들고 로그인시킨다.

**Why this priority**: 회원 가입 경로가 없으면 시드 계정 밖의 사람이 회원 활동(파티 등)을 할 수 없다. 이 기능의 목적 자체다.

**Independent Test**: moa에 가입한 적 없는 구글 계정과 디스코드 계정 각각으로 로그인 화면에서 소셜 로그인을 끝까지 하고, 회원이 생겨 로그인 상태로 첫 화면에 들어가는지 본다.

**Acceptance Scenarios**:

1. **US1-AC1** **Given** moa에 가입한 적 없는 소셜 계정(구글 또는 디스코드)이다, **When** 로그인 화면에서 그 제공자로 로그인하고 제공자 화면에서 허락한 뒤 닉네임 입력과 약관 동의를 마친다, **Then** 새 회원이 만들어지고 로그인 상태로 사용자 셸의 첫 화면(`/`)에 들어간다
2. **US1-AC2** **Given** US1-AC1로 가입했다, **When** 관리자가 사용자 관리 목록을 연다, **Then** 그 회원이 시스템 역할 `USER`인 비밀번호 없는 계정으로 보이고, 드로어에서 비밀번호 초기화를 할 수 없다
3. **US1-AC3** **Given** 처음 소셜 로그인을 해 제공자 화면에서 허락했다, **When** moa로 돌아온다, **Then** 닉네임 입력 화면이 보이고, 닉네임을 넣고 필수 약관에 동의해 마치면 첫 화면(또는 돌아갈 주소)으로 가며 그 닉네임이 표시 이름으로 보인다 (FR-005, FR-013)
4. **US1-AC4** **Given** 로그인이 필요한 화면 주소로 들어와 로그인 화면으로 넘어왔다, **When** 소셜 계정으로 처음 가입한다, **Then** 첫 화면이 아니라 처음 들어오려던 주소로 돌아간다 (`001-admin-menus` FR-006)
5. **US1-AC5** **Given** 처음 소셜 로그인을 해 닉네임 입력 화면이 보인다, **When** 가입을 마치지 않고 떠난 뒤 다시 같은 소셜 계정으로 로그인한다, **Then** 그 사이 회원은 만들어지지 않았고 닉네임 입력 화면부터 다시 시작한다
6. **US1-AC6** **Given** 소셜 계정으로 가입한 회원이 있다, **When** 관리자가 사용자 관리에서 시스템 역할 `ADMIN`을 주거나 역할 관리에서 업무 역할을 주려 한다, **Then** 막히고 소셜 회원에게는 관리 역할을 줄 수 없다는 안내가 보인다 (FR-007)
7. **US1-AC7** **Given** 닉네임 입력 화면이다, **When** 이용약관이나 개인정보 수집·이용 중 하나라도 체크하지 않는다, **Then** 가입을 진행할 수 없고 회원이 만들어지지 않는다. 각 약관은 요약이 보이고 펼치면 전문이 보인다 (FR-013)
8. **US1-AC8** **Given** US1-AC1로 가입했다, **When** 그 회원의 약관 동의 기록을 본다, **Then** 이용약관과 개인정보 수집·이용 각각의 동의 시각과 동의한 약관 버전이 남아 있다 (FR-013)
9. **US1-AC9** **Given** 가입하려는 소셜 계정의 이메일을 다른 회원이 이미 쓰고 있다(어느 로그인 방식이든), **When** 그 소셜 계정으로 처음 로그인한다, **Then** 가입이 막히고 "다른 방식으로 가입된 이메일" 안내가 보이며, 기존 회원에 자동으로 잇지 않고 회원도 만들어지지 않는다 (FR-014)
10. **US1-AC10** **Given** 탈퇴한 소셜 회원의 재가입 제한 기간이 남아 있다, **When** 같은 소셜 계정으로 로그인 화면에서 로그인한다, **Then** 가입이 막히고 재가입이 제한된 계정이라는 안내가 보이며 회원이 만들어지지 않는다. 재가입 가능 일시가 지난 뒤에는 새 회원으로 가입할 수 있다 (FR-015)
11. **US1-AC11** **Given** 영구 정지로 탈퇴(삭제)된 소셜 계정이다, **When** 같은 소셜 계정으로 로그인한다, **Then** 기간과 상관없이 가입이 막힌다 (FR-015)
12. **US1-AC12** **Given** 제공자가 이메일을 주지 않거나 인증되지 않은 이메일을 준 소셜 계정이다(디스코드에서 이메일 인증을 하지 않은 계정 등), **When** 그 소셜 계정으로 처음 로그인한다, **Then** 가입이 막히고 "제공자에서 이메일 인증 후 다시 시도" 안내가 보이며 회원이 만들어지지 않는다 (FR-014)

### User Story 2 - 소셜 회원이 다시 로그인한다 (Priority: P1)

소셜 계정으로 가입한 회원이 다음에 로그인 화면에서 같은 제공자로 로그인하면 새 회원이 생기지 않고 같은 회원으로 로그인한다.

**Why this priority**: 가입만 되고 다시 들어올 수 없으면 쓸 수 없다. US1과 함께 최소 기능이다.

**Independent Test**: US1로 가입한 소셜 계정으로 로그아웃 뒤 다시 로그인하고, 같은 회원(같은 파티·알림 등)으로 들어가는지와 회원 수가 늘지 않는지 본다.

**Acceptance Scenarios**:

1. **US2-AC1** **Given** 소셜 계정으로 가입한 회원이 로그아웃했다, **When** 같은 소셜 계정으로 로그인한다, **Then** 새 회원이 생기지 않고 같은 회원으로 로그인해 사용자 셸의 첫 화면에 들어간다
2. **US2-AC2** **Given** 관리자가 소셜 회원을 잠갔다, **When** 그 회원이 소셜 로그인을 한다, **Then** 로그인되지 않고 잠긴 계정이라는 안내가 보인다
3. **US2-AC3** **Given** 소셜 회원(비밀번호 없음)이 로그인했다, **When** 계정 메뉴를 연다, **Then** 계정 메뉴에 "비밀번호 변경"(`001-admin-menus` FR-005)이 보이지 않는다. 비밀번호 없는 계정에는 숨긴다

### User Story 3 - 소셜 로그인이 안 될 때 안내를 받는다 (Priority: P2)

제공자 화면에서 취소하거나, 제공자 확인이 실패하거나, 그 제공자 로그인을 쓸 수 없는 상태면 로그인 화면에 머물며 무엇이 잘못됐는지 안내를 받는다.

**Why this priority**: 실패해도 로그인 화면으로 돌아와 다시 할 수 있으면 핵심 흐름은 쓸 수 있다. 다만 원인 모를 빈 화면은 막아야 한다.

**Independent Test**: 제공자마다 제공자 화면에서 취소, 확인할 수 없는 제공자 응답, 그 제공자 설정이 없는 환경 각각에서 로그인 화면의 안내와 접속 이력을 본다.

**Acceptance Scenarios**:

1. **US3-AC1** **Given** 로그인 화면이다, **When** 제공자 화면에서 취소하거나 창을 닫는다, **Then** 로그인 화면에 그대로 있고 회원이 만들어지지 않는다
2. **US3-AC2** **Given** 소셜 로그인을 했다, **When** moa가 제공자 응답을 확인하지 못한다(위조, 만료, 다른 서비스용 응답), **Then** 로그인되지 않고 소셜 로그인에 실패했다는 안내가 보이며, 접속 이력에 실패로 남는다
3. **US3-AC3** **Given** 한 제공자(예: 디스코드)의 로그인 설정이 없는 환경이다, **When** 로그인 화면을 연다, **Then** 그 제공자의 로그인 단추만 보이지 않고, 다른 제공자와 아이디·비밀번호 로그인은 그대로 쓸 수 있다

---

### User Story 4 - 관리자가 소셜 로그인 기록을 본다 (Priority: P3)

관리자는 접속 이력에서 소셜 로그인의 성공과 실패를 아이디·비밀번호 로그인과 함께 본다.

**Why this priority**: 접속 이력은 이미 있는 기능(005)이라 소셜 로그인이 빠지지 않게만 하면 된다.

**Independent Test**: 소셜 로그인 성공 한 번, 실패 한 번 뒤 관리자로 접속 이력을 연다.

**Acceptance Scenarios**:

1. **US4-AC1** **Given** 소셜 로그인 성공과 실패가 한 번씩 있었다, **When** 관리자가 접속 이력을 연다, **Then** 두 건이 성공·실패로 보인다 [NEEDS CLARIFICATION: 소셜 로그인 건을 접속 이력에서 무엇으로 보이는가? (회원 식별 칸에 무엇을 적는지, 로그인 방식(구글/디스코드/아이디)을 구분해 보이는지). 회원 정보 모델(FR-004)이 정해져야 정할 수 있다]

### User Story 5 - 내 계정에 소셜 계정을 연결하고 해제한다 (Priority: P2)

로그인한 회원이 계정 설정 화면에서 구글이나 디스코드 계정을 연결한다. 그 뒤로는 그 소셜 로그인으로도 같은 계정에 들어간다. 필요 없어지면 연결을 해제한다.

**Why this priority**: 이미 계정이 있는 사람이 소셜 계정으로 들어오면서 회원이 둘로 나뉘지 않게 한다. 새 가입(US1)과 다시 로그인(US2)만으로도 기능은 쓸 수 있어 P2다.

**Independent Test**: 아이디·비밀번호 계정으로 로그인해 소셜 계정을 연결하고, 로그아웃 뒤 그 소셜 로그인으로 같은 계정에 들어가는지 본다. 이어서 연결을 해제하고, 마지막 로그인 수단은 해제가 막히는지 본다.

**Acceptance Scenarios**:

1. **US5-AC1** **Given** 로그인했고 그 제공자(구글 또는 디스코드)에 연결된 계정이 없다, **When** 계정 설정 화면에서 그 제공자 계정을 연결한다, **Then** 계정 설정 화면에 그 제공자가 연결됨으로 보인다
2. **US5-AC2** **Given** US5-AC1로 소셜 계정을 연결했다, **When** 로그아웃 뒤 로그인 화면에서 그 소셜 계정으로 로그인한다, **Then** 새 회원이 생기지 않고 연결한 그 계정으로 로그인한다
3. **US5-AC3** **Given** 그 소셜 계정이 이미 다른 회원에 연결되어 있다(그 소셜 계정으로 가입한 회원 포함), **When** 계정 설정 화면에서 그 소셜 계정을 연결하려 한다, **Then** 연결되지 않고 이미 다른 계정에 연결된 소셜 계정이라는 안내가 보인다
4. **US5-AC4** **Given** 소셜 계정이 어느 회원에도 연결되어 있지 않고 그 이메일을 쓰는 회원도 없다, **When** 연결하지 않은 채 로그인 화면에서 그 소셜 계정으로 로그인한다, **Then** 기존 계정에 자동으로 잇지 않고 따로 된 새 회원으로 가입한다 (이메일을 쓰는 회원이 있으면 US1-AC9대로 막힌다)
5. **US5-AC5** **Given** 비밀번호가 있는 계정에 소셜 계정이 연결되어 있다, **When** 계정 설정 화면에서 연결을 해제한다, **Then** 그 제공자가 연결되지 않음으로 보이고, 그 소셜 계정으로 로그인 화면에서 로그인하면 이 계정이 아니라 따로 된 새 회원으로 가입한다(FR-014·FR-015에 걸리지 않을 때)
6. **US5-AC6** **Given** 비밀번호가 없고 연결된 소셜 계정이 하나뿐인 회원이다, **When** 계정 설정 화면에서 그 연결을 해제하려 한다, **Then** 해제되지 않고 유일한 로그인 수단이라 해제할 수 없다는 안내가 보인다. 소셜 계정이 둘 이상이면 하나는 해제할 수 있다
7. **US5-AC7** **Given** 관리자 또는 운영자 계정으로 로그인했다, **When** 계정 설정 화면을 연다, **Then** 소셜 계정 연결이 보이지 않고, 연결을 시도해도 막힌다 (FR-007)
8. **US5-AC8** **Given** 로그인한 회원이 연결하려는 소셜 계정의 이메일을 다른 회원이 쓰고 있다, **When** 계정 설정 화면에서 그 소셜 계정을 연결한다, **Then** 연결되지 않고 "다른 방식으로 가입된 이메일" 안내가 보인다. 그 이메일을 쓰는 회원이 로그인한 본인이면(예: 같은 이메일의 구글이 이미 연결된 회원이 디스코드를 연결) 막히지 않고 연결된다 (FR-014)
9. **US5-AC9** **Given** 재가입 제한 기간 안이거나 영구 정지로 탈퇴한 소셜 계정이다, **When** 다른 회원이 계정 설정 화면에서 그 소셜 계정을 연결한다, **Then** 연결되지 않고 재가입이 제한된 계정이라는 안내가 보인다 (FR-015)
10. **US5-AC10** **Given** 로그인한 회원이 연결하려는 소셜 계정을 제공자가 이메일 없이 주거나 인증되지 않은 이메일로 준다(디스코드에서 이메일 인증을 하지 않은 계정 등), **When** 계정 설정 화면에서 그 소셜 계정을 연결한다, **Then** 연결되지 않고 "제공자에서 이메일 인증 후 다시 시도" 안내가 보인다 (FR-006, FR-014)

---

### Edge Cases

- 소셜 계정에서 이름이나 이메일을 바꾼 뒤 다시 로그인할 때: 같은 소셜 계정이면 같은 회원으로 로그인하고, 표시 이름(닉네임)은 바뀌지 않는다 (FR-005). moa에 저장한 소셜 이메일·이름도 따라 바꾸지 않고 가입(연결) 때 값을 그대로 둔다
- 같은 사람이 moa에 다른 방식의 계정을 이미 가지고 있을 때: 자동으로 잇지 않는다. 이메일이 같으면 가입을 막고 안내하고(FR-014), 이메일이 다르면 따로 된 새 회원이 된다. 이렇게 이미 회원이 된 소셜 계정은 다른 계정에 연결할 수 없다 (FR-006)
- 한 사람이 구글과 디스코드를 같은 이메일로 쓸 때: 하나로 먼저 가입하면 다른 하나로는 가입이 막힌다(FR-014). 가입한 계정의 계정 설정에서 다른 하나를 연결해 쓴다 (FR-006)
- 이메일을 주지 않거나 제공자가 인증하지 않은 이메일의 소셜 계정으로 가입할 때: 가입을 막고 "제공자에서 이메일 인증 후 다시 시도" 안내를 보인다. 회원을 만들지 않는다 (FR-014)
- 소셜 회원이 아이디·비밀번호 로그인 폼으로 로그인하려 할 때: 비밀번호가 없으므로 로그인되지 않는다 (비밀번호 없는 계정 규칙)
- 탈퇴한 소셜 회원이 같은 소셜 계정으로 다시 가입하려 할 때: 재가입 가능 일시 전이면 막는다(FR-015). 완전 삭제 뒤에도 같다. 관리자가 사용자 관리에서 삭제한 경우도 탈퇴와 같게 볼지는 회원 탈퇴 스펙에서 정한다
- 계정 설정에서 소셜 계정을 연결할 때: 가입과 똑같이 이메일 없음·미인증과 이메일 중복(FR-014), 재가입 제한(FR-015)을 확인한다. 그 이메일을 쓰는 회원이 연결하려는 본인이면 이메일 중복으로 막지 않는다 (FR-006)
- 관리자·운영자 계정이 소셜 로그인을 쓰려 할 때: 그 계정에는 소셜 계정을 연결할 수 없으므로, 그 사람이 소셜 로그인을 하면 관리자·운영자 계정과 상관없는 따로 된 회원이 된다(FR-014·FR-015에 걸리지 않을 때) (FR-006·FR-007)
- 소셜 회원에게 관리자가 역할을 주려 할 때: 막고 안내한다. 비밀번호 있는 회원이 소셜 계정을 연결한 뒤에도 같다 (FR-007)
- 두 창에서 같은 소셜 계정으로 동시에 처음 가입할 때: 회원은 하나만 만들어진다
- 처음 소셜 로그인 뒤 닉네임 입력 화면에서 떠날 때: 회원도 약관 동의 기록도 만들어지지 않는다. 다음 소셜 로그인 때 닉네임 입력 화면부터 다시 시작한다 (FR-005, FR-013)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 로그인 화면에 구글 로그인 단추와 디스코드 로그인 단추를 두어야 한다(MUST). 설정이 없는 제공자의 단추는 숨긴다. 지금의 아이디·비밀번호 로그인 폼은 그대로 둔다. 관리자·운영자는 키트 기본 계정(아이디·비밀번호)으로 로그인한다(`002-admin-users` 가정)

- **FR-005**: 소셜 계정으로 처음 가입하는 회원은 닉네임 입력 화면을 거쳐야 한다(MUST). 그 닉네임이 회원의 표시 이름이다. 소셜 계정 이름은 표시 이름으로 쓰지 않는다

  - 닉네임 규칙 [NEEDS CLARIFICATION: 닉네임 중복을 허용하는가? 길이·쓸 수 있는 글자는? 가입 뒤 바꿀 수 있는가?]
  - 닉네임을 넣고 필수 약관에 동의해야 가입이 끝난다(MUST, FR-013). 그 전에는 회원을 만들지 않는다. 닉네임 입력 화면에서 떠나면 가입이 안 된 것이고, 다음 소셜 로그인 때 닉네임 입력 화면부터 다시 시작한다

- **FR-006**: 로그인한 회원은 계정 설정 화면에서 자기 계정에 구글·디스코드 계정을 직접 연결하고 해제할 수 있어야 한다(MUST). 제공자마다 하나씩 연결한다. 연결한 뒤에는 그 소셜 계정으로 로그인하면 그 회원으로 로그인한다
  - 소셜 로그인은 이메일이 같다는 이유로 기존 계정과 자동으로 잇지 않는다(MUST). 연결되지 않은 소셜 계정으로 로그인 화면에서 로그인하면 따로 된 새 회원으로 가입하거나, 이메일이 겹치면 막힌다 (FR-002, FR-014)
  - 다른 회원에 이미 연결된 소셜 계정은 연결을 막고 안내한다(MUST)
  - 비밀번호가 없는 회원의 마지막 소셜 계정은 해제할 수 없다(MUST). 로그인 수단이 하나도 남지 않게 하지 않는다
  - 연결할 때도 가입과 똑같이 이메일 중복(FR-014)과 재가입 제한(FR-015)을 확인해 막는다(MUST). 단 그 이메일을 쓰는 회원이 연결하려는 본인이면 이메일 중복으로 막지 않는다
  - 연결은 로그인한 본인이 제공자 인증을 거쳐 직접 한다. 제공자가 이메일을 주지 않거나 인증되지 않은 이메일을 주면 연결을 막는다(MUST, FR-014). 미인증 이메일이 저장되면 그 이메일의 진짜 주인의 가입이 막힐 수 있다 (2026-11-17 정정)
  - 연결·해제는 기존 계정 설정 화면 안에 둔다. 새 메뉴가 아니므로 프로그램으로 등록하지 않는다 (`001-admin-menus` FR-008)
  - 관리자·운영자 계정에는 소셜 계정을 연결할 수 없다 (FR-007)
- **FR-007**: 관리자·운영자 계정(시스템 역할 `ADMIN`이거나 업무 역할을 가진 계정)은 소셜 로그인을 쓰지 않는다(MUST). `002-admin-users`의 "관리자와 운영자는 회원 활동을 하지 않는다" 취지를 따른다
  - 관리자·운영자 계정에는 소셜 계정을 연결할 수 없다(MUST). 계정 설정 화면에 소셜 계정 연결이 보이지 않는다
  - 소셜 계정이 연결된 회원(소셜 회원)에게는 시스템 역할 `ADMIN`이나 업무 역할을 줄 수 없다(MUST). 사용자 관리·역할 관리에서 주려 하면 막고 안내한다
- **FR-008**: 소셜 로그인의 성공과 실패를 접속 이력으로 남겨야 한다(MUST). 보관 기간과 동작은 `005-admin-login-history`(FR-001·FR-002)를 따른다. 접속 이력에서 어떻게 보이는지는 US4-AC1의 질문으로 정한다
- **FR-009**: 소셜 로그인 뒤 가는 화면은 `001-admin-menus` FR-006을 그대로 따른다(MUST). 처음 가입이면 닉네임 입력 화면을 거친 뒤 이 규칙대로 간다. 이 기능이 만드는 새 화면(닉네임 입력, 계정 설정 안의 소셜 계정 연결)은 메뉴로 열지 않으므로 프로그램이 아니다 (`001-admin-menus` FR-008)
- **FR-010**: 소셜 계정으로 가입한 회원은 비밀번호 없는 계정이어야 한다(MUST). 비밀번호 없는 계정에는 아이디·비밀번호 로그인과 비밀번호 초기화를 할 수 없다(`002-admin-users` FR-007)
- **FR-011**: 소셜 로그인이 실패하면(취소, 확인 실패, 설정 없음) 로그인되지 않고 회원도 만들어지지 않아야 한다(MUST). 취소가 아닌 실패는 로그인 화면에 원인을 알 수 있는 안내를 보인다
- **FR-012**: 소셜 로그인으로 들어온 회원의 로그인 유지·로그아웃은 아이디·비밀번호 로그인과 같아야 한다(MUST). 소셜 로그인만을 위한 따로 된 로그인 유지 규칙은 두지 않는다
- **FR-013**: 소셜 계정으로 처음 가입할 때 닉네임 입력 화면에서 이용약관과 개인정보 수집·이용에 동의받아야 한다(MUST)
  - 두 항목 모두 필수다. 둘 다 체크해야 가입을 진행할 수 있다
  - 각 항목은 요약만 보이고, 펼치면 전문을 본다
  - 가입이 끝나면 항목마다 동의 시각과 동의한 약관 버전을 회원에 남긴다(MUST). 가입이 끝나지 않으면 남기지 않는다
- **FR-014**: 가입하려는 소셜 계정의 이메일을 다른 회원이 이미 쓰고 있으면(어느 로그인 방식으로 가입했든) 가입을 막아야 한다(MUST)
  - "다른 방식으로 가입된 이메일"이라는 안내를 보인다. 기존 회원에 자동으로 잇지 않는다
  - 계정 설정의 연결(FR-006)에도 똑같이 적용한다. 단 그 이메일을 쓰는 회원이 연결하려는 본인이면 막지 않는다
  - 제공자가 이메일을 주지 않거나 인증되지 않은 이메일(디스코드 `verified=false` 등)을 주면 가입과 연결을 막아야 한다(MUST). "제공자에서 이메일 인증 후 다시 시도" 안내를 보이고 회원도 연결도 만들지 않는다
  - 막힌 사람이 기존 회원 본인이면 그 회원으로 로그인해 계정 설정에서 연결한다 (FR-006)
- **FR-015**: 탈퇴한 소셜 계정은 재가입 가능 일시 전까지 다시 가입할 수 없어야 한다(MUST). 계정 설정의 연결(FR-006)도 같은 기간 동안 막는다
  - 재가입 가능 일시는 "탈퇴 후 30일"과 "남은 정지 기간 끝" 중 늦은 때다. 영구 정지면 재가입할 수 없다 [NEEDS CLARIFICATION: 영구 정지 단계를 두는가? 정지 기간·단계는 회원 제재 기능이 정한다. 팀 확인 필요 (담당: 팀 회의)]
  - 회원이 완전 삭제된 뒤에도 확인할 수 있도록, 제공자·계정 식별자의 해시와 재가입 가능 일시를 남긴다(MUST). 원래 계정 식별자와 개인정보는 남기지 않는다
  - 010은 가입과 연결 때 이 기록으로 재가입 제한을 확인만 한다. 탈퇴·30일 안 복구·완전 삭제 흐름과 이 기록을 만드는 일은 회원 탈퇴 스펙이 정한다

### Key Entities *(include if feature involves data)*

- **회원**: moa의 계정. 키트 `users`를 쓴다. 소셜 계정으로 가입한 회원은 비밀번호가 없다. 어떤 정보를 갖는지는 FR-004·FR-005
- **외부 계정 연결** (잠정, FR-004): 회원과 소셜 계정(구글, 디스코드)을 잇는 정보. 회원 계정과 따로 두며 한 회원이 여러 개(제공자마다 하나)를 가질 수 있다. 제공자(GOOGLE·DISCORD)와 그 제공자가 주는 바뀌지 않는 계정 식별자로 같은 사람을 알아보고, 같은 제공자·식별자는 한 회원에만 이어진다. 가입(연결) 때 이메일을 함께 둔다(FR-014)
- **약관 동의 기록** (FR-013): 회원이 어떤 약관(이용약관, 개인정보 수집·이용)의 어느 버전에 언제 동의했는지
- **재가입 제한 기록** (FR-015): 탈퇴한 소셜 계정의 제공자·계정 식별자 해시와 재가입 가능 일시(영구면 없음). 회원이 완전 삭제돼도 남는다. 회원 탈퇴 스펙이 만들고 010은 읽기만 한다

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: moa에 처음 온 사람이 로그인 화면에서 소셜 로그인을 시작해 로그인 상태로 첫 화면에 들어가기까지 1분 안에 마친다 (닉네임 입력과 약관 동의 포함)
- **SC-002**: 이미 가입한 소셜 회원은 로그인 화면에서 단추 한 번과 제공자 계정 고르기만으로 다시 로그인한다
- **SC-003**: 같은 소셜 계정으로 몇 번 로그인해도 회원은 하나다
- **SC-004**: 소셜 로그인 시도(성공·실패)는 빠짐없이 접속 이력에 보인다
- **SC-005**: 수용 시나리오(US1~US5) 전부가 자동 테스트로 확인된다 (원칙 II)
- **SC-006**: 약관에 동의하지 않았거나, 이메일이 없거나 인증되지 않았거나, 이메일이 겹치거나, 재가입 제한 기간 안인 가입 시도는 하나도 회원을 만들지 않는다

## Assumptions

- 소셜 로그인은 사용자 쪽 회원을 위한 것이다. 관리자·운영자의 로그인 방식(키트 기본 계정)은 바꾸지 않는다. 관리자·운영자 계정은 소셜 로그인을 쓰지 않는다 (FR-007)
- 로그인 화면은 지금의 `/sign-in` 화면 하나다. 소셜 계정으로 처음 가입할 때만 닉네임 입력 화면(약관 동의 포함)이 더해진다 (FR-005, FR-013)
- 이번 범위는 웹 로그인만이다. 앱 클라이언트의 소셜 로그인은 나중에 정한다
- 제공자는 구글과 디스코드다. 카카오는 나중에 더한다. 네이버 등 그 밖의 제공자는 정하지 않았다. 같은 외부 계정 연결에 제공자를 더하는 방식으로 넓힌다
- 약관 문안(요약·전문)과 버전 값은 이 스펙이 정하지 않는다. 구현 전에 팀이 준비한다. 약관이 바뀐 뒤 기존 회원에게 다시 동의받는 일은 이 스펙의 범위가 아니다
- 이메일 중복 확인(FR-014)이 비교하는 것은 moa가 저장한 회원 이메일이다. 지금 아이디·비밀번호 회원(키트 `users`)에는 이메일 칸이 없으므로, 실제로는 외부 계정 연결에 저장된 이메일과 비교한다. 회원에 이메일이 생기면 그것도 비교한다
- 회원 탈퇴(탈퇴 상태, 30일 안 복구, 완전 삭제)는 이 스펙의 범위가 아니다. 010은 재가입 제한 확인만 한다 (FR-015)
- 소셜 로그인에 쓰는 설정 값(클라이언트 ID 등)은 환경마다 따로 주고 레포에 넣지 않는다 (원칙 VI)
- 나중에 고칠 곳: 이번 단계에서는 다른 스펙을 고치지 않는다. [NEEDS CLARIFICATION]이 풀리면 아래를 함께 고친다
  - `002-admin-users` FR-004: 사용자 관리 목록에 보일 회원 항목 (FR-004의 답)
  - `002-admin-users` FR-007: 드로어의 막는 규칙에 "소셜 회원에게 시스템 역할 `ADMIN`을 줄 수 없음"을 더한다. 역할 관리(`003-admin-roles`)에서 업무 역할을 줄 때도 같은 규칙 (FR-007). 드로어의 "삭제"를 탈퇴와 같게 볼지는 회원 탈퇴 스펙과 함께 정한다 (FR-015)
  - `002-admin-users` 가정 "회원 가입·로그인 방식과 회원 정보 모델은 사용자 쪽 기능이 정한다": 이 스펙(010)을 가리키게 고친다
  - `008-party` 가정 "회원 가입은 아직 없으므로 시드 계정으로 시험한다", "닉네임은 회원 가입·프로필에서 정한다"와 FR-027의 표시 이름: 표시 이름을 닉네임으로 바꾼다 (FR-005). 팀 공유 필요 (담당: 008-party 담당)
  - `001-admin-menus` FR-008 프로그램 표: 고칠 것 없음. 이 기능의 새 화면은 프로그램이 아니다 (FR-009)
  - `005-admin-login-history`: 접속 이력에 로그인 방식을 보이기로 하면 (US4-AC1의 답)
  - `specs/README.md` 맞춰야 할 경계
    - "회원 정보 모델" 줄: FR-004·FR-005가 정해지면 지운다
    - "관리자·운영자 계정의 회원 활동 금지" 줄: 010은 FR-007로 소셜 로그인·연결을 막았다고 적는다
    - "추가로 쓸 키트 헬퍼" 줄: 헬퍼 유무가 팀 확인되면 oauth를 더한다. 표의 출처 칸도 함께
    - "회원 탈퇴 상태와 유예 기간" 줄: 010이 정한 재가입 제한(탈퇴 후 30일과 남은 정지 기간 끝 중 늦은 때, 영구 정지는 불가, 완전 삭제 뒤에도 제공자·식별자 해시와 재가입 가능 일시를 남김)을 적는다. 탈퇴 상태·30일 복구·완전 삭제와 재가입 제한 기록 만들기는 회원 탈퇴 스펙이 맡는다고 적는다
  - 회원 탈퇴 스펙(아직 없음): FR-015의 재가입 제한 기록을 만든다
  - 회원 제재 기능(`specs/README.md` "회원 제재·해제", 아직 없음): 정지 기간과 영구 정지 단계를 정하면 FR-015의 재가입 가능 일시 계산에 쓴다
